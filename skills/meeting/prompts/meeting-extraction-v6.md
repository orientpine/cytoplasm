# meeting-extraction-v6 (현행)

W2-3 회의록 구조화 추출 프롬프트. `skills/meeting/scripts/meeting_llm.py`가
마커 아래 본문을 읽어 `{{MY_NAMES}}`, `{{MEETING_TEXT}}`, `{{SLIDES}}`를 치환해
단일 user 메시지로 전송한다. 변경 시 버전 파일명을 올린다.

버전 이력 (openai-codex gpt-5.4 원샷 실검증):
- v1 폐기: "지시문+스키마 예시 선행" 구조 → codex가 프롬프트를 문서로 오인해 에코.
- v2 폐기: "=== 회의록 시작/끝 ===" 마커 + 스키마 불릿 나열 → 동일 에코 재발.
- v3 채택: 마커/스키마 블록 없는 평문 지시-마지막 구조 — glm-main과 codex 양쪽에서
  patent/clean 픽스처 파싱 성공 확인.
- v4 (2026-08-26): 연구 회의록 서식 재설계에 맞춰 meeting/summary/discussion/
  open_questions/next_meeting 키를 추가하고 decisions에 basis를 붙였다. 발표자료를
  받는 `{{SLIDES}}` 자리와 대명사·모호 지시어 교정 규칙이 함께 들어왔다. **v3의 교훈은
  그대로 지킨다** — 펜스도 스키마 블록도 쓰지 않고 재료가 먼저, 지시가 마지막이다.
  codex 원샷은 반드시 `-t todo`(무해 툴셋)와 함께 호출할 것.
- v5: 현재 미결 Action Item 자료와 resolved_actions 키를 추가해 프로젝트별 Action Item 데이터베이스의 완료 항목을 추적한다.
- v6 (2026-09-01): 전사본이 화자분리를 거치면서 `{{MEETING_TEXT}}` 에 `[00:03:12] 화자1 · 김민수`
  블록 헤더와 `- 화자: 화자1=김민수 [자기소개 00:03:12] · 화자2=미상` 범례가 실린다. 규칙 기반
  이름 추정은 자기소개 문장만 잡으므로, 호명·소개처럼 문맥이 필요한 근거는 여기서 speakers
  키로 받는다. 이름을 **지어내는 것이 미상보다 나쁘다** — 근거가 없으면 null 이다.

<<<PROMPT>>>
아래 회의록을 읽어라.

{{MEETING_TEXT}}

{{SLIDES}}

아래는 이 과제의 현재 미결 Action Item 목록이다.

{{OPEN_ACTIONS}}

이제 이 회의록에서 다음 키를 가진 JSON 객체 하나만 출력하라.

meeting: 회의 자체의 정보 — title(회의 제목), date(회의 날짜 YYYY-MM-DD, 없으면 null), attendees(참석자 이름 문자열 배열), place(장소, 없으면 null).
summary: 이 회의를 3~7줄로 요약한 문자열 배열. 결정·진행상황·위험·다음 단계만 담고, 본문을 읽지 않아도 회의 결과를 알 수 있게 쓴다.
decisions: 회의에서 확정된 결정사항. text(결정 내용)와 basis(근거가 된 회의록 원문 요지) 키의 객체 배열. 아직 논의 중이거나 보류된 제안은 여기 넣지 말고 open_questions로 보내라.
todos: 내가 담당인 액션아이템, title/deadline/basis 키의 객체 배열.
milestones: 특정 날짜에 도달해야 하는 이벤트 — 제출 마감·발표·심사·중간점검 등, title/deadline/basis 키의 객체 배열, 반복 업무 제외.
others: 타인 담당 액션아이템, owner/title/deadline/basis 키의 객체 배열.
discussion: 주제별 논의 요지, topic(주제)/points(요지 문자열 배열)/basis 키의 객체 배열. 발언자별 대화록이 아니라 주제별 요약이다.
open_questions: 아직 결정되지 않았거나 확인이 필요한 항목, title/owner/basis 키의 객체 배열. 담당자도 마감도 없는 할 일은 액션아이템이 아니라 여기에 넣는다.
next_meeting: 다음 회의가 정해졌으면 when(일시)과 note(목적·준비물) 키의 객체, 아니면 null.
resolved_actions: 위 미결 Action Item 목록 중 이번 회의에서 완료·종결로 확인된 항목. id(관리번호를 원문 그대로)와 basis 키의 객체 배열. 목록에 없는 번호를 지어내지 말고, 확인된 것이 없으면 빈 배열로 두어라.
speakers: 회의록 본문의 화자 라벨(화자1, 화자2 …)을 실제 이름에 대응시킨 객체 배열, label/name/basis 키. 근거는 자기소개("저는 ○○입니다"), 호명("김 박사님 말씀대로"), 소개("이분은 ○○ 박사님")처럼 회의록에 적힌 것만이며, 근거가 없는 라벨은 name을 null로 둔다. 화자 라벨이 없는 회의록이면 빈 배열.

"나"는 다음 이름 중 하나로 지칭된다: {{MY_NAMES}}. 담당자가 불명확한 항목은 todos에 넣고 basis에 "담당 불명확"을 덧붙여라. deadline과 date는 회의록에 명시된 날짜만 YYYY-MM-DD로 쓰고(연도가 없으면 회의 날짜 기준 가장 가까운 미래), 날짜가 없으면 null. basis는 근거가 된 회의록 원문 요지이며 한 줄로 줄여 쓴다.

발표자료가 함께 주어졌다면 대명사와 모호한 지시어를 교정하는 데에만 쓴다. "이거·그것·저번 거·그쪽" 같은 표현을 임의로 구체화하지 말고, 직전 문장의 명사 → 발표자료 슬라이드 제목 → 그림·표 번호 순으로 후보를 찾아 정식 명칭으로 바꿔라. 사람 이름은 참석자 명단과 대조하고, 과제·실험·장비 이름은 발표자료의 표기를 따른다. 근거가 하나뿐이라 확신할 수 없으면 "이것(추정: 그림 2)"처럼 추정임을 표시하라. 어떤 후보와도 맞출 수 없으면 원문 표현을 그대로 두고 open_questions에 확인 필요 항목으로 넣어라. 발표자료에만 있고 회의에서 논의되지 않은 내용을 결정사항이나 액션아이템으로 만들지 마라.

회의록에 없는 내용을 지어내지 마라. 설명 금지, 마크다운 펜스 금지, JSON 객체 하나만 출력하라.
