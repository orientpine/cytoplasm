# meeting — 회의록 인제스트 (W2-3)

명시적 `!meeting` 신호가 붙은 회의록(md/txt/pdf ≤25MiB 또는 명령 본문)에서 결정사항/액션아이템을
추출해 ①내 항목 → Kanban 카드 + `~/state/milestones.yaml`, ②타인 항목 →
#team 규약(v0) 게시, ③상세 노트 → `~/notes/meetings/`(700, W2-4가 자동
색인)를 수행한다.

## 동작 방식 (중요 — 에이전트가 지켜야 할 규칙)

1. **소유자가 메시지 시작에 토큰 경계가 있는 `!meeting`을 명시한 본문 또는
   md/txt/pdf 첨부만** 게이트웨이 플러그인(`00-meeting-gate`)이 나(에이전트
   LLM)에게 도달하기 전에 가로채 자동 처리한다. 파일명·확장자·MIME·DM 여부는
   회의 의도가 아니며, 표식 없는 첨부는 일반 요청으로 전달된다. 어댑터가
   소유자 검증 후 `meeting_intent=True` boolean metadata를 설정한 경우만 같은
   명시 의도로 신뢰한다. 트리거된 메시지에 대해 내가 할 일은 없다 (플러그인이
   접수/결과를 직접 통지한다).
   - **통지 위치 (2026-08-23, 소유자 지시)**: 접수 ACK와 처리 완료/거부 통지는
     `!meeting` 지시 메시지에 **앵커된 스레드**로 간다(플러그인이 ACK 시 스레드를
     만들고, CLI는 `--notify-message-id`로 같은 스레드에 결과를 게시 — 원 채널은
     깨끗하게 유지). 어댑터가 메시지 id를 노출하지 않으면 기존대로 원 채널에 게시한다.
     민감 문서의 완료 문구는 기존 마스킹(라벨·건수·노트 경로만) 그대로다.
   - 에이전트가 CLI를 직접 실행하는 경로(아래 2)에서도 채널 지시라면
     `--notify-channel <채널ID> --notify-message-id <지시 메시지ID>`를 함께 넘긴다.
2. 사용자가 **로컬 파일 경로**를 언급하며 회의록 처리를 요청하면, 파일
   내용을 절대 읽지 말고(컨텍스트에 넣지 말고) 아래 CLI를 실행하라:

   ```bash
   python3 ~/.hermes/skills/meeting/scripts/meeting_cli.py ingest \
     --file <경로> --label "<회의 라벨>" --project "<과제명>" \
     [--with-evidence] [--slides <발표자료 경로>]
   ```

   **`--project` 는 과제 회의면 항상 붙인다** — 그것이 action item 원장과 관리번호가 붙는
   유일한 조건이다. 과제를 모르면 생략해도 되고, 그때 CLI 가 라벨을 이미 있는 과제 폴더
   이름과 대조해 스스로 찾는다(못 찾으면 번호 없이 진행하고 통지에 그렇게 적는다).

   소유자가 **발표자료를 함께 준** 경우에만 `--slides`를 붙인다(여러 번 지정 가능,
   pdf·pptx·docx·hwpx·xlsx·md·txt·csv). 발표자료 본문도 컨텍스트에 넣지 말고 경로만 넘긴다.

1-1. **`!meeting` 만 쓰고 아무것도 붙이지 않으면** 플러그인이 `--from-pending-transcript` 로
   CLI 를 띄운다. CLI 는 Drive `전사본/<과제>/<연도>/` 를 훑어 **아직 회의록이 없는 전사본**을
   찾는다 — 대응은 회의록 폴더에 `회의록-<전사본 파일명>` 을 포함한 파일이 있는지로 본다.
   정확히 1건이면 그것으로 회의록을 만들고, **과제는 전사본의 경로가 알려주므로 추측하지 않는다.**
   0건이면 "모든 전사본에 이미 회의록이 있다", 2건 이상이면 목록을 통지하고 멈춘다(exit 7) —
   회의록 여러 개가 한 번에 만들어지는 것보다 고르지 않는 편이 낫다.

1-2. **같은 일을 매일 밤 자동으로 한다** — `meeting_pending_transcript_watch.py` 가
   00:00 KST 에 돌며 미처리 전사본을 상한(`MEETING_PENDING_LIMIT`, 기본 5)까지 `--pending-name`
   으로 순차 처리한다. 대화형은 다건이면 멈추지만 야간 배치는 멈출 수 없다 — 매일 밤 같은 이유로
   서면 기능이 죽는다. 만들 것이 없는 밤에는 아무 말도 하지 않는다(`--no-agent` 의 빈 stdout =
   침묵). 내가 이 워처를 대신 실행하거나 결과를 지어내지 않는다.

2-1. **회의록은 어떤 경로로 요청받든 이 CLI 가 만든다 — 내가 손으로 쓰지 않는다.**
   소유자가 Drive 의 전사본이나 기존 문서를 가리키며 "회의록 써줘"라고 해도 마찬가지다.
   그 파일을 먼저 로컬로 내려받아(`gws drive files get --params '{"fileId":…,"alt":"media"}'`)
   `--file` 로 CLI 에 넘긴다. 내가 직접 회의록을 작성해 `drive_publish_cli --kind meeting` 으로
   발행하면 **원장(action-items.csv)을 거치지 않아 관리번호가 존재할 수 없고**, 내가 그 자리에서
   번호를 지어내게 된다(2026-08-27 실제 발생: `TR-260825-M01`). 그 발행 경로는 이제
   `DRIVE-PUBLISH-REFUSED` 로 막혀 있다.

3. **금지**: 회의록 원문을 내 컨텍스트/응답에 붙여넣기. 민감도 게이트
   (constraint 6)는 CLI 안에서 LLM 호출 전에 실행되며, 특허 민감 문서는
   비-GLM(openai-codex)으로만 추출되고 상세는 `~/notes/meetings/`(700)에만
   남는다. 민감 문서의 각 액션아이템은 공개 문자열(제목·마감·근거)을
   동일한 결정 규칙(`sensitivity-rules.yaml`)으로 **항목 단위 재검사**한다 —
   어떤 규칙에도 걸리지 않은 항목만 `[민감회의] <제목> (마감 …)` 정보형
   카드(근거 + 로컬 노트 출처)로 생성되고, 하나라도 걸리거나 규칙을
   확인할 수 없으면 일반 마스킹 카드로 남는다(fail-closed). 문서 단위
   보호(비-GLM 라우팅, #team 미게시, 원문은 노트에만)는 그대로다.
   **내 액션아이템 카드는 생성 직후 항상 `blocked/needs_input`으로 전환된다.**
   사람의 실행·검토가 필요한 항목이므로 gateway dispatcher가 LLM 작업자를
   배정해서는 안 된다. 소유자가 검토한 뒤에만 수동으로 다음 상태를 정한다.
4. 스캔본 PDF(텍스트 레이어 없음)는 CLI가 "수동 변환 요청"으로 응답한다 —
   내용을 추측해 채우지 마라.
5. 처리 결과 질문에는 CLI가 출력한 JSON 요약(건수/노트 파일명)만 사용하라.

## 회의록 서식 (v1.1.0, 2026-08-26 소유자 지시)

노트는 `meeting_minutes.render`가 단독으로 그린다. 순서는 웹 리서치로 확인한 연구 회의록
골격이다 — **메타데이터 헤더**(일시·장소·참석·발표자료·원본·작성) → **한눈에 보기**(TL;DR)
→ **결정사항** → **액션 아이템**(담당·마감·근거 열이 있는 표) → **마일스톤** → **논의 요지**
→ **미결·확인 필요** → **다음 회의** → **부록**. 헤더의 일시는 추출된 **회의 날짜**이지
처리 시각이 아니다. 비어 있는 조건부 섹션은 `- (없음)`으로 채우지 않고 통째로 생략한다.
모델이 추출한 논의 주제는 `논의 요지` 아래의 굵은 목록 항목으로만 렌더한다. 추출 문자열을
절 제목으로 승격하지 않으므로 특정 참석자 이름이나 개인 중심 Action Item 문구가 공용 회의록의
섹션 제목이 될 수 없다.

**근거는 전부 하단이다.** 본문에는 `[근1]` 같은 짧은 마커만 남고, 근거 원문·지식 파사드
출처(`[E1]`)·원문 전사본은 `## 부록 · 근거와 원문` 아래 A/B/C 소절에 모인다. 회의록과 근거는
**한 파일**이며 사이드카로 쪼개지 않는다(`*.evidence.json`은 기존 추적용 사이드카 그대로).
`[^1]` 각주 문법은 쓰지 않는다 — 지원 렌더러가 정의를 문서 끝으로 옮겨 우리 제목을 비우고,
Drive 프리뷰의 지원 여부도 확인되지 않았다.

## 과제 양식과 Action Item 데이터베이스 (`--project`, v1.2.0)

`ingest --project <과제명>` 은 Drive `autophagy/회의록/<과제명>/` 을 회의 상태의 출처로 읽는다.
세 가지가 달라진다.

1. **과제의 회의록 양식대로 배치한다.** 그 폴더의 양식 파일(`meeting_template.parse`)이 정한 절
   번호·제목·순서를 그대로 따르고, 회의가 채울 것이 없는 절은 `- (해당 없음)` 으로 남긴다.
   읽는 형식은 `.md`/`.markdown`/`.txt` 뿐이다. `.hwp`·`.docx` 양식은 **추측하지 않고**
   `TEMPLATE-UNREADABLE project=… name=…` 을 stderr 에 남긴 뒤 내장 골격으로 되돌아간다.
   양식이 없을 때도 같은 내장 골격이다.
2. **미결 action item 이 파일 하나에 누적된다.** `<과제명>/action-items.csv` 가 미결·신규·완료
   행을 한 파일에 들고 있으며 완료 행은 지우지 않는다. 열은
   `id,project,title,owner,due,status,opened_on,opened_note,closed_on,closed_note,basis`.
   기존 항목은 모델이 `resolved_actions` 로 그 **관리번호를 보고했고** 그 번호가 실제로 그 과제의
   미결 행일 때만 닫힌다. 모르는 번호와 이미 닫힌 번호는 무시한다(번호를 지어내지 않는다).
3. **회의록은 action item 표로 끝난다.** 양식의 action 절(양식이 없으면
   `## Action Item 종합`) 아래에 `### 가. 미결 Action Items` 와 `### 나. 신규 Action Items` 가
   각각 `관리번호 | 내용 | 조치기한 | 담당기관` 표로 붙는다.

**관리번호는 정확히 10자**다: `<영문 4자><연도 2자><일련 4자>`, 예 `HOGS260015`. 영문 4자는 과제명의
한글 초성을 로마자로 옮긴 것이고(해양고신뢰성 → ㅎㅇㄱㅅ → HOGS), 충돌하면 마지막 글자로 밀린다.
배정은 `autophagy/회의록/project-codes.csv` 레지스트리가 **전 과제에 걸쳐 유일하게** 유지하므로,
나중에 여러 과제의 번호를 한 통에 모아도 부딪히지 않는다.

번호는 **항목이 처음 열릴 때 한 번** 발급되고 끝날 때까지 바뀌지 않는다 — 미결 표에 있든 신규 표에
있든 같은 번호이며, 미결/신규는 번호의 속성이 아니라 그 시점의 상태다. 일련번호는 과제·연도마다
0001 부터 다시 시작하고 10,000건이 한도다. 한도에 닿으면 번호를 지어내지 않고
`ACTION-ID-EXHAUSTED` 를 남긴 채 **회의록은 그대로 쓴다** — 신규 표의 번호 자리만 `—` 가 되고
원장은 건드리지 않는다(번호 없는 행이 원장에 들어가면 원장이 거짓말을 한다).

`--project` 가 없거나 민감 회의면 Drive 에 아무것도 쓰지 않는다. 그때도 표는 그대로 렌더되며
관리번호 자리에 `—` 가 들어간다. 상태 파일 경로와 발행 진입점(`publish_state_file` /
`fetch_state_file`)의 정본은 `../../docs/guide/drive-publish.md` 다.

## 발표자료 기반 지시어 교정 (`--slides`)

`--slides <경로>`(반복 가능, pdf·pptx·docx·hwpx·xlsx·md·txt·csv)를 주면 슬라이드 텍스트가 `[슬라이드 N]` 라벨과
함께 추출 프롬프트에 재료로 실린다. 프롬프트는 보수적 교정 규칙을 강제한다 — 임의 구체화
금지, 후보 탐색은 직전 문장 명사 → 슬라이드 제목 → 그림·표 번호 순, 확신이 없으면
`이것(추정: 그림 2)`처럼 추정 표기, 어떤 후보와도 못 맞추면 원문을 유지하고 `open_questions`로
보낸다. 발표자료에만 있고 회의에서 논의되지 않은 내용은 결정사항·액션아이템이 되지 않는다.

- **fail-soft**: 스캔본·미지원 형식·없는 파일이어도 ingest는 계속되고, 노트 헤더에
  `<파일명> — 읽지 못함: <사유>`로 남는다.
- **fail-closed**: 발표자료 본문은 회의 본문과 **함께 민감도 게이트에 합산**된다. 특허 내용이
  발표자료에만 있어도 문서는 민감으로 판정되어 비-GLM 경로로 간다.

## 소유자 참고자료 (자동)

회의 라벨·과제명에 **전사 본문의 상위 낱말**(구어 군더더기 제외, 상한 6개)을 더한 질의로
소유자의 Drive 참고자료 폴더(`DRIVE_REFERENCE_ROOT`, 기본 `KIMM`)를
찾아 **발표자료와 같은 경로**로 넣는다. 에이전트가 따로 할 일은 없다 — 옵션도 없고, 경로를
넘길 필요도 없다.

- 참고자료 본문은 발표자료와 **함께 민감도 게이트에 합산**된다. 특허 내용이 참고자료에만
  있어도 문서는 민감으로 판정되어 비-GLM 경로로 간다.
- 추출 프롬프트에는 「소유자 참고자료」 블록으로 들어가고, 노트 헤더 표에
  `| 참고자료 | <파일명> |` 행으로 남는다(읽지 못한 자료는 사유와 함께).
- Drive 옵트인(`DRIVE_PUBLISH_ENABLED=1`)이 꺼져 있거나 폴더가 없으면 **아무 일도 일어나지
  않는다** — 참고자료 없이 회의록을 쓸 뿐 ingest 는 멈추지 않는다.

## 지식 파사드 근거

`--with-evidence`는 회의 제목·참석자·주제로 읽기 전용 지식 파사드를 한 번 호출해
관련 선행 회의와 노트를 추출 프롬프트 재료로 넣는다. 근거 본문도 기존 민감도 게이트에
합산하며 patent-sensitive 또는 센티널 근거는 비-GLM으로만 처리한다. 생성 인용은 팩의
`[En]`만 허용하고 출처는 파사드 `sources` 형식 그대로 로컬 회의 노트 말미와 mode 0600
`*.evidence.json`에 남긴다. 민감 회의 원문과 본문은 기존처럼 카드·공개 표면에 싣지 않는다.

근거가 없으면 `근거 없음`, 조회 불가면 `근거 수집 불가`를 기록하고 회의록 생성은 계속한다.
재시도·임계값 하향·자체 검색은 하지 않는다. `meeting evidence --title ... --topics ... --json`은
원문 대신 `evidence_count`와 계층 상태만 미리 보여준다. 정본은
[`지식 계층 규약`](../../docs/guide/지식-계층-규약.md)이다.

## Drive 게시 (회의록)

민감 회의가 **아닐 때만**, `DRIVE_PUBLISH_ENABLED=1`이면 노트가 cha 본인 Drive의
`autophagy/회의록/[<과제>/]<YYYY>/<회의일>_회의록-<라벨>.md`에 자동 업로드된다. `--project` 를 주면
과제 폴더 아래로 들어가 같은 과제의 전사본·용어집과 나란히 놓인다(speechtotext 체인이 자동으로
넘겨준다). 라벨은 `--label`
(없으면 파일명, 확장자 제외)이고, 발행 코드는 마운트 경로에서도 `automation` 을 찾도록
런타임 루트를 해석한다 — 그러지 못하던 동안에는 업로드가 `DRIVE-PUBLISH-SKIP reason=ImportError`
로 조용히 건너뛰어졌다. 날짜는 추출한 회의일이며, 날짜가 없거나 해석할 수 없으면 처리일로 안전하게 대체한다.
같은 회의를 다시 인제스트해도 사본이 아니라 기존 파일이 갱신된다. 민감도 게이트에 걸린
회의록은 업로드하지 않고 `DRIVE-PUBLISH-SKIP reason=sensitive`만 남긴 채 로컬 노트로만
보관한다. 발행은 공용 파사드 `automation.drive_outputs`만 쓰며 best-effort다 — 실패해도 로컬
노트와 카드 생성은 그대로 진행된다. 상세: `../../docs/guide/drive-publish.md`.

## 산출물을 만들 때 (중요)

이 스킬이 만드는 로컬 노트(`~/notes/meetings/*.md`)는 **부록(`## 부록 · 근거와 원문`) 아래에 음성
전사본을 그대로 안고 있다.** 전사본은 고유명사·용어에 인식 오류가 있으므로 공정표·계획서·보고서
같은 산출물의 출처로 쓰지 않는다.

- 산출물은 **완성 회의록**에서 작성한다 — Drive `autophagy/회의록/<과제명>/<연도>/`.
  `ingest --project <과제명>` 을 주면 그 자리에 발행되고, 카드 본문도 그 정본 경로를 먼저 가리킨다.
- 코드에서 노트를 읽어야 하면 `meeting_minutes.finalized_view(text)` 로 부록 위만 취한다.
  경계를 따로 자르지 않는다(상수와 함수가 같은 모듈에 있다).
