# 공급망 자동 재개 확장 설계

현재 자동 재개는 승인 레코드만으로 실행 인자를 완전하게 복원할 수 있는
`skill-deploy`에 한정한다. `managed-activate`와 `skill-publish`는 필요한 경로 맥락이
승인 레코드에 없으므로 `SUPPORTED_KINDS`에 넣지 않는다. 이 문서는 확장 전에 내려야
할 결정을 고정하며, 현재 지원 집합을 확장하지 않는다.

## 1. 재개 맥락의 저장 위치

**결론: 재개 맥락은 승인 레코드 필드에 추가하지 않고, 스키마와 무결성을 검증하는
전용 상태 파일에 둔다.**

승인 레코드는 소유자가 허용한 행위와 해시를 증명하는 인가 원장이다. 여기에 fetch가
만든 격리 디렉터리나 저장소 작업 경로처럼 변하는 운영 상태를 섞으면, 인가 바인딩과
실행 진행 상태의 수명주기가 결합된다. 전용 상태 파일은 체크아웃 밖의 0700 디렉터리에
0600·원자 교체로 기록하고 다음 필드를 기계 검증한다.

- 스키마 버전과 요청 key/kind
- 승인 레코드의 action hash 및 대상 digest
- 허용된 런타임 루트 아래의 정규화된 경로와 해당 콘텐츠의 provenance digest
- 생성 릴리스와 완료/회수 상태

파일이 없거나 깨졌거나 승인 바인딩과 다르거나 경로가 허용 루트를 벗어나면 재개하지
않고 레코드를 보존한다. 상태 파일은 인가를 새로 만들지 않으며, 실행 직전 기존 승인
레코드를 다시 검증한다.

## 2. `SUPPORTED_KINDS` 확장 조건

**결론: 각 kind가 승인만으로 재구성 가능한 검증된 맥락, 멱등 재개 어댑터, 재조정과
회수 경로, 격리된 회귀 테스트를 모두 갖춘 뒤에만 그 kind를 `SUPPORTED_KINDS`에
추가한다.**

공통 사전조건은 다음과 같다.

1. 전용 상태 파일이 승인 action hash와 대상 digest에 묶이고, 스키마·권한·경로·콘텐츠
   provenance를 fail-closed로 검증한다.
2. 재개 명령은 저장 맥락에서 결정론적으로 만들어지며 임의 인자, 셸 해석, 네트워크에서
   새로 발견한 경로를 받지 않는다.
3. 기존 key별 실행 lease를 사용하고, 재조정으로 이미 실현된 효과는 재실행하지 않고
   승인 게이트의 CAS 회수만 수행한다.
4. 성공·일시 실패·결정적 실패·손상/유실 맥락을 단위 및 무외부효과 종단 테스트로
   고정하고, 유예·감사 로그·소유자 통지 계약을 갖춘다.

`managed-activate`는 quarantine 디렉터리와 manifest/provenance/skill 콘텐츠 digest를
검증해 보존하고 `--activate-managed` 어댑터가 멱등임을 증명해야 한다. `skill-publish`는
대상 managed repository의 불변 식별자와 게시 입력 digest를 보존하고, publish CLI가
같은 릴리스를 중복 발행하지 않는 재조정 어댑터를 가져야 한다. 어느 하나라도 없으면
현재처럼 `retain`한다.

## 3. 위험 분석과 완화

자동 재개가 잘못되면 낡거나 바뀐 격리 산출물을 활성화하거나, 다른 저장소에 발행하거나,
이미 끝난 외부효과를 중복 실행하거나, 손상된 상태 때문에 무한 재시도할 수 있다. 경로
주입이나 심링크 치환은 특권 경계까지 잘못된 입력을 전달할 수 있고, 상태 파일을 승인으로
오인하면 소유자 인가 범위도 넓어진다.

**결론: 맥락의 부재·불일치·손상은 모두 보존 후 중단하고, 승인 해시와 콘텐츠
provenance의 이중 바인딩, 허용 루트·심링크 거부, 원자적 0600 상태, key lease,
실행 전 재조정, 제한된 백오프와 감사/통지를 함께 적용해야만 자동 재개를 허용한다.**

이 완화책은 잘못된 실행보다 지연을 택한다. 따라서 검증기가 판단하지 못하면 사람에게
넘길 수 있도록 승인 레코드와 상태를 남기며, 부분 구현 상태에서는 동결 테스트가
`SUPPORTED_KINDS == frozenset({"skill-deploy"})`를 강제한다.
