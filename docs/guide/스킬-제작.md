# 스킬 제작·배포 가이드 (W1-8)

Hermes 인스턴스(agent/peer)에 올라가는 스킬을 만들고, v2.2 스킬 게이트
(**샌드박스 → 자가승인 → 마운트**)를 통과시켜 배포하는 방법.

## 1. 스킬 형식 (agentskills.io)

스킬은 repo `skills/<skill-name>/` 디렉터리 하나다. Hermes는
`~/.hermes/skills/<skill-name>/`에 디렉터리를 드롭하면 자동 발견한다
(`hermes skills list`에 `local/local/enabled`로 표시 — 별도 install 불필요).

```
skills/<skill-name>/
├── SKILL.md            # 필수. frontmatter + 사용법 본문
└── scripts/
    ├── <main>.sh       # 스킬이 부르는 실행물(선택)
    └── scenario.sh     # 필수(배포 파이프라인용). 샌드박스 검증 시나리오
```

`SKILL.md` frontmatter 필수 필드 — 파이프라인 lint가 강제한다:

```yaml
---
name: <skill-name>        # 디렉터리명과 정확히 일치 (^[a-z0-9][a-z0-9-]{1,40}$)
description: "10자 이상의 설명."
version: 1.0.0            # 권장
license: MIT              # 권장
metadata:
  hermes:
    tags: [ ... ]         # 권장
---
```

### scenario.sh 계약 (샌드박스 필수 통과 조건)

- 파이프라인이 `env -i HOME=… PATH=/usr/bin:/bin AUTOPHAGY_DEMO_SECRET=DUMMY-…`
  환경에서 실행한다. **실시크릿은 절대 주입되지 않는다.**
- 시나리오는 자기 시크릿이 `DUMMY-` 접두사인지 스스로 확인하고, 실토큰
  모양(`sk-`, `ghp_`, `Bot `)이면 즉시 실패해야 한다. 배포 리뷰의 secret-scan은 `sk-…`, `ghp_…`, `Bot|Bearer + 8자 이상 토큰형 문자열`, PRIVATE KEY 블록을 차단한다. **주석/문서 문자열에도 `bot ` + 단어 조합을 피하라** — 실제 사례: `# Discord bot attachment ceiling` 주석이 오탐으로 배포를 막았다(리워드로 해결). 스캐너는 숫자/점 포함 토큰만 매치하도록 개선됐지만 원칙적으로 토큰 모양 문자열 자체를 쓰지 말 것.
- 성공 시 stdout에 `SCENARIO-PASS` 마커를 출력하고 exit 0. 그 외 전부 실패.
- 참조 구현: `skills/hello-autophagy/scripts/scenario.sh`.

#### peer와 같은 격리 조건으로 로컬 재현

리포 안에서 `bash skills/<name>/scripts/scenario.sh`만 실행하면
`AUTOPHAGY_REPO_ROOT`의 기본값이 현재 리포를 가리켜, 실제 peer 검토에서는 없는 공유 모듈을
lazy import할 수 있다. 로컬 PASS와 peer FAIL이 갈리는 것을 막으려면 스킬을 체크아웃 밖으로
복사하고 최소 환경으로 실행한다.

```bash
rm -rf /tmp/isolated
mkdir -p /tmp/isolated
cp -r skills/<name> /tmp/isolated/
tmp_home="$(mktemp -d)"
(
  cd /tmp/isolated/<name>
  env -i HOME="$tmp_home" PATH=/usr/bin:/bin \
    AUTOPHAGY_DEMO_SECRET=DUMMY-skill-review bash scripts/scenario.sh
)
```

이 절차는 `automation/skill_review.py`가 peer 검토에서 만드는 조건을 재현한다. 임의로
`AUTOPHAGY_REPO_ROOT`나 `PYTHONPATH`를 추가하면 격리 검사가 아니므로 결과를 배포 판정에 쓰지 않는다.

## 2. 배포 파이프라인

```bash
automation/deploy-skill.sh <skill-name>            # 전체 파이프라인
automation/deploy-skill.sh <skill-name> --sandbox-only   # ① 샌드박스만
automation/deploy-skill.sh <skill-name> --request-only [--fresh]  # ①+② 요청 게시까지
automation/deploy-skill.sh <skill-name> --remove   # agent+peer에서 제거
```

- 기본은 로컬(오케스트레이터 머신)에서 실행하며 `DEPLOY_SSH_HOST`
  (`<primary-node>`)로 SSH + `sudo -n -u agent|peer` 한다. 노드 위에서 직접 실행하면
  SSH 없이 동작한다.
- **① 샌드박스(peer)**: 런타임 parse(peer의 hermes CPython = py3.11, cron 인터프리터) →
  lint → hermes 디스커버리 → DUMMY 시크릿 시나리오 → 격리 프로브. 실패 = exit 2, 승인 단계 미진입.
  런타임 parse는 3.12 전용 문법(PEP701 f-string·PEP695 `type` 별칭)이 dev/CI(py3.12)를 통과하고도
  prod(py3.11)에서 SyntaxError로 워처를 죽이는 것을 배포 전에 차단한다(사고 t_90a2e810: triage_gate.py가
  mail 승인 워처를 멈춤). dev 쌍둥이 검사: `tests/unit/test_py311_syntax_guard.py`.
- **② 승인(개인 서버의 #approvals, 소유자 전용)**: agent 봇이 승인 요청을 게시한다.
  **cha 본인 계정의 ✅ 리액션만** 승인으로 인정된다(봇·타인 리액션 거부).
  아직 아무도 답하지 않았으면 **exit 1**, cha가 **⛔로 취소**했으면 **exit 8**이며 어느 쪽도 마운트되지 않는다.
  둘을 나누는 이유는 exit 1이 peer 증명 refresh 재시도를 유발하기 때문이다 — 취소된 배포를 다시 증명하는 것은
  왕복 낭비이고, 로그가 "소유자가 멈춘 뒤에도 파이프라인이 계속 밀어붙이는" 것처럼 읽힌다.
  ⛔는 ✅보다 **우선**한다(둘 다 눌렸으면 취소). **스킬 하나에 살아 있는 승인 요청은 항상 1건**이다 —
  같은 내용(hash)으로 재실행하면 기존 요청 메시지를 그대로 재사용하고(nonce도 유지),
  내용이 바뀌면 옛 메시지를 **먼저 지운 뒤** 새로 올린다(고아 메시지 없음).
  `--fresh`도 같은 규칙을 따른다 — 우회가 아니라 교체(supersede)다.
  기존 요청을 건드릴 수 없는 상황(cha가 이미 ✅/⛔를 눌렀거나, 본문 바인딩 불일치,
  pending 레코드 손상, Discord 조회 실패)에서는 **exit 6**으로 거부하고
  stderr에 `reason=<토큰>`을 남긴다 — 기존 승인 메시지는 그대로 살아 있다.
  승인 성공은 `/srv/autophagy-agents/logs/approvals.jsonl`에 기록된다.
  **소유자의 ✅ 결정은 경과 시간만으로 만료되지 않는다.** peer 증명만 자기 게시 시각부터
  30분(`peer_attestation.PEER_ATTESTATION_TTL`) 유효하며, 배포 시 증명만 만료됐으면 같은
  content hash·nonce·action·destination으로 peer 검증을 다시 수행하고 owner 요청은 재게시하지 않는다.
  본문/바인딩 변경, ✅ 철회, ⛔ 취소, supersede, nonce 재사용은 refresh 전에 fail-closed 차단한다.
  요청 뒤 `skills/<name>/**`를 바꾸면 digest가 달라져 기존 승인을 쓸 수 없으므로 코드를 굳힌 뒤 요청한다.
- **③ 마운트(agent)**: 복사 → 디스커버리 확인 → invoke 스모크 → peer 샌드박스
  복사본 정리.

### ✅ 한 번이면 마운트까지 간다 — 스킬을 새로 만들어도 자동으로 포함된다

위 ②에서 요청만 올려두면(`--request-only`) **소유자가 `#approvals`에서 ✅ 한 번**만 눌러도 마운트까지
끝난다. 세션이 다시 개입하지 않는다 — `autophagy-supply-chain-watch.timer`(2분 주기, 시스템 유닛)가
대기 레코드를 열거해 소유자 결정만 읽고, 승인된 것만 **③을 재개**한다. 상세: [소개](../기능소개/승인-한번-자동배포.md).

**새로 만든 스킬도 등록 없이 자동 포함된다.** 워처의 대상 판정은 스킬 이름이 아니라 승인 종류다 —
`supply_chain_plan.SUPPORTED_KINDS = {"skill-deploy"}`. `deploy-skill.sh`가 올리는 모든 스킬 배포
요청은 이 종류이므로, 스킬 목록이나 화이트리스트를 손볼 필요가 없다.

제외되는 것은 **재개에 필요한 인자가 레코드에 없는 종류**뿐이다 — `managed-activate`(격리 디렉터리
경로가 레코드에 없음) · `skill-publish`(다른 프로그램과 `--managed-repo` 필요). 이들은 추측 실행이
공급망 위험이므로 의도적으로 `retain (unsupported-kind)`로 남겨 사람이 끝낸다.

**재개가 실패하면 유예된다 — 그러나 되돌아온다.** 재개가 실패하면(`failed (resume-exit:N)`) 워처는
같은 실패를 매 tick 반복하지 않으려고 그 요청을 유예한다. 유예는 영구가 아니다 — 실패 지문이
`릴리스 sha:사유`이므로, **원인을 고쳐 랜딩해 노드 릴리스가 바뀌면 다음 tick에 자동으로 재시도된다**
(사람이 다시 부를 필요 없음). 같은 릴리스에서 기다리는 동안에도 **매 tick 한 줄이 남는다** —
`[supply-chain-watch] skill-deploy:<skill> backoff (attempt N, retry in Ns)`. 전에는 이 줄이 없어
유예된 요청이 삭제된 것처럼 보였다(2026-08-04, 8 tick 연속 3건이 로그에서 통째로 누락).

그래도 **급하면 기다리지 않아도 된다** — 같은 릴리스에서 대기 중이거나 수렴을 기다릴 여유가 없으면
아래로 상태를 확인하고 `automation/deploy-skill.sh <skill>`을 직접 한 번 돌린다(승인은 이미 있으므로
③만 수행된다).

```bash
# 무엇이 아직 대기 중인가
ssh <primary-node> 'sudo -n -u agent bash -c "ls ~/.hermes/skill-gate/pending/"'
# 워처가 그 요청을 어떻게 판정했나 (done / retain / failed)
ssh <primary-node> 'journalctl -u autophagy-supply-chain-watch.service -n 30 --no-pager | grep supply-chain-watch'
```

### 무인 회귀 (E2E)

```bash
E2E_TEST_MODE=1 automation/deploy-skill.sh <skill-name>
```

W1-6 injection adapter의 HMAC 서명 승인 레코드를 게이트가 검증한다
(서명 + owner id + 채널/텍스트 일치). **프로덕션 agent gateway에는
E2E_TEST_MODE를 절대 설정하지 말 것** — unit의 production guard가 부팅을
거부한다. 회귀 실행별 시크릿은 agent 홈에서 생성 후 즉시 삭제된다.

### 자동 생성 제안 상한 (크로스커팅 제약 4)

자동 생성 스킬 제안은 `SKILL_PROPOSAL_SOURCE=auto`로 요청해야 하며, 게이트가
ISO 주 기준 **주 3회**를 초과하면 exit 3으로 거부한다(수동 배포는 무제한,
기록은 동일하게 남음).
exit 3은 오직 이 상한에만 쓰인다 — 승인 생명주기 거부는 exit 6이다.

## 4. 관리형 스킬 발행

관리자(cha)가 발행하는 관리형 스킬은 별도의 `managed-skills` 저장소를 통해 배포됩니다.

### 작성 규칙
*   **이름**: 소스 디렉터리명, `SKILL.md`의 `name`, 매니페스트의 `skill` 필드, 그리고 최종 라이브 심링크 이름이 모두 일치해야 하며, 반드시 `managed-` 접두사를 포함해야 합니다.
*   **제약**: 전체 이름은 `^managed-[a-z0-9][a-z0-9-]*$` 패턴을 따라야 하며 최대 41자입니다.

### 발행 파이프라인 순서
1.  **배포 승인 증거 확보**: `deploy-skill.sh <skill> --approve-only`를 실행하여 샌드박스 및 리뷰를 통과하고 소유자 승인을 받은 증거(message_id:nonce)를 얻습니다. 승인 뒤에는 스킬 파일을 수정하지 않습니다. peer 증명만 만료되면 다음 실행이 같은 바인딩으로 자동 재검증합니다.
2.  **발행 요청**: `publish_cli.py`를 사용하여 매니페스트를 생성하고 발행 승인을 요청합니다.
3.  **소유자 승인**: `#approvals` 채널에서 발행 요청에 ✅ 리액션합니다.
4.  **태그 및 푸시**: 승인 확인 후 `publish_cli.py`가 자동으로 SSH 서명된 태그를 생성하고 저장소에 푸시합니다.
