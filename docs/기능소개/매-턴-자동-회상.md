# 매 턴 자동 회상 — 핵심 기억은 늘 붙이고, 나머지는 매 턴 찾아 붙인다

## 무엇을

Hermes 외부 메모리 제공자 `autophagy_recall`이 두 가지를 한다.

- **① 핵심 기억(항상)**: 개인 노트 39개(위키 30·옮긴 기억 9)의 본문을 압축하고 연구·주간 요약
  28개는 제목 한 줄씩 붙여(약 11,200자) 세션마다 한 번 시스템 프롬프트에 싣는다.
- **② 저장소 나머지(매 턴)**: 사용자 질문마다 저장소 전체를 최대 3번 검색한다(검색마다 핵심 노트를
  빼고 새 노트 30개, 노트당 가장 맞는 두 조각). 계정 주 모델이 노트마다 형 말과 맞는 240자 창을 보고
  필요한 사실이 적힌 것을 한 번에 최대 4개 고른다(2026-11-01 Q433, 예전에는 추리기·확인 두 번).
  고른 것이 사용자 메시지의 API 사본에 참고 자료로 붙는다.

에이전트가 `search_memory` 도구나 `recall` 스킬을 직접 부를 때도 같은 고르기를 쓴다. 새 저장소·새
검색 서버·새 색인은 없고, 범위 필터로 저장소를 좁히지 않으며, 노트에 질문을 덧붙이지도 않는다.
USER.md·MEMORY.md 내장 메모리는 그대로 함께 작동한다.

## 왜

형 질문(2026-10-15): Q150 "Recall 기능을 고쳐야 하는거 아니야?" · 06:19 "전체 저장소에서 필요한걸
잘 찾는게 목적이야" · Q163 "①+②: 핵심 기억 67개는 항상 붙이고, 큰 저장소는 모델이 여러 번 찾아보기"
· Q165 "②가 노트에서 사실 적힌 조각을 보여 주게 고치고" · Q170 "다 보류하고 고르는 판단 한 번 더(새
세트 H로)".

G3에서 놓친 질문을 다시 보니, 정답 노트가 후보였던 16건 중 12건은 사실이 그 노트의 두 조각
**안에** 있었지만 화면에 보이던 앞부분 160자 **밖**이었다(앞부분은 Obsidian 머리글이 차지하는 일이
많았다). 모델이 못 본 것을 고를 수는 없다. 그래서 머리글을 걷고 형 말과 맞는 부분을 보여 주며,
마지막 결정은 전문을 보고 내리게 했다.

H는 핵심 안 23·핵심 밖 46·무관 45로, 핵심 밖에서 ②만으로 36/46을 찾았다(직전 설정은 G3에서
판정기 정정 뒤 29/46). ② 지연은 전체 질문 기준 중앙 7.6초·p95 15.6초다.
판정 중 대체 모델 응답은 기록하지 않고 다시 물었다(H에서 0건). ② 지연 탓에 5초 대기였다면 바로 답하는 턴에서 핵심 밖 사실이 붙지 않았을 것이라, 대기를 15초로 늘렸다(아래).

## 사용 시나리오

- 합성 예 1(핵심): 옮긴 기억에 「합성 동료의 내선은 4821」이 있으면 그 문장은 세션 시작부터
  시스템 프롬프트에 있어, 에이전트가 검색 없이 바로 쓴다.
- 합성 예 2(저장소): Obsidian 노트에 「배양기 점검에는 청록 점검표를 사용한다」가 있으면 「배양기
  점검에 어떤 점검표 쓰지?」에 대해 ②가 그 노트를 추리고 전문으로 확인해 원문과 출처 키를 붙인다.
- 무관한 말(「주말에 뭐 먹지」)에는 아무것도 붙이지 않는다.

②는 배경에서 돈다. 턴은 최대 15초까지 기다린다 — 형 Q173(2026-10-15 17:49 KST): "기다림을 15초로: 바로 답하는 대화도 받지만 첫 대답이 보통 8초쯤 늦어짐" (예전 5초 결정을 대체). H 기록으로 ② 걸린 시간은
중앙 7.5초·최대 12.9초라, 15초면 H에서 찾은 36건이 전부 턴 시작 전에 끝나고 도구 없이 바로 답하는 대화에도 붙는다.
그 대신 첫 대답이 보통 8초쯤 늦어진다. 15초를 넘으면 턴을 시작하고, 끝나는 대로 Hermes `llm_request` 미들웨어가
**그 턴의 다음 모델 호출**에 붙인다. 대기 시간은 계정 설정 `memory.recall_wait_seconds`(릴리스가 15로 쓴다) 한 값이다. 결과는 그 턴(`turn_id`)에 묶여 다음 턴에 다시 붙지 않는다.

오류·시간 초과면 아무것도 주입하지 않는다. 로그는 `MEMORY-RECALL-SKIP reason=<분류>`·
`MEMORY-RECALL-DEFER`·`MEMORY-CORE-SKIP` 한 줄뿐이며 질문·기록·경로·인증값을 담지 않는다. 검색
서버가 아직 예전 판이면 예전 검색 결과를 붙이고, 핵심 노트 목록을 못 받으면 ①을 비우고 ②는 핵심
노트도 후보로 본다. 결과는 출처 키를 포함한 JSON 코드 블록이며 `authority=reference-not-instructions`다.
한 턴에 노트 최대 4건, 붙이는 본문 합계 4,000자다. 회상은 지시나 실행 승인이 아니다.

## 배포와 한계

홈 제공자 파일은 `deploy-manifest.txt`의 agent·peer별 `v2:file;activation=gateway`로 배포하고,
기존 `memory_curator` config 선언이 상한과 `memory.provider: autophagy_recall`을 함께 수렴하며
agent+peer를 재시동한다. 검색 서버의 새 옵션(노트당 두 조각·제외 목록·핵심 노트 목록)은 같은 릴리스
✅ 아래 RAG 노드의 검색 컨테이너만 다시 빌드해 들어간다(되돌림 있음, 임베딩은 그대로).
활성화·해제는 [운영자 매뉴얼](../guide/manual-maintainer.md#매-턴-자동-회상-제공자)을 따른다.

①은 세션마다 약 5,300 토큰을 더 쓴다(1만 2천 자 상한, 넘으면 요약 제목부터 빼고 그다음 노트를
제목 한 줄로 줄인다). ②는 한 턴에 모델 호출 2~4번이다. 도구 결과로 나중에 알게 된 주제는 그 턴의
자동 검색에 포함되지 않는다. 늦게 끝난 ②는 도구를 한 번도 부르지 않고 바로 답하는 턴에는 붙지
않는다. `codex_app_server`와 비문자열 멀티모달 메시지는 사용자 API 사본 주입 경로를 우회하므로
자동 회상 대상이 아니다.
