# 에이전트 자가 스킬 (SS-1)

## 무엇을

에이전트가 반복되는 일을 **스스로 스킬로 만들어** 다음부터 그것을 쓴다. 그 스킬은 계정
자기 소유의 쓰기 가능한 Hermes 루트에만 살고, 관리자(cha)가 배포하는 스킬은 read-only
live 스토어에 그대로 남아 함께 발견된다. 통제는 승인 게이트가 아니라 격리 + 이름 충돌
차단 + 감사 원장이다.

## 왜

Hermes v0.18.2에는 자가 저작 기능이 이미 있었지만(에이전트 툴 `skill_manage`, 정리 유도,
7일 주기 curator) 두 계정의 상태가 갈려 있었다.

- `agent`는 **구조적으로 불가능**했다. 스킬 루트가 live 스토어의 read-only bind mount여서
  `skill_manage`가 EROFS로 실패했고, 부작용으로 Hermes 자기 상태 파일(`.usage.json`·
  `.curator_state`·`.archive`)도 쓸 수 없었다 — `hermes curator usage`가 "no skills found"였다.
- `peer`는 **이미 저작하고 있었다**. 현역 자가 스킬 2개가 수백 번 호출되고 있었는데, 어느
  게이트도 거치지 않았고 우리 우회 감사에도 잡히지 않았다.

즉 한쪽은 자기 개선이 막혀 있었고 다른 쪽은 아무도 보지 않는 곳에서 일어나고 있었다.
소유자는 둘 다 고치기로 했다 — **자유롭게 저작하되, 무엇을 만들었는지 보이게 한다.**

## 어떻게 나뉘나

| 루트 | 소유·권한 | 내용 | 역할 |
|------|-----------|------|------|
| `<계정 홈>/.hermes/skills` | 계정 소유 0700 | 자가 스킬 + Hermes 자기 상태 | **1차 루트**(쓰기) |
| `<skill_store>/live` | root 소유 read-only | 관리자 배포 스킬 | `skills.external_dirs`(읽기) |

반전이 필요했던 이유는 하나다: `skill_manage(create)`는 **1차 루트에만** 쓴다. writable한
루트를 골라주지도, external로 폴백하지도 않는다.

## 사용 시나리오

### 정상 — 반복 작업이 스킬이 된다

1. cha가 같은 모양의 요청을 며칠에 걸쳐 반복한다(예: 특정 형식의 주간 정리).
2. 에이전트가 그것을 자기 스킬로 만든다. 승인 요청은 오지 않는다 — 자기 루트 안이고
   외부효과가 아니다.
3. 다음 요청부터 그 스킬이 쓰인다. 관리자 배포 스킬은 그대로 다 보인다(같은
   `hermes skills list`에 external로 함께 열거).
4. 다음 09:00 감사 틱에서 소유자 DM 한 통이 온다:
   `[자체 스킬 감사] 계정=agent / 변경=1 생성=1` + `- 생성 <이름> sha256=<앞 12자> 출처=agent`.
   **이름·해시·출처만** 실린다(본문 비노출). 마음에 안 들면 `hermes curator archive <이름>`,
   죽지 않아야 하면 `hermes curator pin <이름>`.

### 거부 1 — 배포가 자가 저작물을 덮어쓰려 할 때

관리자 배포 스킬 이름이 계정의 자가 스킬과 겹치면 `deploy-skill.sh`가 **아무것도 스테이징
하기 전에** 멈춘다.

```
SELF-SKILL-COLLISION-BLOCK: <skill> already exists as a self-authored skill on <account> (...)
```

exit 4이고 peer staging도 일어나지 않는다. 우선순위는 없다 — 소유자가 자가 저작물을
archive하거나 배포 쪽 이름을 바꿔야 배포가 재개된다. 루트를 읽지 못하거나 분류가 모호할
때도 같은 코드로 멈춘다(fail-closed).

### 거부 2 — 이미 있는 이름으로 만들려 할 때

cha가 "`recall`이라는 이름으로 스킬 만들어"라고 지시하면 에이전트가 만들지 못한다.
Hermes의 `skill_manage(create)`가 **어느 루트에든** 같은 이름이 있으면 거부하기 때문이다
(관리자 배포본이 external 루트에 있어도 마찬가지). 디렉터리는 생기지 않는다.

## 알아둘 것

- **원장은 승인 게이트가 아니다.** 이미 일어난 일을 보이게 만드는 장치다. `write_approval`은
  꺼진 채로 두고 `guard_agent_created`만 켜서 위험 패턴 스캔을 받는다.
- **provenance는 파일 소유권이 아니다.** Hermes `.usage.json`의 `created_by=agent` /
  `agent_created=true`로 판정하며, 확인할 수 없으면 `unverified`로 남긴다 — 추측하지 않는다.
- **보고는 at-least-once다.** DM 전송이 실패하면 watermark를 전진시키지 않아 다음 틱이 같은
  델타를 다시 보고한다. 조용히 빠지는 것보다 중복이 낫다.
- **노드 반전은 아직 실행되지 않았다.** 코드와 가드는 두 토폴로지에서 모두 안전하게 동작하며,
  마이그레이션 창은 소유자가 실행한다(아래 patch 문서).
