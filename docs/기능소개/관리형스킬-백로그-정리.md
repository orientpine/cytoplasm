# 관리형 스킬 백로그 정리

## 무엇을

관리형 스킬의 실제 마운트 상태와 구독 장부를 다시 맞추는 보조 명령을 추가하고, 자기 digest 회수 실수를 발행 시점에 명확히 차단했습니다. 발행·배포 승인 로그의 물리 위치는 계정 경계를 보존하기 위해 분리 유지하는 것으로 결정했습니다.

## 왜

기존 `state.json`의 `activated_digest`는 마운트나 제거 성공 뒤 자동으로 갱신되지 않아 `status`가 낡을 수 있었습니다. 실제 동작과 회수 판정은 항상 라이브 심링크를 읽어 안전했지만 운영자가 보는 장부가 부정확했습니다. 또한 새 매니페스트가 자기 소스 digest를 회수하면 구독 검증에서 일반 거부로 끝나 발행자가 실수의 원인을 알기 어려웠습니다.

## 사용 시나리오

### 정상 경로

1. 소유자가 격리된 `managed-example`을 기존 승인 게이트로 활성화합니다.
2. `readlink /srv/autophagy-skills/live/managed-example`로 성공을 확인합니다.
3. `python3 -m automation.managed_sync mark-activated managed-example`을 실행합니다.
4. 명령이 라이브 링크에서 digest를 직접 읽어 `state.json`을 갱신하고, 이후 `status`가 같은 digest를 표시합니다.

제거가 끝난 뒤 같은 명령을 실행하면 라이브 항목의 확인된 부재를 바탕으로 `activated_digest`를 비웁니다. digest를 인자로 받지 않으므로 저장 상태가 새로운 권위 소스가 되지 않습니다.

### 실패·거부 경로

- 라이브 항목이 dangling 심링크, 비심링크, 해석 불가능한 digest이면 장부를 바꾸지 않고 `ACTIVATION-MARK-ERROR`로 실패합니다.
- 발행할 소스 digest가 `revoked_digests`에도 들어 있으면 승인 요청 전에 `SELF-DIGEST-RECLAIM`으로 거부합니다. 발행자는 회수 대상 digest를 수정해 다시 시도합니다.

## 승인 로그 설계 결정

발행은 cha의 워크스테이션에서, 배포·활성화는 agent 계정에서 수행됩니다. 두 환경은 공유 파일시스템이 없고 워크스테이션에는 agent 정본 로그 쓰기 권한이 없습니다. 이 권한을 단순히 열면 배포 인가에 쓰이는 원장에 임의 레코드를 추가할 수 있으므로 물리 통합을 강제하지 않습니다. 두 로그는 같은 스키마와 게이트 검증을 유지하며, 향후 인증된 원격 재검증과 단일 writer가 설계될 때만 통합을 재검토합니다.

## 관련

- 발행 검증: `automation/managed_skills/publish_cli.py`
- 운영 가이드: `docs/guide/managed-skill-channel.md`
- 발견 증적: `docs/qa/MS-F/ms-f2-final-verification.txt §⑥`
