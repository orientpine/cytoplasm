# 멱등 단일 노드 설치기 (W-F1-B)

## 무엇을

`python3 -m automation.install`은 제3자 Linux 노드 한 대를 같은 원하는 상태로 수렴시킨다.
계정·공유 그룹·`/srv` 레이아웃·privileged helper·sudoers·systemd timer·Git hook·설치별
read-only deploy key·peer attestation 서명키·계정별 `~/.hermes/node.toml`을 설치하고, 마지막에 기존
`automation/healthcheck.sh`를 통과해야 성공한다.

## 왜

기존 provision 스크립트는 운영 시기별로 나뉘어 있어 새 설치자가 순서와 누락 여부를 직접
판단해야 했다. 새 설치기는 현재 상태를 읽고 필요한 작업만 만드는 순수 계획 계층을 두어,
중간 실패 뒤 재실행하거나 이미 설치된 노드에 다시 실행해도 계정·키·timer를 중복 생성하지
않는다. deploy checkout에는 커밋 거부 hook, 실제 커밋이 가능한 repair 작업 clone에는 기존
gitleaks fail-closed hook을 설치한다.

## 사용 시나리오

### 정상 흐름

1. 공개 릴리스 번들의 업데이트 신뢰 공개키와 설치별 `node.toml` 값을 준비한다.
2. `python3 -m automation.install --update-trust-key <공개키> --dry-run`으로 전체 작업 목록을
   확인한다. dry-run은 쓰기 없이 rc 0으로 끝난다.
3. Hermes agent·peer gateway와 Discord 설정을 외부 선행조건으로 준비한 뒤 같은 명령에
   `sudo`를 붙여 실행한다.
4. 설치기가 출력한 **공개** deploy key만 upstream 관리자에게 전달해 read-only로 등록한다.
   private key는 로컬 `ops` 홈 밖으로 나가지 않고 출력되지 않는다.
5. peer attestation private key는 peer 홈에 0600으로 남고, 공개키만 root-owned 0644로
   `/etc/autophagy/`에 게시된다. 신규 런타임 config는 `peer_attest_mode = "signed"`를 기록한다.
6. 등록 전 clone이 거부됐다면 같은 명령을 재실행한다. 이미 끝난 단계는 건너뛰고 clone,
   timer 활성화, `healthcheck.sh`로 이어진다.

### 실패·거부 흐름

Hermes가 없거나 gateway unit이 비활성이면 설치기는 Hermes를 대신 설치하지 않고
`hermes-gateway`를 FAIL로 보고한다. Discord 점검 실패, 업데이트 신뢰키 지문 불일치,
deploy key 미등록에 따른 clone 실패, 최종 healthcheck 실패도 모두 non-zero로 종료한다.
실패 전 완료된 단계는 그대로 두며 다음 실행이 남은 단계만 다시 계획한다.
