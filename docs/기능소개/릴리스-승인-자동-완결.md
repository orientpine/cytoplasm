# 릴리스 승인 자동 완결 — ✅ 한 번이면 태그·수렴·마운트까지

## 무엇을

소유자가 릴리스 요청에 ✅를 누르면, 사람이 아무 명령도 더 돌리지 않아도 **서명 태그 컷 → 노드 릴리스 트리 수렴 → 전량 반영(`deploy_all.sh --apply`) → 영수증**까지 이어진다. 두 조각으로 되어 있다.

- `automation/release.sh`가 태그를 자른 뒤 **스스로** 노드 수렴을 기다려(`deploy_all.sh --apply --wait-converge`, 기본 600초) 전량 반영까지 끝낸다. `--no-deploy`를 주면 옛 동작(태그만)이다.
- `automation/release_complete.sh`를 워크스테이션 `systemd --user` 타이머가 **2분마다** 돌린다. 이미 ✅된 요청이 살아 있으면 `release.sh`를 재개해 위 과정을 잇고, 아니면 조용히 다음 틱으로 넘어간다. 설치는 `automation/release_complete_install.sh` 한 번.

## 왜

- 릴리스 승인(VA-1)이 스킬별 ✅를 대체했지만(VA-2 `--release-approval`), 실행은 자동이 아니었다. `release.sh`의 ✅ 폴링은 **세션과 함께 죽고**, 태그 뒤 마운트는 `deploy_all.sh --apply`를 누군가 따로 돌려야 했다. 2026-08-31 실측: 대기 프로세스가 30분 타임아웃으로 두 번 죽었고, v1.0.140 태그가 잘린 뒤에도 스킬 6개가 stale로 남아 있었다 — 소유자는 "승인하면 마운트까지 자동 아니냐"고 물었고, 답은 "절반만"이었다.
- 서명키는 워크스테이션에만 있어야 한다(「릴리스 태그 규칙」, MD-1). 그래서 완결 주체를 노드나 CI로 옮기지 않고 **워크스테이션의 타이머**로 둔다 — 자동화하는 것은 서명 주체가 아니라 실행 시점이다.

## 사용 시나리오

1. **평소** — 세션이 `automation/release.sh`를 돌려 요청을 올린다(이 부분은 그대로). 소유자는 `#approvals`에서 ✅만 누른다. 세션이 아직 살아 있으면 그 프로세스가, 죽어 있으면 늦어도 2분 안에 타이머가 태그를 자르고 노드 수렴을 기다려 스킬을 전부 마운트한다. 끝나면 `~/.hermes/release-completer/completed/<sha>` 마커가 남고, 그 sha는 다시 건드리지 않는다.
2. **⛔·무응답** — completer는 아무것도 하지 않는다. 요청을 새로 올리거나 되살리지 않는다(`request`/`retire`/`plan`을 부르지 않는 것을 회귀 테스트가 subcommand 대조로 고정한다).
3. **실패** — 태그는 잘렸는데 전량 반영이 막히면(예: 샌드박스 블록) `release.sh`는 exit 10, completer는 다음 틱에 다시 시도한다 — 재시도는 HEAD의 기존 태그를 재사용한다(`release_version_for`; 다음 버전을 계산하면 이름 불일치 검사가 자기 태그를 거부해 2026-09-03 v1.1.1 attempt 2가 그렇게 죽었다). 세션의 `release.sh`가 아직 살아 있으면 두 실행이 `deploy_all`을 겹쳐 돌려 스킬별 `EXECUTION-LOCK-BLOCK`이 난다 — 손상은 없고 마운트는 합집합으로 완료되지만 각자는 `incomplete`로 끝난다(`docs/follow-ups.md`). sha별 **3회**(`RELEASE_COMPLETE_MAX_ATTEMPTS`)까지만이다 — 지속 결함을 매 틱 전량 재배포로 되풀이하지 않고 `COMPLETE-GIVEUP`을 남긴다. 원인을 고쳐 랜딩하면 새 sha가 새 릴리스가 되어 처음부터 다시 센다. 손으로 재개하려면 `automation/release.sh`(이 상한을 모른다) 또는 `automation/deploy_all.sh --apply`를 돌린다. 미완은 그동안에도 헬스체크의 `RECEIPT-STALE` 프로브가 계속 표시한다.
4. **설치·점검** — 워크스테이션의 **메인 체크아웃**에서 `automation/release_complete_install.sh`(유닛 렌더 → `daemon-reload` → `enable --now`). `--status`로 타이머·마지막 실행을 보고, `--uninstall`로 걷는다. 세션 워크트리에서 설치하면 `ExecStart`가 그 워크트리를 가리켜 `worktree.sh finish` 때 끊어진다.

## 알아둘 것

- completer는 **자기 워크트리**(`~/.hermes/release-completer/worktree`)에서만 일한다 — 매 틱 `origin/main`으로 맞추고, 더러워져 있으면 exit 5로 멈춘다(지우면 다음 틱이 다시 만든다). 겹친 틱은 `flock`으로 무음 종료.
- 유닛의 `ExecStart` 는 메인 체크아웃의 `release_complete.sh` 를 가리키지만, 그 스크립트는 워크트리 동기화 직후 origin/main 의 자기 사본과 다르면 `SELF-UPDATE` 를 남기고 그 사본으로 exec 한다(잠금 fd 상속·`RELEASE_COMPLETE_REEXEC` 재진입 가드, 2026-09-06). 완결기 코드 변경은 다음 틱부터 반영되고, 메인 체크아웃을 손으로 ff-pull 하는 것은 설치(`release_complete_install.sh`) 때만 필요하다. 파이썬 단계도 같은 세대를 써야 하므로 `REPO_ROOT` 로 **cd 한 뒤** `python3 -m` 을 부른다 — `-m` 은 `sys.path[0]` 에 cwd 를 넣어서, 유닛의 `WorkingDirectory`(메인 체크아웃)에 있는 낡은 `automation` 패키지가 워크트리 세대의 모듈을 가린다(2026-09-09 실측: 완결 리컨실이 매 틱 `No module named automation.release_completion_target` 만 남기고 조용히 죽었다).
- `release.sh`의 전제(clean tree · HEAD == origin/main · 로컬 CI 영수증)는 그대로다. 승인 요청을 올린 sha에 대해 이미 성립한 것들이라 completer가 새로 만들 것은 없다.
- 실행 로그는 `journalctl --user -u autophagy-release-complete.service`.
- `deploy_all.sh --apply`는 워크스테이션 로컬의 `${DEPLOY_ALL_LOCK_DIR:-$HOME/.hermes/deploy-all}/apply.lock`을 잡아 세션과 완결 타이머가 같은 ✅를 동시에 소비해도 한 실행만 배포한다. 뒤따른 실행은 `APPLY-LOCK-WAIT`을 남기고 기본 1,800초(`DEPLOY_ALL_LOCK_WAIT_SECONDS`)까지 기다린 뒤 다시 판정한다. 앞선 실행이 전량 반영을 끝냈으면 `APPLY-LOCK-RECHECK`과 영수증만 남기고 deployer 없이 exit 0이며, `--plan`·`--verify`는 읽기 전용이라 이 lock을 잡지 않는다.

## 낡은 pending 요청의 자가 회복

`binding-mismatch`로 거부된 요청 중 저장 probe가 `bound_pending`이고 head가 origin/main tip에서 밀려난 경우만 `release.sh`가 감사형 abandon 뒤 정확히 1회 재요청한다.
결정된(✅/⛔) 레코드는 L3 불변이며, abandon 실패 또는 재요청 거부는 오늘과 같이 거부로 끝난다.

## 적용 완료 DM 통지 (2026-09-05)

**릴리스가 실제 운영환경에 적용되면 소유자 Discord DM 으로 「릴리스 v1.2.4 가 적용되었습니다.」가 릴리스당 정확히 한 번 나간다.** 승인 요청 채널의 ✅ 는 "잘라도 좋다"는 허락이지 적용이 아니다 — 태그가 잘린 뒤에도 전량 반영은 막힐 수 있어서(샌드박스 블록·수렴 실패) 승인 반응만으로 완료를 말하면 거짓말이 된다.

- **완료 판정의 근거는 셋이고, 셋이 모두 같은 sha 를 가리켜야 한다** — ① 완결기의 성공 마커 `~/.hermes/release-completer/completed/<sha>`(`release.sh` + `deploy_all --apply` 가 끝난 뒤에만 쓰인다) ② 노드의 활성 릴리스 포인터 `readlink /srv/autophagy-agent-current` ③ 전량 재판정 영수증 `deploy-all/receipt.json` 의 `release_sha`(RC-4). 포인터·영수증은 완결 타이머가 매 틱 노드를 **읽기 전용**으로 한 번 조회해서 얻는다.
- **번호는 추정하지 않는다.** 그 sha 를 가리키는 릴리스 태그(`v<major>.<minor>.<patch>`, prerelease 접미사는 제외)가 유일한 출처다. 태그가 없으면 `NO-TAG` 로 보류하고 다음 틱에 다시 보며, 한 커밋에 릴리스 태그가 둘이면(실측: `f00f334ca` 의 v1.1.5+v1.2.0) `VERSION-AMBIGUOUS` 로 **영구 보류**한다 — 사람이 정리할 일이지 기계가 고를 일이 아니다.
- **지나간 릴리스는 알리지 않는다(SUPERSEDED).** 완결 마커는 옛 sha 에도 남아 있다. 활성 포인터의 조상인 sha 는 지금 돌고 있지 않으므로 `notify-skipped/<sha>` 에 사유만 남기고 보내지 않는다. 2026-09-05 도입 시점의 실제 상태가 그 예다 — 활성 릴리스 **v1.2.4**(`29a0a59087ca`) 한 건만 DM 을 받고, 승인은 됐지만 이미 밀려난 **v1.2.3**(`a17b051f49dd`)과 그 앞 15건은 전부 `SUPERSEDED` 로 기록만 된다.
- **멱등과 재시도.** 보낸 릴리스는 `notified/<sha>`(`<버전> <UTC 시각>`, 0600), 영구 보류는 `notify-skipped/<sha>` 로 남고 다음 틱은 그 sha 를 아예 건너뛴다. 전송이 실패하면 **마커를 남기지 않아** 다음 틱(2분)이 다시 시도한다 — 횟수 상한은 두지 않는다(지시: "실패 시 재시도"). 노드에서도 발신 직전에 포인터를 한 번 더 확인해, 판정과 발신 사이에 릴리스가 바뀌었으면 `APPLIED-POINTER-MISMATCH` 로 거부한다.
- **통지는 완결을 막지 않는다.** 스윕은 완결 단축회로 **앞**에서 돌지만(대상이 바로 그 완결된 sha 다) best-effort 라 어떤 예외도 `RELEASE-APPLIED-SWEEP-FAIL` 한 줄로 끝나고 완결기의 종료코드·동작은 그대로다. 통지 대상이 하나도 없으면 노드를 찌르지도 않는다.
- **로그 표식**(`journalctl --user -u autophagy-release-complete.service`): `RELEASE-APPLIED-NOTIFIED <버전> <sha12>` · `RELEASE-APPLIED-SKIP <SUPERSEDED|VERSION-AMBIGUOUS> <sha12>` · `RELEASE-APPLIED-RETRY <NO-TAG|POINTER-UNREADABLE|POINTER-BEHIND|RECEIPT-MISSING|RECEIPT-STALE> <sha12>` · `RELEASE-APPLIED-SEND-FAIL rc=<n> <sha12>` · `RELEASE-APPLIED-SWEEP-FAIL <예외종류>`.
- DM 은 `automation/owner_notice.notify_owner_dm` 하나로만 나간다 — 통지 채널(`#notifications`)이 설정된 설치에서도 이 통지는 DM 으로 간다(소유자 지시가 대상 자체다). 발신은 노드의 agent 계정에서 그 계정의 자격증명으로 이뤄지고, 워크스테이션은 토큰을 만지지 않는다.
