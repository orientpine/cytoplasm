# 기능 소개: 메일 본문 보기와 장문 승인 첨부

**PR:** #506(본문 보기), #511(장문 승인 첨부) · **스킬:** `mail` · **티켓:** repair `t_38cd3b3c`, `t_82644d12`

## 무엇을

두 가지가 바뀐다.

1. **본문 보기.** 소유자가 "본문 보여줘"라고 하면 요약 대신 `triage_cli.py get <uid> --body`가 Discord에서 읽기 좋은 청크를 만든다. 제목·보낸 사람·받는 사람·날짜·첨부 건수는 불릿 헤더로, 본문은 빈 줄 하나로 정돈되고 목록·표·링크 Markdown은 유지된다. 인용 원문은 기본적으로 마지막 한 줄로 접히며 `--full`이면 펼치고, `--raw`면 wrapper가 공개한 문자열을 가공 없이 돌려준다. 이 명령은 읽기 전용이다.
2. **장문 승인 카드.** 새 발송 승인 카드가 Discord 2,000자 한도를 넘으면 제목·수신자·draft id·본문 SHA256·승인 해시·✅/⛔ 안내만 담은 요약 카드를 올리고, **같은 메시지**에 본문과 인용 전체를 UTF-8 텍스트 파일 하나로 첨부한다. 긴 메일도 내용을 줄이지 않고 검토할 수 있다.

## 왜

긴 메일은 요약만 보면 판단이 어렵고, 승인 카드는 한도 때문에 본문이 잘려 소유자가 실제로 무엇을 보내는지 확인할 수 없었다. 본문을 줄여 넣는 대신 검증 가능한 첨부로 옮기고, 읽기 경로는 wrapper 계약을 그대로 둔 채 렌더만 더했다.

## 동작 규칙

- 첨부 검증 정보(파일 이름·바이트 수·SHA256)는 기존 승인 해시 **밖**에 저장한다. 짧은 카드와 이미 게시된 카드의 바이트는 바뀌지 않으며, 새 형식은 `approval_format=attachment-v1`로 구분한다.
- 승인 재사용 검사와 ✅ 리액션 처리는 저장된 메타데이터, 메시지의 첨부 선언, 실제로 내려받은 바이트를 모두 대조한다.
- 다운로드는 명시적 봇 User-Agent를 쓰고 인증 헤더는 보내지 않는다. 노드 실측에서 기본 Python 요청은 같은 첨부 URL에 403을 받았지만, 봇 User-Agent 요청은 200과 원본 SHA256을 반환했다. 정상 첨부가 다운로드 단계에서 잘못 거부되는 문제를 고친다.
- 마스킹 표면(`--masked`)에서는 `--raw`·`--full`도 마스킹을 풀지 않고, 본문 대신 기존 해시·바이트 수 JSON이 나온다.

## 사용 시나리오

### 정상 경로

1. 소유자가 특정 메일의 본문을 요청한다. 에이전트는 `get <uid> --body` 출력 청크를 순서대로 그대로 붙여 넣고 다시 요약하지 않는다. 여러 청크면 `(i/n)` 접미까지 한 메시지씩 보낸다.
2. 긴 회신 초안이 승인 대기에 오르면 요약 카드 한 장과 텍스트 첨부 한 개가 같은 메시지로 게시된다. 소유자는 첨부를 열어 본문·인용을 확인한 뒤 카드에 ✅를 남긴다.
3. 워처가 첨부 이름·크기·SHA256과 다운로드한 바이트를 대조한 뒤에만 기존 발송 경로로 넘긴다.

### 실패·거부 경로

- 첨부가 빠졌거나 이름·크기·SHA가 저장값과 다르거나 다운로드가 실패하면 ✅를 실행하지 않고 기존 게이트 거부로 남긴다. 잘못된 첨부 URL이나 업로드 응답 형식 오류도 예외 누출 없이 같은 거부가 된다.
- 제목·수신자만으로 요약 카드마저 한도를 넘으면 승인 스레드 생성과 posting journal 예약 **전에** 거부한다.
- 본문 파일이 없으면 렌더에 그 안내가 표시되고, 조회 실패는 wrapper의 기존 오류·종료코드를 그대로 따른다.

## 승인 경계

읽기 명령은 게이트 대상이 아니다. 발송은 기존 소유자 ✅ 게이트 그대로이며, 첨부 검증은 그 게이트를 더 엄격하게 만들 뿐 우회 경로를 만들지 않는다. 실제 노드의 합성 카드에서 8,151바이트 첨부의 해시를 대조했고 발송은 호출하지 않았다. 수정된 게이트 전체의 라이브 재검증은 후속 배포 뒤에 수행한다.
