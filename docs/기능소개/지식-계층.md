# 지식 계층 — 제안서·보고서·위키·회의·연구동향·메일이 개인 기록을 근거로 쓰는 경로

## 무엇이 달라졌나

`proposal`이 세 개인 지식 계층을 읽는 첫 채택 스킬이 됐다. Obsidian 원천 노트, 소유자가
승인한 wiki 판단, 개인 RAG 검색 결과를 스킬이 따로 뒤지는 대신 읽기 전용
`automation.knowledge` 파사드 한 번으로 EvidencePack을 받는다. 기본 동작은 그대로이며
`draft --brief-file ... --with-evidence`를 명시한 경우에만 조회한다.

팩의 근거만 프롬프트에 들어가고 초안의 팩 밖 인용은 제거된다. 섹션 초안은 파사드가 만든
`### 근거` 각주로 끝나며, `assemble`은 여러 섹션의 같은 근거를 하나로 줄여 문서 말미
`## 근거 목록`을 만든다. 원본 팩은 제안서 워크스페이스의 0600 `*.evidence.json`에 남는다.
JSON 미리보기에는 원문 대신 근거 수와 계층 상태만 나온다.

`report`도 `report --with-evidence`와 `evidence` 미리보기를 채택했다. 기존 `~/notes`
선택은 바꾸지 않고 팩 근거를 추가 재료로 사용하며, 보고서의 기존 `## 근거 노트`
아래에 파사드가 렌더한 `## 근거`를 병기한다. 팩은 같은 이름의 0600
`*.evidence.json`에 남고 근거 본문까지 기존 민감도 라우팅에 포함된다.

`wiki consult`는 과거의 수동 `twin_consult → recall` 순차 호출을
`purpose="judgment"` 파사드 한 번으로 바꿨다. 질의 토큰과 실제 위키 태그 어휘의
교집합만 태그로 사용하고, 팩 메타에 따라 `[위키 규칙]`·`[RAG 선례]`·
`[불확실·충돌]`로 표시한다. `draft --with-evidence`는 파사드 출처를 `## Sources`로
붙이되 기존 초안 → 확인 메시지 → 소유자 ✅ 쓰기 게이트는 바꾸지 않는다.

`meeting ingest --with-evidence`는 제목·참석자·주제에 관련된 선행 회의와 노트를
추출 재료로 쓴다. 팩 밖 인용은 제거하고 출처와 0600 사이드카는 개인 회의 노트에만
남긴다. 근거 본문도 기존 민감도 판정에 합산하므로 센티널·patent-sensitive 근거는
GLM으로 가지 않으며, 민감 회의의 카드·공개 표면 제한은 그대로다.

`topics list --with-evidence`와 주간 `research-trends` 보고서는 등록 주제에 대한
`## 내 관련 노트`를 덧붙인다. 주간 보고서가 다음 tick에 RAG로 다시 들어가더라도
`note:research-trends/` 문서는 어댑터에서 제외해 자기인용 루프를 만들지 않는다.
조회 불가는 보고서 생성을 막지 않고, 기존 주 1회 워터마크와 dry-run 비소진 계약도
바꾸지 않는다.

`mail draft|compose --with-evidence`는 entity preflight가 통과한 뒤에만 상대·주제 관련
근거를 수집한다. 근거는 회신 프롬프트와 소유자 DM 승인 표면·0600 사이드카에만 남고,
수신자에게 갈 초안 본문에서는 팩 인용까지 모두 제거한다. 기존 소유자 ✅ 발송 게이트와
동결 해시 바인딩은 그대로다.

5단계에서 MCP 검색은 호출자가 준 엔터티 앵커의 literal 후보와 기존 dense 후보를
문서 id로 합치고, 엔터티 일치·semantic score·명시 `event_date` 순으로 재정렬한다.
날짜 없는 문서는 제외하지 않고 뒤에 두며 limit 20, score threshold, grounding 비율은
낮추지 않았다. 새 인자 없는 호출은 기존 semantic 검색과 같은 요청·응답 경로를 쓴다.
Obsidian 날짜는 YAML/callout 명시값만 정규화하고 경로 날짜는 근거만 표시한다.
파사드는 구버전 MCP가 새 인자를 거부하면 기존 호출로 강등한다. 운영 MCP 배포 검증 전에는
0단계 `--entity-fallback`을 유지해 양쪽 검색 경로가 모두 없는 창을 만들지 않는다.

## 왜 필요한가

이전 제안서 초안은 사람이 준 brief와 기존 섹션만 보았다. 소유자의 과거 실증 기록이나 승인된
판단이 이미 있어도 근거로 연결되지 않았고, 각 스킬이 검색과 출처 형식을 별도로 만들면 진실
우선순위와 민감도 처리가 갈라질 위험이 있었다. 공통 파사드는 wiki > 날짜가 명시된 Obsidian >
RAG 기타 기록이라는 방향, 단일 출처 형식, 팩 밖 인용 제거를 한 계약으로 유지한다.

근거가 없으면 "근거 없음", 조회 계층이 내려가면 "근거 수집 불가"를 초안 머리에 명시한다.
후자의 경우에도 생성은 계속하지만 재시도, 임계값 하향, 자체 검색은 하지 않는다.
patent-sensitive 근거나 `[[PATENT-SENSITIVE-RECALL]]` 센티널이 있으면 근거 본문까지 민감도
라우팅 입력에 포함되므로 GLM 대신 Codex 전용 경로를 선택한다.

## 사용 시나리오 — 건설 로보틱스 과제

```bash
# 제안서와 섹션을 만든 뒤 brief를 준비한다.
python3 skills/proposal/scripts/proposal_cli.py create \
  --slug construction-robotics --title "건설 로보틱스 과제" \
  --section approach:추진전략

# 원문 없이 팩 규모와 계층 상태를 먼저 확인한다.
python3 skills/proposal/scripts/proposal_cli.py evidence \
  --slug construction-robotics --section approach \
  --brief-file /private/robotics-brief.md --json
# {"evidence_count": 1, "layers": {"rag": "hit", "twin": "none", "wiki": "none"}}

# 같은 질의 계약으로 근거 포함 초안을 만든다.
python3 skills/proposal/scripts/proposal_cli.py draft \
  --slug construction-robotics --section approach \
  --brief-file /private/robotics-brief.md --with-evidence
```

초안 형태는 다음과 같다.

```markdown
현장 실증 결과를 다음 단계의 작업 계획에 반영한다 [E1].

### 근거

[E1] RAG/note: robotics/result.md (2026-08-18, path)
```
