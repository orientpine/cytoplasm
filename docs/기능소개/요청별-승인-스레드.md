# 요청별 승인 스레드 — 승인·리마인더·결과 통지가 한 스레드에서 완결

## 무엇을

소유자 전용 승인(mail·budget·calendar·coordination·todo·wiki·patent-prep·obsidian·repair)은
`#agent-chat` 아래 **요청 하나에 스레드 하나**를 연다. 이름은 `<상태 하나> <종류 아이콘> <제목≤40자>`(아이콘·큰 제목: [스레드 큰 제목](스레드-큰-제목.md))
(예 `🔔 ✉️ 세미나 안내`, `🔔 📋 보고서 초안`)이고, 마스킹 kind(calendar·wiki·
patent-prep·obsidian)는 `🔔 🗓️ draft-42` 처럼 **id만** 싣는다. 승인 카드(✅/⛔)·리마인더·
실행/취소/만료 결과가 전부 그 스레드에 들어가고, 종결되면 이름 앞에 `✅` / `⛔` /
`💤` 를 붙여 아카이브한다.

## 왜

2026-09-01 소유자 지시. 승인은 kind별 고정 스레드(`승인-mail-compose` …)에, 결과는 지시 메시지에
달린 별개 스레드에 갈라져 있어 한 건의 처리 경로를 두 곳에서 따라가야 했다. "일의 처리 경로가
한 번에 관리"되려면 요청 단위로 묶여야 한다. 덤으로 `#agent-chat` 의 **활성 스레드 목록이 곧
진행 중 요청 보드**가 된다 — 종결된 요청은 아카이브되어 목록에서 사라지므로 무엇이 대기 중인지
목록만 봐도 안다.

## 사용 시나리오

1. **happy**: cha 가 `#agent-chat` 에서 "OOO 에게 세미나 안내 메일 보내줘" → 에이전트가
   `compose --origin-channel-id <agent-chat> --origin-message-id <지시 메시지>` → 그 지시 메시지에
   `🔔 ✉️ 세미나 안내` 스레드가 열리고 승인 카드가 게시된다 → cha ✅ → 발송 → 같은 스레드에
   `✉️ 발송 완료: …` → 스레드 이름이 `✅ ✉️ 세미나 안내` 로 바뀌고 아카이브된다.
2. **origin 없음**: 새벽 cron 이 만든 회신 초안, repair 패치 승인은 지시 메시지가 없으므로
   `#agent-chat` 에 `🔔 ↩️ …` / `🔔 🛠️ t_2578c8ed` 스레드를 새로 연다. 나머지는 동일.
3. **거부·만료**: ⛔ → 결과 문구 뒤 `⛔ …` 로 종결. 리마인더 만료 → `💤 …`.
4. **마스킹**: 캘린더 요청은 `🔔 🗓️ <draft id>` — 제목·시간은 스레드 이름에도 결과 문구에도
   없다(승인 카드 안에서만). wiki·patent-prep 은 결과 통지 자체가 없던 규칙 그대로이고 승인 요청만
   요청별 스레드로 옮겨졌다.
5. **실패 경로**: 이름 변경·아카이브가 거부되면(`THREAD-CLOSE-FAIL`) 결과 통지는 이미 도달했고
   실행·영수증·exit code 는 불변 — 스레드가 활성 목록에 남을 뿐이다. `agent_chat_channel_id`
   미설정이면 승인 게시 자체가 fail-closed 다(기존과 동일).

## 관련

- 핵심: `automation/interop/approval_surface.py` `RequestThread`·`KIND_LABELS`·
  `request_thread_name`·`resolve_new_binding(request=)`(S6 — 표면 facts 가 그대로라 **정책 버전
  bump 없음**, 저장된 v7/v8 레코드 해석 불변), `approval_directory.agent_chat_request_thread`
  (지시 메시지가 이 채널 소속이면 앵커, 400=이미 있음 → message id 재사용 — 그 스레드를 한 번 읽어 서버
  좌표를 얻어 `APPROVAL-THREAD` 줄이 실제 링크를 내고, 이름에 종류 아이콘이 없으면 `joined_thread_name`으로
  상태 하나+아이콘을 붙인다(다른 에이전트가 먼저 연 스레드, 2026-11-04; 거둔 카드가 남긴 💤 같은 끝 표시는
  🔔 로 바꾼다), 아니면 채널 스레드 생성 —
  조회 없음, 요청끼리 스레드를 공유하지 않는다), `origin_notice` (`approval_thread_id` 최우선·
  `ThreadOutcome`·`close_thread`·`deliver(outcome=)`).
- 생산자: 각 스킬 `*_binding.py`(mail·budget·calendar·coordination·wiki·patent-prep),
  `todo_approval_runtime.py`, `automation/memory_relocate/effects_live.py`(obsidian),
  `automation/repair/repair_ops_binding.py` 가 `request=` 를 넘기고 레코드에 `approval_thread_id`
  (승인 해시 밖)를 저장한다. 리액션 워처·리마인더·lifecycle probe 는 레코드 `channel_id` 를 읽으므로
  무변경.
- 이름 바꾸기 제한(2026-11-04): Discord 는 스레드 이름을 10분에 두 번까지만 바꾼다. 메일 카드는 게시 직후
  바로 묶이고(`MailApprovalGate._bind`) ✅⛔ 가 먼저 달리며, 🔔 는 429 에 기다리지 않고 한 번만 시도한다
  (`triage_confirm.no_rate_limit_wait`). 못 바꾼 스레드는 `thread-marks/` 에 남아 `watch` tick 이
  카드가 결정 전일 때 다시 붙인다(`retry_thread_marks`).
- 상태 표시의 주인 하나(2026-11-12, 카드 셋·결과 넷이 11분에 몰려 보낸 메일의 스레드가
  🔔 로 남음): 메일 승인 스레드의 🔔·✅·⛔·💤·❗ 는 `triage_approval_gate.mark_thread` 만 붙인다. 결과 통지는 끝 표시를
  거기 넘기고, 같은 스레드에 결정 전 카드가 남아 있으면 🔔 가 이긴다(형이 눌러야 할 게 먼저). 바라는 표시는
  이름을 바꾸기 전에 `thread-marks/<스레드>` 에 마지막 하나만 적고, 이미 그 이름이면 이름을 바꾸지 않으며, 이름
  바꾸기는 어디서든 429 에 기다리지 않는다(`triage_confirm._api`). 못 바꾼 표시는 `watch` tick 이 붙인다.
  유돌 수신기(도리 포크)도 결정 전 카드가 있는 스레드에 형 글이 오면 🔔 를 그대로 둔다.
- 보관된 스레드의 ✅⛔(2026-11-04, 36b605): Discord 는 보관된 스레드 안의 반응을 거부한다(400, 50083). 반응이
  그렇게 막히면 스레드 보관만 따로 풀고(`archived: false`, 이름 없이 — 이름 제한과 상관없고 429 에 기다리지 않음)
  다시 붙인다(`triage_approval_gate._add_reactions`). `watch` tick 은 ✅⛔ 가 빠진 카드를 찾아 채우되
  (`fill_missing_reactions`), 결정 전(pending)이고 그 채널의 가장 새 카드이며 글이 아직 카드 바이트 그대로인
  카드만 건드린다 — 새 판에 밀린 카드·거둔 카드·글이 「대체됨」으로 바뀐 카드는 버튼이 되살아나지 않는다. 그래도 못
  붙이면 `APPROVAL-REACTIONS-MISSING` 과 함께 그 tick 이 실패(rc 1)해 출력이 버려지지 않는다.
- 강제: `tests/unit/test_request_thread_adoption_conformance.py` — `resolve_new_binding` 호출부
  인벤토리에서 `request=` 없는 호출은 RED, 같은 패키지에 `approval_thread_id` 가 없어도 RED. 예외는
  공급망 표면(`skill_gate_surface`) 하나.
- 범위 밖: 공급망 승인(skill-deploy·attest·publish·submit·managed 활성화·release)은 2차 주체인
  peer 봇이 같은 채널을 봐야 하므로 `#approvals` 그대로.
- 배포 주의: interop 런타임(`INTEROP_RUNTIME`)이 **먼저** 새 시그니처를 가져야 한다 — 스킬만
  재배포되면 `request=` 를 모르는 옛 `resolve_new_binding` 이 `TypeError` 로 거부해 승인이 게시되지
  않는다(fail-closed). 릴리스 승인(`release.sh`)의 전량 수렴이 둘을 같이 올린다.
- Discord 제약: 스레드 이름 100자(라벨+제목 40자로 여유), 길드당 활성 스레드 1,000개 — 종결
  아카이브가 그 상한을 지킨다. 아카이브된 스레드에 새 메시지가 오면 자동으로 다시 열린다.

## 만료도 종결이다 (2026-09-03)

`ThreadOutcome.EXPIRED` 는 todo·budget 두 스킬에서 쓰이지 않아, 아무도 ✅ 하지 않은 요청의
스레드가 진행 중 보드에 그대로 남았다. 이제 todo `_expire` 는 아카이브한 뒤 `origin_notice` 로
EXPIRED 를 전달하고, budget 은 todo 와 같은 24시간 TTL 만료 분기를 새로 갖는다 — 둘 다 스레드
이름이 `💤` 로 닫힌다. 통지가 실패해도 아카이브와 종료 코드는 바뀌지 않는다. 소유자가
답하지 않은 것은 사고가 아니므로, 알리지 못한 사실이 요청 처리 결과를 뒤집어서는 안 된다.

## 형 요청 스레드 안의 카드 (2026-10-18)

형 지시(23:00 KST): "모든 요청은 별도 스레드로 열게 해". 형 요청이 이미 `#agent-chat` 아래
스레드에서 오가면, 그 요청의 승인 카드는 채널에 안내를 올리고 새 스레드를 여는 대신 **그 스레드에**
선다. 대화·카드·결과 통지가 한 스레드에 남는다.

- 형 글이 스레드 안: 카드가 그 스레드로 간다(Discord 조회 한 번, 새 글·새 스레드 없음).
- 형 글이 채널에 있고 거기 스레드가 이미 달림: 예전처럼 그 스레드를 쓴다(스레드 id = 메시지 id).
- 형 글이 채널에 있고 스레드가 없음: 그 글에 스레드를 연다.
- `#agent-chat` 밖의 스레드는 예전처럼 안내 + 새 스레드.
- 시험: `tests/unit/test_request_thread_owner_thread.py`.
