# 설치기 위생과 신뢰키 회전 병합

## 무엇을

설치기가 **자기가 어느 노드를 설치하는지 추측하지 않게** 하고, dry-run의 rc 0이
「전제 충족」으로 읽히지 않게 하고, clone이 요구하는 호스트키 부재를 이름 붙여
먼저 알린다. 그리고 신뢰키를 회전할 때 **구 키와 신 키를 함께 설치**할 수 있는
`install --add`를 더한다.

## 왜

네 가지 모두 「조용히 잘못되는」 모양이었다.

- `--config`는 아무것도 구성되지 않은 호스트에서 `--dry-run`이 돌게 하려고 선택
  인자다. 그런데 같은 기본값이 **실제 설치**를 추적된 시드
  (`configs/node.example.toml`)로 보낸다 — 다른 설치의 계정·경로·호스트명이 root
  소유 sudoers·systemd 자산에 그대로 박힌다. 설치 가이드가 모든 예시에서
  `--config`를 요구하는 것으로 덮고 있었지만, 산문은 가드가 아니다.
- `--dry-run`은 `check` 액션을 **실행하지 않는다**. rc 0은 "계획을 계산할 수
  있다"는 뜻인데 "전제가 충족됐다"로 읽기 쉽다.
- clone은 `StrictHostKeyChecking=yes`로 도는데 설치기는 `known_hosts`를 시드하지
  않는다. 첫 설치에서 ssh 안쪽에서 죽고, 운영자에게는 예외 타입 이름만 남았다.
- `plan_signer_install`이 단일 엔트리로 신뢰 파일 전체를 렌더해 교체하므로, CLI로
  새 신뢰키를 넣으면 **구 키가 사라진다**. 회전은 신 키로 서명한 릴리스를 컷하기
  전에 전 노드가 두 키를 함께 신뢰해야 안전한데, 순서를 어기면 노드가
  `UPDATE-TRUST-BLOCK`으로 멈춘다 — 그것은 rc 0이라 알람이 없다.

## 사용 시나리오

**계획만 보기 (권한 불필요, 아무것도 쓰지 않는다)**

```bash
python3 -m automation.install --update-trust-key <bundle>/update-trust.pub --dry-run
```

마지막 줄에 이렇게 나온다:

```
NOTE: check 항목은 쓰기가 아니라 판정이며 --dry-run에서는 실행되지 않는다
(checks are not executed in dry-run) — rc 0은 「계획이 만들어졌다」이지
「전제가 충족됐다」가 아니다.
```

**실제 설치에서 `--config`를 빠뜨리면 (거부 경로)**

```
INSTALL-BLOCK: NODE-CONFIG-REQUIRED: 실제 설치에는 --config가 필요하다. 생략하면
추적된 시드(configs/node.example.toml)가 쓰여 다른 설치의 계정·경로·호스트명이
root 소유 자산에 그대로 박힌다. 이미 구성된 노드라면
`--config /etc/autophagy/node.toml`을 명시한다. 계획만 보려면 --dry-run을 붙인다.
```

**호스트키가 없으면 (clone 전에 멈춘다)** — `KNOWN-HOSTS-MISSING`이 호스트명과
`ssh-keyscan <host>` 명령을 함께 알린다. **설치기가 대신 넣어주지는 않는다** —
어떤 호스트키가 진짜인지는 지문을 대역외로 대조한 사람만 정할 수 있고, 그 판단을
설치기가 가로채면 `StrictHostKeyChecking=yes` 자체가 무의미해진다
([install.md](../guide/install.md) §6.2).

**신뢰키 회전 (두 키 병기)**

```bash
# 먼저 렌더될 파일에 두 줄이 다 들어있는지 눈으로 본다
sudo python3 automation/install/trust_key_bootstrap.py install --add --dry-run \
    --key <bundle>/update-trust-2.pub --path /etc/autophagy/update-allowed-signers

# 실제 병합 — 구 키 줄은 보존된다
sudo python3 automation/install/trust_key_bootstrap.py install --add \
    --key <bundle>/update-trust-2.pub --expect-fingerprint 'SHA256:<신키>'
```

같은 키를 다시 넣어도 줄이 늘지 않는다(멱등). 설치본이 엔트리 0개로 파싱되면
`SIGNERS-EMPTY`로 멈춘다 — 어떤 릴리스를 진짜로 인정할지 정하는 파일을 추측으로
다시 쓰지 않는다. `--add` 없는 `install`은 그대로 교체이며, 그것이 회전의 마지막
단계다([manual-maintainer.md](../guide/manual-maintainer.md) §3.3·§3.4).

**소유자 DM은 여전히 검사되지 않는다** — `discord_check`의 보고에
`UNVERIFIED-SURFACE` 한 줄이 추가됐다. 채널 검사가 전부 PASS여도 메일·캘린더·
조율·할일·수리 승인이 도달한다는 뜻이 아니다. DM 채널은 config에 id가 없고 조회
자체가 쓰기 호출이라 읽기 전용 검사가 확인할 수 없다 — 설치 후 소유자가 봇과의
DM을 열어 첫 승인 카드가 오는지로 확인한다.

## 관련

- 승인·게이트: 없음(설치 시점 도구). 실제 설치는 root 권한이 필요하고
  `--dry-run`은 필요 없다.
- 핵심 파일: `automation/install/{installer,known_hosts,allowed_signers,trust_file,trust_key_bootstrap,discord_check,apply,executor}.py`
- 회귀: `tests/unit/test_install_{config_required,known_hosts,signer_rotation,owner_dm_coverage,clean_host_ci}.py`
- CI: `python:3.12-slim` 컨테이너에서 의존성 설치 없이 `--dry-run` rc 0을 확인하는
  `clean-host-install` 잡 — 설치기의 import 표면이 stdlib 밖으로 넓어지는 순간
  빨간불이 된다.
- 같은 사이클의 인접 수리: 소유자 자격증명 조회 alias 프로비저닝 복원
  (`automation/provision-agent.sh`), peer-attestation 신뢰 앵커 진단
  (`automation/peer_attestation.py`), 스킬 시나리오 드리프트 가드
  (`tests/unit/test_skill_scenario_drift.py`).
