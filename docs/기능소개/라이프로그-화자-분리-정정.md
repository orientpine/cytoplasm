# 라이프로그 화자 분리 정정

## 무엇을

라이프로그 전사본이 "화자 1명 · 벽 하나" 로 나오던 것을 고쳤다. 화자 분리 기본값 두 개를
노드 실측으로 다시 잡고, 군집화의 잔여물을 화자로 세지 않게 하고, 화자가 하나뿐일 때도
문단이 끊기게 했다. 그리고 **전사본에게 화자 수를 물어 그 수로 한 번 더 나누는 패스**를
더했다. 덤으로, Plaud 가 제목을 못 붙인 녹음의 노트가 시각을 이름으로 쓰던 것도 고쳤다.

## 왜

소유자가 라이프로그 노트 두 건을 보고 "너무 별로야 … 화자 수가 틀린 것은 그렇다 치고,
**발화 구분 자체도 올바르게 안되어 있어**" 라고 지적했다. 노드에서 그 두 녹음의 오디오를
되받아 재보니 지적이 정확했고, 원인이 넷이었다(증적 [docs/qa/PLD1](../qa/PLD1/summary.md)).

### 1. 임계값이 절벽의 반대편에 있었다

배포 기본값(`1.35`)은 두 녹음을 **둘 다 화자 1명**으로 뭉갰다. 임계값을 훑어 보면 사다리가
아니라 절벽이다(발화 시간 5% 이상만 화자로 셈):

| 임계값 | 272.5초 (소유자 "3명") | 549.4초 (소유자 "4명") |
| ---: | --- | --- |
| 0.8 | 6명 / 43턴 | 7명 / 150턴 |
| **1.0** | **4명 / 40턴** | **4명 / 139턴** |
| 1.2 | 2명 / 30턴 | 2명 / 104턴 |
| 1.35 (옛 기본값) | 1명 / 12턴 | 1명 / 51턴 |

옛 값은 64분 2인 녹음에서 골랐지만 그 표는 파편 가드를 **주지 않고** 잰 것이었다 —
임계값은 그 가드와 함께 붙는 값이라, 실행 조건과 다른 조건에서 고른 값이었다.

### 2. 발화 구분을 지운 것은 임계값이 아니라 파편 가드였다

`--min-duration-off=0.8` 은 같은 화자의 0.8초 미만 간격을 **재귀적으로 이어 붙인다**.
그래서 4.5분 녹음의 턴 중앙값이 16.65초였다 — 화자 수 이전에 발화 구분이 문서에 없었다.
화자 수를 정답으로 고정해 놓고 가드만 바꾸면 이렇게 된다:

| 녹음 | 고정 화자 수 | 가드 | 화자 | **턴** |
| --- | ---: | --- | ---: | ---: |
| 272.5초 | 3 | 0.5/0.8 (옛 기본값) | 3 | 34 |
| 272.5초 | 3 | 0/0 | 3 | **104** |
| 549.4초 | 4 | 0.5/0.8 | 4 | 108 |
| 549.4초 | 4 | 0/0 | 4 | **280** |

**화자 수는 그대로인데 턴만 3배**다. 이어 붙인 침묵이 전사 커버리지의 발화 시간에도 섞여
261.8초로 보고됐다(실제 244.3초). `off` 만 0 으로 내리고 `on=0.5` 는 남겼다 — 0.5초 미만
조각의 임베딩은 불안정해 가짜 화자를 만들고, 동시 발화(=`화자0 OVERLAP`)도 늘린다.

### 3. 임계값을 낮추면 부스러기 군집이 함께 생긴다

549.4초 녹음은 새 임계값에서 군집 22개가 나오는데 그중 실질은 4명이고 나머지 18개는
1% 미만 조각이다. 그것까지 화자로 세면 아무도 하지 않은 말에 `화자5`‥`화자22` 가 붙는다.
발화 시간 5% 미만 군집은 분리기 경계에서 뺀다 — 그 낱말은 다른 화자로 넘어가지 않고
근거를 잃어 `화자0` 으로 남는다. 전부 바닥 아래면 전원을 남긴다(라벨 0개가 더 나쁘다).

### 4. 화자가 하나면 문단 규칙이 꺼져 있었다

블록은 화자가 바뀔 때만 닫혔다. 그래서 모든 낱말이 한 화자에게 배정된 녹음은 문장 179개가
블록 **하나**로 나왔다. 사람이 읽는 단위는 화자와 무관하므로 문단 경계를 화자 배정 여부와
상관없이 적용한다.

### 5. 그리고 화자 수는 오디오가 아니라 전사본이 안다

어떤 고정 임계값도 두 녹음을 동시에 맞히지 못한다. 그런데 화자 수를 **주면** 분리기는
그 수로 다시 묶는다:

| 경로 | 272.5초 (기준점 3) | 549.4초 (기준점 4) |
| --- | --- | --- |
| sherpa 자동 (옛 기본값) | 1 ✗ | 1 ✗ |
| sherpa 자동 (새 기본값) | 4 | **4 ✓** |
| sherpa · 화자 수 고정 | 2 ✗ | 3 ✗ |
| pyannote 자동 | 2 ✗ | 2 ✗ |
| **pyannote · 화자 수 고정** | **3 ✓** | **4 ✓** |

세 번째 목소리는 음향적으로 분리 **가능하다**(pyannote 가 발화 시간 11.4% 로 찾는다).
모자란 것은 분리기가 아니라 k 를 아는 일이고, k 의 근거(자기소개·호칭·질문과 응답의 짝)는
전사본 텍스트에 있다. 그래서 1차 분리로 만든 초안을 모델에게 보여 주고 **화자 수만** 묻는다.

처음 붙였을 때는 이게 듣지 않았다. 노드에서 실제로 돌리니 모델이 두 녹음 모두 "2명"이라
답했다(기준점 3·4). 초안이 **1차 분리 라벨로 조립**되므로 모델이 문서에 보이는 라벨을 그대로
세어 돌려준 것이었다. 같은 초안에서 라벨만 걷어내고 다시 물었더니:

| 초안 | 모델의 답 |
| --- | --- |
| 라벨 있음(`화자1`·`화자2`가 보임) | 2명 |
| **라벨 없음(시각과 말만)** | **3명 ✓** |

프롬프트에 "라벨을 믿지 말라"고 적어 둔 것으로는 이기지 못했다. 그래서 세지 말라고 부탁하는
대신 셀 것을 주지 않는다 — 이제 초안은 화자 라벨을 걷어낸 채로 모델에게 간다. 말은 한 글자도
바뀌지 않는다.

고친 뒤 노드에서 두 녹음을 끝까지 돌린 결과는 이렇습니다. **절반만 성공했습니다.**

| 녹음 | 말씀하신 인원 | 모델의 답 | 문서의 화자 |
| --- | ---: | ---: | ---: |
| 272.5초 | 3명 | 3 | **3명 ✓** |
| 549.4초 | 4명 | 2 | 2명 ✗ |

272.5초는 사슬이 스스로 맞혔습니다(1차 2명 → 모델 3 → 강제 재분리 → 3명). 549.4초는 라벨을
걷어낸 8,624자 초안에서도 모델이 2라고 답해 재분리가 일어나지 않았습니다. 그래서 "전사본이
화자 수를 안다"는 것은 이 두 표본에서 **한 번만** 참이었고, 그래서 이 패스는 옵트인으로
둡니다. 반대로 549.4초는 질의 패스 없이 기본값만으로 4명(말씀하신 인원)이 나옵니다 —
두 경로가 서로 다른 녹음을 맞힙니다.

### 6. 한계 — 긴 녹음은 과분할된다. 그리고 되돌릴 수 있다

솔직히 적는다. 새 임계값은 **긴 녹음을 과분할한다**. 소유자가 화자 2명으로 확인한 64분
녹음을 파이프라인에 그대로 통과시키면 이렇게 나온다.

| 설정 | 문서에 나가는 화자 | 턴 |
| --- | ---: | ---: |
| 옛 기본값(1.35) | **2** (정답) | 584 |
| 새 기본값(1.0) | **4** (+2) | 944 |
| 새 기본값 + `--speaker-count 2` | **2** (정답) | **998** |

세 라이프로그 녹음을 나란히 놓으면 새 기본값의 오차 합이 더 작지만(3 vs 5), 이 녹음 하나만
보면 옛 값이 맞았다. 그런데도 `1.0` 을 고른 이유는 **실패의 방향**이다.

- `1.35` 의 실패는 **과병합**이다. 화자가 문서에서 아예 사라지고, 그 문서만 보고는 되돌릴
  방법이 없다 — 소유자가 지적한 두 녹음이 정확히 그 상태였다(둘 다 화자 1명).
- `1.0` 의 실패는 **과분할**이다. 한 사람이 둘로 보일 뿐이고, 위 표의 셋째 줄처럼
  `--speaker-count` 하나로 정확히 되돌아간다. 그것도 옛 기본값보다 **71% 많은 턴 구조**와
  함께(584 → 998).

즉 이 기본값은 "틀리더라도 되돌릴 수 있는 쪽으로 틀린다" 를 고른 것이고, 되돌리는 일을
자동으로 하는 것이 바로 §5 의 화자 수 질의 패스다. 화자 수를 아시는 녹음이라면 지금도
`--speaker-count N` 이 모든 추정을 이깁니다.

## 사용 시나리오

**평소(설정 없음)**: 라이프로그 녹음이 들어오면 새 기본값으로 분리·전사된다. 질의 패스는
옵트인이라 켜지 않으면 동작이 예전과 같고, 대신 임계값·가드·프룬·문단 규칙이 바뀐 만큼
전사본에 발화 구분이 살아 있다.

**질의 패스를 켠 노드**(`SPEECHTOTEXT_SPEAKER_COUNT_LLM=1`):
1. 1차 분리 → 초안 조립
2. 초안이 민감도 게이트를 통과하면 모델에 "몇 명인가" 만 질의(Codex OAuth 단일 경로)
3. 답이 지금과 다르면 그 수를 못박아 **한 번만** 재분리 → 화자 라벨·범례만 갱신
4. `DIARIZE-RECOUNT observed=<N> asked=<N> redo=<N|None>` 한 줄이 stderr 에 남는다

**거부·실패 경로**: 초안이 `patent-sensitive` 로 분류되면 모델을 부르지 않는다
(`RECOUNT-SKIP patent-sensitive`). 민감도 규칙을 읽지 못해도 묻지 않는다
(`RECOUNT-FAIL rules-unreadable`). 모델이 "3~4" 나 "세 명입니다" 처럼 애매하게 답하면
답으로 받지 않는다 — 망설임을 확신으로 바꾸면 그 라벨이 문서에서 누군가의 발언처럼 읽힌다.
질의 실패도 재분리 실패도 1차 결과를 그대로 남기고, **낱말은 어느 경로에서도 바뀌지 않는다**.
소유자가 `--speaker-count` 로 화자 수를 선언했으면 묻지 않는다.

**제목**: Plaud 의 AI 제목은 Plaud 요약과 같은 때 만들어지는데, 로컬 전사 경로는 요약도
전사도 빈 녹음을 골라 동결한다 — 즉 로컬 전사가 필요한 녹음은 언제나 제목이 없어
`2026-09-07-113911--….md` 처럼 시각이 이름 자리에 섰다. 이제 추출이 만든 제목이 그 자리를
대신한다(추가 모델 호출 없음, 이름에 글자가 하나도 없을 때만). Plaud 가 붙여 준 이름은
사람이 고른 이름이므로 기계 제목이 덮지 않는다.

## 후속 (2026-09-07 오후) — 화자 구분을 한 번 더, 그리고 노트 군더더기 정리

### 블록의 절반이 `화자0` 이던 진짜 이유

위 수정 뒤에도 블록의 약 절반이 `화자0` 이었습니다. 낱말 하나하나가 어떤 근거로 판정됐는지
노드에서 세어 보니 예상과 달랐습니다.

| | 272.5초 | 549.4초 |
| --- | ---: | ---: |
| 화자를 **정확히** 받은 낱말 | 85.4% | 76.1% |
| 화자가 없던 낱말 | 12.0% | 20.5% |
| **화자0 블록** | 47.6% | 49.7% |

낱말은 이미 대부분 맞고 있었습니다. 그런데 낱말 12%가 블록 48%가 됩니다 — 두 녹음 모두
**정확히 2.4배**로요. 배율이 같다는 것이 원인을 가리켰습니다: 판정 기준이 아니라 **문장을
조립하는 순서**였습니다.

사슬은 이렇습니다. 오전에 `--min-duration-off` 를 0으로 내린 것은 옳았지만(그 값이 4.5분
녹음을 12턴으로 뭉갰습니다), 그 값이 하던 일이 곧 "같은 사람의 짧은 쉼을 이어 붙이기"였습니다.
끄고 나니 한 사람이 문장 도중에 숨을 쉴 때마다 분리기가 턴을 둘로 나눴고, 그 경계마다 문장이
잘렸으며, 침묵에 걸친 조각은 근거가 없어 `화자0` 이 됐습니다.

그래서 두 곳을 고쳤습니다. **화자가 실제로 바뀌는 자리에서만 자르고**(침묵은 화자를 바꾸지
않습니다), **문장을 먼저 만든 뒤 그 문장 안의 낱말 증거로 화자를 정합니다**. 앞 문장을 보고
정하는 것이 아니므로 "직전 화자를 물려받지 않는다"는 원칙은 그대로입니다.

| 녹음 | 지적하셨을 때 | 오전 수정 뒤 | **지금** |
| --- | ---: | ---: | ---: |
| 272.5초 블록 / 화자0 | 31 / 51.6% | 84 / 47.6% | **36 / 33.3%** |
| 549.4초 블록 / 화자0 | **1** / — | 153 / 49.7% | **61 / 39.3%** |

문장 수도 104→61, 258→181 로 줄었는데 **말이 사라진 것이 아니라** 잘려 있던 조각이 원래
문장으로 되붙은 것입니다. 가장 긴 블록은 181자·200자라 벽도 아닙니다.

남은 한계: 549.4초에서 분리기가 찾은 4명 중 둘은 여전히 문서에 오르지 못합니다. 그 둘은
낱말 단위에서 한 번도 이기지 못해서 문장 단위 다수결로도 올라오지 않습니다 — 이번에 고친
것은 조각화이고, 그건 별개의 열린 항목입니다.

### 노트에서 걷어낸 네 줄

```
- 녹음:: 2026-09-07 (월) 15:06 · 4분 32초 · 화자 1명   ← 남습니다
- 사람:: [[신영구원님]], [[김병진]]                      ← 걷어냈습니다
- 한 줄:: 평지에 굴착 목표만 설정하자 …                  ← 걷어냈습니다
```

`사람::` 은 인식이 틀린 이름을 `[[위키링크]]` 로 굳혀 vault 에 없는 문서를 만들고 있었습니다
(`[[신영구원님]]` 은 "신영구 연구원님"의 오인식입니다). `한 줄::` 은 바로 아래 요약 첫 줄의
복사본이고, `주제::` 는 frontmatter 의 `tags:` 와 같은 값을 두 번 적고 있었습니다.
`장소::` 는 쓰는 곳이 없었습니다.

남긴 것은 `녹음::` 한 줄과 **진단 줄**입니다 — `추출:: 생략 (사유)`·`요약:: 없음 (사유)` 은
무엇이 잘못됐는지 알려주는 유일한 신호라 지우면 실패가 조용해집니다. frontmatter 태그는
그대로 생깁니다.

### 요약은 이렇게 바뀝니다

프롬프트를 v4 로 올려 **개요 문단 + 주제별 묶음**을 요구합니다. 노드에서 실제 모델을 불러
확인한 결과(마스킹):

```
## 요약

<개요 3문장 — 누가 무엇을 왜 이야기했고 어디로 결론이 갔는지>

### <주제 1>
- <숫자·조건·결론이 담긴 완결 문장>
- …

### <주제 2>
- …
```

소제목은 `###` 로 못박았습니다. `##` 는 노트 자신의 섹션과 같은 수준이라 구획과 충돌할 수
있고, `###` 는 충돌하지 않으면서 frontmatter 태그를 계속 만들어 줍니다 — 실제로 소제목 3개
에서 태그 3개가 생성됐습니다. 사람 이름은 이제 요약 본문이 문맥과 함께 말합니다.
