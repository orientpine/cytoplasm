# 기관메일 편집기 재로드 대기 — 승인된 메일이 몇 시간씩 멈추지 않게

## 무엇을

기관메일 발송이 본문을 채울 때, 메일 편집기(Namo CrossEditor iframe)가 스스로 다시 로드되는
몇 초를 **기다렸다가** 채운다. 채우기 호출을 0.5초 간격으로 최대 20초까지 다시 시도하고, 그
성공을 준비 신호로 삼는다(compose 열기가 이미 쓰는 방식과 같다).

## 왜

2026-09-28, 소유자가 ✅ 한 기관메일 두 건이 각각 1시간·4시간 넘게 나가지 못했고 그동안
`mail-triage-watch` 가 2분마다 `rc=6 GATE-REFUSED 메일 서비스 연결에 실패했습니다
(external_service_error stage=provider)` 를 반복 보고했다(연속 149회).

노드 로그의 실제 원인은 매번 같았다 — `compose editor frame unavailable`. 로그인도, compose
열기도 성공한 뒤였다. compose 를 연 뒤 1초 간격으로 편집기를 실측하니:

| compose 후 | 편집기 iframe body |
|------------|--------------------|
| t+1.4s | 있음 |
| t+2.5s ~ t+5.9s | **없음** (iframe 이 다시 로드되는 중) |
| t+7.8s 이후 | 있음 (안정) |

발송 경로는 고정 3초를 기다린 뒤 채우기를 **한 번만** 시도했으므로 정확히 그 구간에 걸려
실패했다. 재시도해도 같은 구간에 걸리니 150회에 한 번꼴로만 우연히 통과했다.

(같은 날 03:32~08:00 UTC 의 `open https://mailon.kr/ timed out` 은 별개다 — 로그인 페이지
자체가 열리지 않은 외부 장애였고 이 수정 대상이 아니다.)

## 사용 시나리오

- **happy**: 소유자가 승인 스레드에서 ✅ → 워처 틱이 발송 → compose 가 열리고 편집기가
  재로드되는 몇 초를 기다린 뒤 본문을 채움 → 수신자·본문 검증 → 발송 → 보낸편지함 확인.
  예전처럼 몇 시간씩 재시도가 쌓이지 않는다.
- **편집기가 끝내 돌아오지 않는 경우**: 20초 뒤 예전과 같은 오류로 fail-closed 한다. 무한
  대기는 없고, 워처의 기존 재시도·연속 실패 통지가 그대로 동작한다.
- **다른 브라우저 실패**: 재시도하지 않고 즉시 전파된다 — 재시도는 편집기 재로드 한 가지에만 쓴다.
- **안전 불변식**: 발송 직전의 수신자·본문 검증(`verify_compose_form`)과 편집기 API 재채우기는
  그대로다. 본문이 폼에 없으면 여전히 보내지 않는다.

## 검증 (마스킹)

같은 노드·같은 자격증명에서 벤더 트리만 바꿔 번갈아 `mailon send --dry-run`(POST 0, 외부효과 없음):

| 트리 | 결과 |
|------|------|
| 수정 전 (2회) | 2회 모두 `external_service_error` / `compose editor frame unavailable` — 사고 재현 |
| 수정 후 (3회) | 3회 모두 `{"status":"dry_run","csrf_present":true,"network_post_count":0}` |

단위 회귀: `tests/unit/test_mailon_editor_frame_reload.py` — 수정 전 2건 RED, 수정 후 GREEN.
