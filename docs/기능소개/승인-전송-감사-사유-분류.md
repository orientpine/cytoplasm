# 승인-전송 감사: 어긋난 행마다 사유를 이름 짓는다

## 무엇을
F4 스코프 감사의 `approvals-send-log` 체크가 어긋난 전송을 숫자 하나(`unmatched_sends`)로 보고하던 것을, 행마다 **세 가지 사유 중 하나**를 붙여 보고하도록 바꿨다.

- `approval-missing` — 소유자 승인 레코드가 없다(승인 게이트의 구멍, 항상 실패).
- `send-log-row-missing` — 승인은 있는데 감사 원장에 그 전송을 가리키는 행이 없다.
- `method-not-matched` — 가리키는 행은 있으나 매칭 규칙이 받아주지 않았다(검사기 쪽 격차).

## 왜
2026-08-21 라이브 노드에서 `unmatched_sends=31`(전부 `manual_reaction`)이 나왔는데, 증적만으로는 **검사기가 못 맞춘 것**과 **실제로 감사 행이 없는 것**을 가릴 수 없었다. 둘은 심각도가 다르다 — 전자는 감사 규칙의 결함이고, 후자는 승인-전송 추적의 구멍이다. 가르려면 사람이 노드에 들어가 한 건씩 대조해야 했다.

분리하는 과정에서 원인 하나가 코드에서 드러났다: 매칭 규칙이 쓰인 것은 2026-07-18(`35d104a7`)이고 `mail.compose_send` 감사 행이 생긴 것은 **그 다음 날** 2026-07-19(`02c133fa`)다. 승인·전송·감사 행이 모두 정상인 compose 발송이, 접미사 목록에 이름이 없다는 이유만으로 계속 어긋난 것으로 세어졌다.

## 사용 시나리오
**감사 실행(소유자)** — 기존과 같다. `automation/final/f4_scope.sh` 가 노드에 이 파일을 표준입력으로 흘려보내고, 계약(인자·증적 줄·실패 시 exit 1)은 그대로다. 달라진 것은 출력이다:
```
unmatched ref='...' method='manual_reaction' reason=method-not-matched sha256_prefix=...
```
사유가 `method-not-matched` 뿐이면 검사기 격차이고, `approval-missing` 이 하나라도 있으면 승인 게이트를 봐야 한다.

**분류는 면제가 아니다(실패 경로)** — 세 사유 모두 unmatched 로 세고 종료코드 1을 만든다. 읽을 수 없는 입력도 통과가 아니라 오류다(fail-closed).
