# 수리 승인 — 패치 내용에 바인딩

## 무엇을
자가수리(W6-2)의 승인 요청이 **어떤 코드 변경인지**를 보여주고, cha의 ✅가 **그 바이트에만** 유효하도록 묶는다.
요청별 승인 스레드의 카드에 변경 파일 목록·라인 증감·패치 sha256이 실리고, `action_hash`가 그 내용에서 파생된다.
패치 본문은 여전히 Discord에 노출하지 않고 ops 호스트 경로만 안내한다.

## 왜
기존 `repair_action_hash`는 `sha256("repair:<ticket>:<patch_name>")`였다. 패치 파일 이름은 언제나 `patch.diff`이므로
**해시가 티켓당 상수**였고, 적용 경로는 그 이름 해시를 디스크의 현재 파일로부터 다시 계산했다. 결과:

- 승인 DM에는 ticket·hash·nonce뿐이라 cha는 **무엇을 승인하는지 알 수 없었다**.
- 승인 뒤 `patch.diff`가 다른 내용으로 바뀌어도 해시가 그대로여서, **옛 ✅가 새 바이트를 적용**했다.

즉 그때의 ✅는 "이 코드 변경을 봤고 동의한다"가 아니었다.

## 사용 시나리오

### 정상 경로
1. 샌드박스가 GREEN이면 기존 정책이 정한 요청별 승인 스레드에 신규 v3 카드가 올라온다.
   대상·사실·위치·인계·되돌리기 **5필드, 각 한 줄**이다. 아래 해시·시각은 설명용 자리표시자이며 실제 카드는 전체 값을 싣는다.

```
대상: 수리 승인 (<ticket>)
사실: action_hash: <전체 해시>; patch_sha256: <전체 digest>; 1 files +1/-1; - automation/mod.py (+1/-1); nonce: <nonce>; sandbox: PASS; 패치 본문 비노출: `<패치 경로>` (승인 요청; 만료: <생성 시각+24h>)
위치: 이 메시지
인계: 소유자: 위 위치 · 반응 ✅ 승인 또는 ⛔ 취소; 다음: 승인된 패치만 반영
되돌리기: 해당 없음; 취소 시: 패치 미반영, 티켓 재개
```

카드는 자기 표면을 가리키므로 Discord URL을 붙이지 않는다. ✅·⛔ 판정과 24h TTL은 기존 그대로다.

2. cha가 ✅를 누른다. 워처가 적용을 지시하면, 적용 게이트가 **그 순간 디스크의 패치**로 해시를 다시 계산해
   승인된 해시와 대조한 뒤에만 적용한다.
3. 파일이 10개를 넘으면 10건만 나열하고 `… 외 N개 파일 생략`을 붙인다 — **합계와 해시는 항상 전체를 포함**한다.

### 실패·거부 경로
- **승인 후 패치가 바뀌었다** → `RepairOpsError`로 거부하고 적용 0건. 티켓은 열린 채 남고 24h TTL 뒤 재개된다.
  (False가 아니라 예외인 이유: 호출자는 False를 "승인 대기"로 읽어 exit 0 하고, 그러면 워처가 레코드를 회수하며
  approvals 로그에 "승인됨"을 남긴다 — 아무것도 적용하지 않은 채로.)
- **cha가 아직 안 눌렀는데 패치가 바뀌었다** → 옛 메시지를 지운 뒤 새 요청을 올린다(살아 있는 요청은 항상 1건).
- **내용 바인딩 이전의 옛 레코드** → 그 ✅로는 아무것도 적용되지 않는다. 미반응 상태면 자동으로 교체되고,
  이미 눌린 것은 파괴하지 않고 TTL로 정리된다.
- **패치를 읽을 수 없거나 요약할 수 없다**(combined diff·바이너리·경로 이탈·비 UTF-8) → 아무것도 게시하지 않는다.
  누락된 파일 하나는 곧 승인받지 않은 변경이므로, 부정확한 요약보다 거부를 택한다.

## 승인 대기 리마인더

`repair_ops_reaction_watch`는 기존 승인 레코드의 표면에만 리마인더를 보낸다.
새 통지는 `owner_message` 봉투로 렌더하며, 같은 승인 스레드에서는 원문 URL을 반복하지 않는다.
소유자는 기존 승인 원문에 반응한다. 리마인더는 새 승인 카드가 아니며 원문을 교체하거나
리액션·해시·24시간 만료·발송 주기를 바꾸지 않는다. 봉투 모듈이 없는 구런타임이나
렌더 검증 실패에서는 기존 리마인더 바이트를 그대로 보낸다.

수리 완료·취소·만료·거부 보고는 `repair_report_queue` → `repair_report_consumer` →
`repair_report_send`의 봇 보고 프로토콜로 남는다. 탐지기 실행 경로와 수동 요청 중복제거는
이 통지 변경과 무관하다. 회귀: `tests/unit/test_repair_owner_message.py`.

## 주의
- 렌더러 v1·v2·v3의 문구는 **동결**이다. 이미 게시된 메시지는 **렌더 없이** 검증한다.
  신규 레코드는 실제 게시 본문의 `content_sha256`을 저장하며 공용 `automation.stored_content.content_matches`로 대조한다.
  저장 사실과 본문의 바인딩은 동결된 v1·v2·v3 읽기 문법으로 검증한다. 다이제스트가 없는 기존 레코드도
  같은 문법으로 읽으며, 검증을 위해 저장 레코드나 원격 메시지를 다시 쓰지 않는다.
- 신규 카드의 별도 `render_version=3`만 봉투를 사용한다. `render_version`이 없으면 기존 `content_binding_version` 선택대로
  v1(내용 바인딩 없음) 또는 v2(내용 바인딩 2)를 재생한다. **`content_binding_version=2`와 해시 preimage는 바꾸지 않는다.**
  문구 변경만으로 기존 카드를 수정·삭제·재게시하거나 레코드 판본을 올리지 않는다.
- 봉투 import 또는 렌더 실패 시 **신규 요청만** v2로 만들고 실제 사용한 `render_version=2`를 기록한다.
  CLI는 자격증명만 읽고, 기존 바인딩을 먼저 해석한다. 살아 있는 동일 요청이나 이미 결정된 요청은
  새 카드를 준비하지 않는다. 신규 카드가 필요할 때만 시각·본문·판본을 동결한 뒤 요청 스레드를 해석·생성한다.
  신규 카드의 두 판본 모두 렌더 불가면 스레드·게시·pending 기록 모두 0건이다. 만료 시각의 마이크로초도 보존한다.
  이미 저장된 v3은 봉투 모듈 부재나 렌더 실패에도 그대로 검증·소비하며, 다른 본문으로 폴백하지 않는다.
  본문 변조·바인딩 불일치·알 수 없는 저장 판본은 계속 거부한다.
- v3의 리액션 안내는 직접 구성한다. v1·v2의 공유 문구 `.replace()`에 기대지 않는다.
  v3도 저장 레코드의 리터럴 바이트 핀으로 고정한다. 공유 `owner-ko-v1`은 동결이며 이후 문구 변경은 새 판본으로 추가한다.
- `core.quotePath` 때문에 실제 `git diff`는 한글 경로를 8진 이스케이프로 감싼다. 파서가 이를 복원하므로
  `docs/기능소개/*.md`를 건드리는 수리도 승인할 수 있다.
- 남은 창: `permits`가 바이트를 읽은 뒤 `git apply`가 같은 파일을 다시 읽는 **같은 실행 내부의 짧은 구간**.
  ops 전용 0700 경로에 대한 쓰기 권한이 필요하며, 완전 차단은 `repair_ops_cli.py` 경유 스레딩이 필요해
  후속 과제로 남겼다(`docs/features.md`).
