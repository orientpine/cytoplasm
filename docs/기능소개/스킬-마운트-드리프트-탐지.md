# 스킬 마운트 드리프트 탐지

## 무엇을

머지된 스킬이 실제로 prod에 마운트됐는지를 헬스체크가 매 스윕마다 대조한다. 어긋나면 FAIL과 함께 어느 스킬이 어긋났는지 이름으로 짚어준다.

## 왜

**릴리스 수렴과 스킬 마운트는 서로 독립이다.** 머지는 릴리스(git sha)만 움직이고 스킬 마운트(내용 해시)는 건드리지 않는다. 그래서 릴리스가 `origin/main`에 도달해 있어도 스킬은 옛 내용으로 남을 수 있고, **그 상태는 아무 신호도 내지 않는다.**

배포 체크아웃이 어긋나면 `git pull --ff-only`가 막혀 시끄럽게 실패한다. 이쪽은 조용하다 — 에이전트는 새 코드가 돈다고 여기지만 실제로는 구버전이 돈다.

2026-08-01 실측에서 릴리스는 `79faef4`(= 당시 `origin/main`)였는데 **5개 스킬의 마운트가 이틀째 옛 내용**이었다. `611595f`가 건드린 6개 중 `doctype`·`mail`만 배포되고 나머지가 남은 **부분 배포**였다. 부분 배포가 가장 조용하다 — 배포가 "있었기" 때문에 아무도 다시 보지 않는다.

## 어떻게 판정하나

`skill_digest(릴리스/skills/<이름>)` 대 `readlink live/<이름>`이 가리키는 해시를 비교한다. 마운트 심링크가 내용 해시를 경로에 그대로 담고 있어서, 판정이 `readlink` 한 번으로 끝난다.

git sha를 쓰지 않는 이유 셋:

- sha는 리포 전체에 하나뿐이라 **어느 스킬이** 바뀌었는지 말해주지 못한다
- 스킬은 sha가 없는 출처(샌드박스·managed 활성화)에서도 배포된다
- 마운트는 커밋이 아니라 아티팩트라, 물어야 할 질문이 "지금 걸려 있는 내용이 릴리스와 같은가"다

## 사용 시나리오

**정상**: `automation/healthcheck.sh`가 도는 동안 프로브가 릴리스와 마운트를 대조한다. 일치하면 `PASS <primary-node> skill mounts match the release` 한 줄로 지나간다.

**드리프트 발견**: 스킬을 머지했는데 배포를 잊었다. 다음 스윕에서 이렇게 나온다.

```
[healthcheck] SKILL-STALE: calendar — 릴리스 6b9133e8d73fe736… 이지만 마운트는 19e4e1e9c0519842…
[healthcheck] FAIL <primary-node> skill mounts match the release
```

수리 티켓에는 **"이것은 코드 결함이 아니라 배포 누락이다 — 패치하지 말 것"**이 먼저 실린다. 수리 자동화의 반사적 조치는 코드를 고치는 것인데, 여기서는 코드가 멀쩡하므로 그 반사가 곧 헛수고가 되기 때문이다. 조치는 어긋난 스킬마다 `automation/deploy-skill.sh <skill>`을 돌려 소유자 ✅ 뒤 마운트하는 것이다.

**판정 불가**: 릴리스 트리나 마운트 루트를 읽지 못하면 `PASS`가 아니라 **실패**한다. 이 드리프트는 원래 조용해서, 판정 불가를 통과로 처리하면 프로브가 있으나 마나가 된다.

## 알아둘 것

- **읽기 전용**이다. 배포를 시도하지 않는다 — 탐지기가 스스로 고치려 들면 소유자 승인 게이트를 우회하게 된다. 쓰기 호출이 없다는 것을 AST로 고정해 두었다.
- **마운트는 심링크만** 센다. 마운트 루트에는 스킬이 아닌 것도 산다(실측: root 소유 `.hub`). 심링크가 진짜 디렉터리로 바뀌어치기는 손상은 조용히 통과하지 않고 "미배포"로 잡힌다.
- `hello-autophagy`는 예외 목록에 사유와 함께 등록돼 있다 — 마운트 대상이 아니라서, 넣지 않으면 헬스체크가 영구 적색이 되고 영구 적색인 게이트는 아무도 보지 않게 된다. 예외는 "배포하지 않음"만 뜻하며, **마운트돼 있는데 내용이 어긋나면 예외와 무관하게 잡힌다.**
