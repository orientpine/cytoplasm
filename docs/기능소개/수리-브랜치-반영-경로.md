# 자가수리 — 브랜치로 반영, main은 cha가 머지

## 무엇을
수리 에이전트가 만든 패치를 **`repair/t_<ticket>` 브랜치로 push**한다. 작업은 전용 작업 클론
(`/srv/autophagy-repair-work`)에서만 이뤄지고, 배포 체크아웃(`/srv/autophagy-agents`)은
**커밋이 구조적으로 불가능**해졌다 — pre-commit 훅이 모든 커밋을 무조건 거부한다.
main 반영은 cha가 GitHub에서 브랜치 diff를 보고 머지한다.

## 왜
2026-07-28 드리프트 복구에서, 배포 체크아웃의 미병합 커밋을 만든 주체가 사람이 아니라
**수리 자동화 자신**임이 드러났다. ops deploy key가 read-only라 그 커밋들은 origin에 도달할 수 없었고,
결과는 삼중 손해였다:

- 프로덕션이 **git에 없는 코드**를 돌린다.
- 다음 정렬 때 그 수리가 **말없이 유실**된다.
- 그전까지 **모든 세션의 `git pull --ff-only`가 막힌다**.

즉 "즉시 반영"이라는 장점을 유실·파이프라인 정지로 지불하는 구조였다. 이제 급한 불은 브랜치까지
자동으로 꺼지고, main 반영만 사람 눈을 거친다.

## 사용 시나리오

### 정상 경로
1. 티켓이 열리고 샌드박스 회귀가 GREEN이면, `#approvals`에 승인 요청이 올라간다.
2. cha가 ✅를 누르면 수리가 **작업 클론에서** apply·commit된다(배포 체크아웃은 건드리지 않는다).
3. 커밋이 생기면 곧바로 `repair/t_<ticket>` 브랜치로 push된다. 결과 JSON에 `branch` 필드가 실린다.
4. cha가 GitHub에서 브랜치 diff를 확인하고 main으로 머지한다.
5. 노드는 평소대로 `git pull --ff-only`로 받는다. 배포가 필요하면 기존 배포 경로를 탄다.

### 실패·거부 경로
- **push 키가 없으면** → push를 시도하지 않고 `exit 4` + `push_error`. 조용히 ops read-only 키로
  폴백하지 않는다(진짜 원인에서 먼 곳에서 실패하는 것을 막기 위해).
- **티켓 id가 아니면** → git이 실행되기 전에 거부. `main`·`../main`·`refs/heads/main` 모두 차단되므로
  조작된 id로 refspec을 넓힐 수 없다.
- **회귀 뱅크가 RED면** → 커밋 자체가 없으므로 아무것도 push되지 않는다(`exit 3` 유지).
- **배포 체크아웃에서 커밋을 시도하면** → 훅이 `exit 1`로 거부하고, 개발 체크아웃에서 커밋하는 방법과
  **비파괴 복구 절차**(`format-patch` → `am`)를 함께 안내한다. `git fetch`·`git pull --ff-only`는
  커밋을 만들지 않으므로 영향이 없다.

## 주의
- 키는 `/srv/autophagy-private/repair_push_key`(ops:600)에 둔다. **홈에 두면 안 된다** —
  두 수리 유닛이 `ProtectHome=yes`라 `/home`이 서비스에게 빈 디렉터리로 보이고, 파일이 디스크에
  멀쩡히 있는데도 런타임에만 "키 없음"으로 실패한다.
- 호스트 키는 `/srv/autophagy-private/repair_known_hosts`에 고정한다. 같은 `ProtectHome` 때문에
  유닛은 `~/.ssh/known_hosts`에 닿지 못하고 노드에 전역 호스트 키 파일도 없어, 고정하지 않으면
  push가 호스트 키 검증에서 죽는다. `accept-new`로 우회하지 않는다.
- `main` 직접 push와 자동 ff-머지는 금지다. 훅과 테스트가 함께 강제한다.
