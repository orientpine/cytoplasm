# 제3자 런타임 전제 문서 + 초기 설정 보조 (P0-6)

## 무엇을

공개본을 처음 설치하는 사람이 **스스로 마련해야 하는 것**을 한 문서
([`docs/guide/third-party-runtime-prereqs.md`](../guide/third-party-runtime-prereqs.md))에 모으고,
기계로 확인할 수 있는 두 부분을 도구로 만들었다.

- `automation/install/discord_check.py` — 봇 토큰 하나로 **토큰 유효성 · Message Content 인텐트 ·
  봇 권한 · 필수 채널 3종 접근**을 read-only(전부 GET)로 확인한다.
- `automation/install/trust_key_bootstrap.py` — 업데이트 신뢰키를
  `/etc/autophagy/update-allowed-signers`에 **root:root 0644**로 설치하고, 지문이 공개 repo에
  게시된 공지값과 일치하는지 대조한다.

## 왜

설치가 실패하는 지점은 대부분 코드가 아니라 **전제**다. Message Content 인텐트가 꺼져 있으면
다른 봇 메시지의 본문이 빈 문자열로 도착해 규약 파싱이 **오류 없이 조용히** 전부 실패하고,
채널 권한 하나가 빠지면 승인 리액션을 읽지 못한다. 이런 것은 설치 후 몇 시간 뒤에야 증상으로
나타나므로, 시작 전에 이름을 붙여 지목해 주어야 한다.

업데이트 신뢰키는 다른 이유로 필요하다. 자동 업데이트는 **서명된 릴리스 태그에만** 수렴하는데,
서명을 검증하려면 코드를 받기 전에 이미 서명자를 신뢰하고 있어야 한다(닭-달걀). 그래서 키를
설치기에 동봉하고, 그 신뢰가 실제 값을 갖도록 **지문을 대역외로 공지해 사용자가 직접 대조**한다.

## 사용 시나리오

### 정상 경로

1. Discord 앱·봇을 만들고 Message Content 인텐트를 켜고, 최소 권한 초대 URL(`permissions=309237746752`)로
   협업 서버와 개인 서버에 초대한다.
2. `set -a; . ~/.env.secrets; set +a` 후
   `python3 automation/install/discord_check.py --config ~/.hermes/interop/config.json` →
   모든 체크가 `PASS`, 종료코드 0.
3. `trust_key_bootstrap.py fingerprint --key <번들>/update-trust-key.pub`로 지문을 보고,
   공개 repo README·릴리스 노트의 공지값과 **눈으로** 대조한다.
4. `sudo ... trust_key_bootstrap.py install --key ... --expect-fingerprint 'SHA256:<공지값>'` →
   이어서 `verify`가 소유·모드·지문을 전부 `PASS`로 낸다.
5. 전제 체크리스트 9개가 통과하면 설치 절차(`docs/guide/install.md`)로 넘어간다.

### 실패·거부 경로

- 인텐트가 꺼져 있으면 `MESSAGE-CONTENT-INTENT-OFF`와 함께 Portal 경로와 "게이트웨이 재시작까지
  해야 적용된다"는 조건을 함께 알린다.
- `Administrator`·`Manage Guild`·`Manage Roles`를 가진 봇은 `OVER-PRIVILEGED`로 **거부**한다 —
  편의가 아니라 위협모델 문제이기 때문이다.
- 채널은 실패 형태를 구분해 지목한다: id 미제공(`MISSING-CHANNEL-ID`) / 존재하지 않음
  (`MISSING-CHANNEL`) / 조회 불가(`NO-ACCESS`) / 이력 읽기 불가(`NO-HISTORY`) / 잘못된 타입.
- 번들 지문이 공지값과 다르면 **아무것도 쓰지 않고** non-zero로 끝난다.
- 설치본이 심링크·비-root 소유·group/other 쓰기 가능·0644가 아니면 `verify`가 각각 다른 코드로
  거부한다. 그리고 그 파일을 **지우면 리컨실러는 검증 근거가 없으므로 전진을 거부한다**(fail-closed).
