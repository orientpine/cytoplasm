# 제안서 표 크기 최적화

## 무엇을

렌더가 끝난 HWPX 의 표에서 **열 너비를 내용에 맞게 다시 나눈다**. 양식(seed)에서 복제된 표가
물려받은 균등 분할을 버리고 각 열이 실제로 요구하는 폭에 비례해 다시 배분한 뒤, 표 전체가
본문 폭(42,520 HWPUNIT)에 정확히 맞도록 만든다.

## 왜

`kimm-docbot` 은 비교표·KPI 표를 KIMM 양식의 표에서 **복제**해 만든다. 그래서 표의 크기가 원
양식에 맞춰진 채로 남았다 — 실측(2026-09-07, `excavator` v000011):

| 표 | 열 0 | 열 1 | 열 2 | 폭 합 |
|---|---|---|---|---|
| 비교표 | 33.3% (수요 14.4%) | 33.3% (30.6%) | 33.3% (55.0%) | 41,952 |
| KPI 표 | 33.3% (16.0%) | 33.3% (**8.8%**) | 33.3% (75.3%) | 41,952 |

단위 열("%")이 필요한 폭의 **3.8배**를 차지해 그만큼이 공백으로 남았고, 설명 열은 필요한 폭의
0.44배만 받아 여러 줄로 접히며 표가 불필요하게 높아졌다. 표 폭 합도 본문 폭보다 568 모자라
오른쪽에 빈 띠가 남았다.

## 사용 시나리오

**정상 경로.** 평소대로 렌더하면 된다 — 새 명령도 새 옵션도 없다.

```bash
python3 -m skills.proposal.scripts.proposal_cli render --slug <slug>
```

렌더가 표를 모두 쓴 뒤 마지막에 열 너비를 다시 잰다. 같은 문서의 실측 변화:

- KPI 표 `[13984, 13984, 13984]`(합 41,952) → `[10196, 5540, 26784]`(합 **42,520**)
- 표 안의 글자는 한 자도 바뀌지 않는다(추출 텍스트 sha 동일).
- KPI 행이 3줄에서 2줄로 줄어 아래 내용이 그만큼 위로 올라온다.

**손대지 않는 것.** 추진 내용 표(13열)처럼 **자기 배분 규칙을 이미 가진 표**는 건드리지 않는다.
행 높이도 그대로 둔다 — 표가 `noAdjust="0"` 이라 한/글이 열 때 내용에 맞춰 다시 계산하므로,
우리가 추정해 적으면 오히려 지워지지 않는 공백이 된다.

## 관련

- 엔진: `kimm-docbot` `src/kimm_docbot/hwpx/table_fit.py`(`fit_tables`), 배선은
  `pipeline/orchestrator.py` 의 표 작성 직후. 회귀는 `tests/hwpx/test_table_fit.py`.
- 엔진 위치: `skills/proposal/engine/`(2026-09-08 내제화). 엔진이 이 저장소 안에 있으므로 핀도, 노드
  런타임 설정 갱신도 필요 없다 — 체크아웃이 곧 렌더가 쓰는 엔진이다.
- 승인 게이트는 관여하지 않는다 — 렌더 안에서 끝나는 결정적 계산이다.
