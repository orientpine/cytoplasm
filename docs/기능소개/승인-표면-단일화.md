# 승인 표면 단일화 — 오너 DM 및 공급망 이원화

## 무엇을
소유자(cha) 전용 승인 요청은 행위 봇의 오너 DM으로, 스킬 공급망 승인은 개인 서버 `#approvals`로 전달하도록 승인 표면을 이원화하고 정책을 단일화합니다.

## 왜
기존에는 6개 모듈이 승인 채널을 각자 해석하여 문서와 실제 라우팅이 어긋나는 문제가 있었습니다. 메일 다이제스트는 오너 DM으로 오는데 푸터는 `#approvals`를 가리켰고, 실제 `#approvals` 채널에는 메일 승인이 단 한 건도 없었습니다. 특히 개인 서버에 참여하지 않는 ops 봇(수리 에이전트)은 승인 요청을 게시할 수 있는 경로가 아예 존재하지 않는 결함이 있었습니다.

## 사용 시나리오

### 정상 경로
1. cha가 에이전트에게 민감한 메일 답장 발송을 요청합니다.
2. 승인 요청이 개인 서버 `#approvals`가 아닌, 해당 에이전트와의 **오너 DM**으로 도착합니다.
3. 메시지에 미리 부착된 ✅를 누르면 메일이 즉시 발송됩니다.

### 실패·거부 경로
- ⛔를 누르면 취소되고 아무것도 발송되지 않습니다. ✅와 ⛔가 함께 있으면 **⛔가 우선**합니다(외부효과 fail-safe).
- 봇이 승인 표면이나 채널의 정체를 확정할 수 없으면, 임의의 채널에 추측해서 게시하지 않고 게시 거부(refusal)를 보고하여 안전을 보장합니다.
- 다른 봇의 DM ID를 재사용하려는 시도는 정책 모듈에서 거부됩니다.
- 정책이 바뀌기 전에 이미 올라가 있던 승인 요청은 **게시 당시의 채널에서 그대로 처리**됩니다. 정책 이력이 append-only라 과거 버전으로 저장된 레코드의 해석은 바뀌지 않으며, 이관 시점에 대기 중이던 승인은 하나도 무효화되지 않았습니다(프로덕션 감사로 확인).

### 공급망 승인 (대조)
- 스킬 배포(`deploy-skill.sh`) 시에는 피어 봇이 같은 채널에 독립적인 증명(attestation)을 게시해야 하므로, 기존처럼 개인 서버 `#approvals`에 요청이 게시되어 다자간 검증을 수행합니다.

## 관련
- 핵심 파일: `automation/interop/approval_surface.py` (정책 SSOT), `automation/interop/approval_directory.py` (채널 해석)
- 승인 게이트: `automation/interop/approval_lifecycle.py` (파사드 경유 강제)
- 정책 버전: `POLICY_VERSION = 6`
- 증적: `docs/qa/AS-0/` ~ `docs/qa/AS-3/`
