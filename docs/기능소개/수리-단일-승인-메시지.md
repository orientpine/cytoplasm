# 수리 승인 요청 — 단일 라이브 승인

## 무엇을
자가수리(W6-2)의 `#approvals` 승인 요청을 공유 승인 생명주기(`request_owner_approval`)로 게시한다.
티켓 하나가 가진 승인 키(`repair:{ticket_id}`)에는 **살아 있는 요청이 항상 1건**뿐이고,
저장된 `message_id`는 **덮어써지지 않는다** — 옛 메시지를 지운 뒤에만 교체된다.
생산자(게시)와 워처(리액션 해석)는 **같은 lease**를 잡으므로 서로 경쟁하지 않는다.

## 왜
수리 게이트는 원래 "같은 티켓이면 다시 올리지 않는다"까지만 지켰다. 그래서:
- 티켓의 패치가 바뀌어도 옛 요청이 그대로 살아 있어, cha가 **이미 폐기된 패치**의 해시에 ✅를 누를 수 있었다.
- 승인 메시지가 지워지면 레코드가 TTL(24h)까지 **고아로 남아** 그 티켓의 수리가 통째로 멈췄다.
- 900초짜리 patch apply가 도는 중에도 생산자가 같은 티켓을 건드릴 수 있었다.

## 사용 시나리오

### 정상 경로
1. 샌드박스가 GREEN이면 `#approvals`에 요청 1건이 올라간다(✅·⛔ 선부착, nonce·sha256 바인딩).
2. 같은 티켓·같은 패치로 다시 도달해도 **아무것도 올라가지 않는다** — 기존 요청이 그대로 유효하고 nonce도 그대로다.
3. 패치가 바뀌면 옛 메시지를 **먼저 지운 뒤** 레코드를 풀고 새 요청을 올린다(살아 있는 요청은 여전히 1건).
4. 승인 메시지가 사라졌으면 고아 레코드를 풀고 다시 올려 재바인딩한다.
5. cha가 ✅를 누르면 리액션 워처가 기존 `--apply-approved` 경로로 적용한다(TTL·감사 로그 동일).

### 실패·거부 경로
- cha가 이미 ✅/⛔를 누른 뒤 패치가 바뀌면 → 메시지를 지우지 않고 `owner-decided`로 연기. 그 승인은 워처가 소비한다.
- 본문이 저장된 요청과 다르면 → `binding-mismatch`로 거부(삭제·해제 없음).
- pending 레코드가 손상되면 → `store-unreadable`로 거부. 건너뛰면 "미결 없음"으로 읽혀 중복 게시가 되므로 fail-closed.
- Discord를 읽지 못하면 → `unverifiable`로 연기. 증명 못 한 생존은 생존으로 친다.
- 워처가 lease를 쥐고 있으면 → `lease-held`로 연기(게시·삭제·기록 모두 없음).

호출자가 보는 값은 변하지 않는다: `PostingOwnerApproval.permits()`는 예전처럼 **항상 `False`**를 돌려주고,
실제 적용은 리액션 워처의 다음 tick에만 일어난다.
