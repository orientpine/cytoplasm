# 릴리스 리텐션·설치 검증 (G3)

## 무엇을

불변 런타임 릴리스는 최근 5세대만 유지하되 현재 세대와 직전 세대를 반드시 보호한다. 새 릴리스와
이미 존재하는 릴리스를 활성화하기 전에, root 소유 설치 헬퍼가 기존 `release_provenance.py`로
파일 집합·Git blob OID·실행 비트·쓰기 권한을 기준 커밋과 대조한다.

헬스체크는 `/srv/autophagy-agent-releases`의 세대 수와 총 바이트를 함께 기록한다. 기본 경계는
보호 세대를 고려한 6세대와 1 GiB이며, 초과하면 수리 티켓 경로로 드러난다.

## 왜

기존 설치기는 호출자가 보낸 tar와 SHA를 그대로 신뢰해 `.origin-sha`를 썼다. 같은 SHA 디렉터리가
이미 있으면 내용 확인 없이 `current`만 다시 가리켰다. 따라서 마커는 출처의 증명이 아니었고,
착지마다 새 세대가 쌓여도 `/srv` 증가를 측정하는 주체가 없었다.

이번 변경은 새 서명 체계를 만들지 않고 이미 배포 가드가 사용하는 blob 단위 검증기를 설치 경계에
연결한다. SSH 서명 태그는 root/ops 침해까지 위협 모델을 넓힐 때의 별도 설계로 남긴다.

## 사용 시나리오

### 정상 설치

1. `land.sh` 또는 자동 수렴 헬퍼가 origin/main의 특정 SHA를 고정해 tar를 만든다.
2. root 설치 헬퍼가 staging에 압축을 풀고 읽기 전용으로 만든다.
3. staging 트리가 해당 커밋과 blob 단위로 일치할 때만 `os.replace`로 세대를 확정하고 `current`를
   원자적으로 전환한다.
4. 최근 5세대 밖의 릴리스를 정리하되 현재 대상·직전 세대·설치 중 staging은 건드리지 않는다.

### 변조·불일치 거부

- tar의 `seed.txt`가 주장한 커밋과 한 바이트라도 다르면 설치 디렉터리와 `current`를 만들지 않고
  `RELEASE-STORE-BLOCK`으로 끝난다.
- 기존 릴리스 디렉터리가 변조됐으면 재설치도 inode를 재사용하거나 심링크를 뒤집지 않고 거부한다.
- 헬스체크가 세대 또는 용량 경계를 넘긴 것을 발견하면 수동 `rm` 대신 정상 landing으로 pruning을
  재실행하도록 안내한다. 직전 세대 롤백 보호를 위해 임의 삭제는 하지 않는다.
