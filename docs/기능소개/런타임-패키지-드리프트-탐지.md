# 런타임 패키지 배포와 드리프트 탐지

## 무엇을

릴리스 트리 밖의 계정 홈에서 실행되는 Python 패키지가 릴리스와 같은지 헬스체크가
재귀 SHA-256으로 확인한다. 등록부 `configs/runtime-package-manifest.txt` 에는 지금 `rag_ingest`·
`regression_bank`·`research_trends` 와 RAG 노드의 `personal-rag` 트리가 있다(처음에는 `rag_ingest`·
`memory_curator` 둘이었고, `memory_curator` 는 래퍼가 릴리스 트리를 import 하게 바뀌며 빠졌다). RAG 인제스트에는 패키지 전체와 cron 래퍼를 배포하는
`automation/rag_ingest/deploy.sh`도 생겼다. 패키지의 `cron/` 하위는 대조에서 제외한다 —
배포기가 그것을 패키지에 넣지 않고 `~/.hermes/scripts/`로 따로 보내며, 그쪽은 워처
매니페스트 프로브가 관측한다(2026-08-22 첫 라이브 실행에서 `ABSENT cron/…_watch.py`
오탐을 내던 것을 바로잡았다).

> **2026-10 갱신**: 런타임 패키지는 이제 탐지에서 끝나지 않는다. 각 배포기 옆
> `deploy-manifest.txt` 에 `v2:tree` 행으로 선언돼, 릴리스 판정이 트리를 대조하고 어긋나면 그
> 배포기를 돌려 **수렴**시킨다. 교체는 `deploy_tree_swap`(staging → 원자 교체 → 재대조)으로 하며,
> 아래의 tar 교체 서술은 그 이전 방식이다. 지문은 양쪽 모두 노드 전용 `.env.secrets` 와 캐시
> 디렉터리를 뺀다. `memory_curator` 는 래퍼가 릴리스 트리를 import 하게 바뀌어 홈 사본이 retired
> 로 선언됐고 이 표에서 빠졌다. 상시 프로브는 그대로 남아 릴리스 사이의 드리프트를 알린다.

## 왜

RAG 워처는 불변 릴리스가 아니라 `~agent/.hermes/rag_ingest_runtime/`의 사본을
import한다. 2026-08-22 실측에서 래퍼는 릴리스와 같았지만 패키지는 2026-07-22에
머물러 `same=13, diff=5, absent=1`이었다. 즉 래퍼 드리프트 검사가 clean이어도 한
달치 기능과 수정이 프로덕션에 도달하지 않는 조용한 실패가 가능했다.

## 사용 시나리오

- **정상 배포**: 오케스트레이터가 머지 뒤 `automation/rag_ingest/deploy.sh`를 실행한다.
  배포기는 provenance를 확인하고 워처의 `watch.lock`을 최대 300초 기다린 뒤, 락을
  잡은 동안 패키지를 tar로 교체한다. 파일 수와 핵심 파일 해시, 별도 워처 래퍼 해시를
  원격에서 다시 읽어 모두 같을 때만 성공한다. cron은 이미 있으면 만들지 않는다.
- **실패·탐지**: 인제스트가 계속 실행 중이면 배포는 기존 패키지를 건드리지 않고 실패한다.
  배포를 빠뜨리거나 파일이 사라지면 healthcheck의 `runtime packages match the release`가
  `DIFF`·`ABSENT`·`EXTRA`를 파일별로 내고 해당 `deploy.sh`를 안내한다. 런타임을 읽지
  못한 경우도 `UNKNOWN`으로 실패하므로 조용히 통과하지 않는다. 로컬 릴리스 스냅샷은
  `/`에서 시작하는 격리된 subshell로 계산한다. 따라서 SSH 호출자가 접근할 수 없는 작업
  디렉터리를 상속해도 읽을 수 있는 릴리스를 거짓 `UNKNOWN`으로 판정하지 않는다.
