# 소유자 통지 자격증명 프로브 · argv 거부 명명

## 무엇을

healthcheck 스윕에 프로브 한 줄이 늘었다. `/etc/autophagy/repair-approval.env` 를 읽어
**이 노드가 소유자 통지를 보낼지 아무도 결정하지 않은 상태**를 잡는다. 그리고 설치기는
`discord_check.py` 가 argv 를 거부할 때 트레이스백 대신 이름 있는 실패를 낸다.

## 왜

### 1. 설치가 사람에게 넘긴 결정을 아무도 되묻지 않았다

설치기는 `DISCORD_BOT_TOKEN` 이 없으면 `discord-readiness` 를 WARN 으로 남기고
「소유자 확인 절차」를 출력한다. 그런데 **그 절차를 돌렸는지 묻는 것이 없었다** —
`LIVE_CHECKS` 의 어느 행도 통지 자격증명을 보지 않으므로, 끝내 채우지 않은 노드는
수렴 실패도 배포 드리프트도 소유자에게 알리지 못하면서 `ALL_HEALTHY` 를 계속 보고했다.
**통지가 도달하지 않는다는 사실 자체가 통지로만 알 수 있는 상태**였다.

### 2. 그렇다고 매 틱 Discord 에 물을 수는 없다

후속 과제는 "`discord_check.py` 를 프로브로 넣자, 다만 레이트리밋·주기를 먼저 정해야
한다"로 열려 있었다. 이 프로브는 **그 질문에 답하는 대신 없앤다** — 네트워크를 부르지
않는다. 5분 스윕이 Discord API 를 부르면 Discord 장애가 수리 티켓이 되고(cry-wolf),
정책 질문이 새로 생긴다. 조용한 실패의 실제 모양은 "끝내 안 채웠다"이고 그것은 파일
하나로 판정된다. 선례는 `peer_gateway_probe.sh` — 로컬·읽기 전용·설정 드리프트·fail-closed.

### 3. 빈 파일은 여전히 정당한 구성이다

[신규 노드 설치 공백](../troubleshooting/신규-노드-설치-공백.md) §2-1 은 "빈 파일로 두어도
된다"고 안내했고 그 말은 지금도 옳다 — 통지를 잃을 뿐 수렴은 그대로 돈다. 그래서 이
프로브가 묻는 것은 「채웠는가」가 아니라 **「결정했는가」**다. 무조건 실패로 만들었다면
문서가 허용한 구성을 5분마다 티켓으로 만들었을 것이다.

## 사용 시나리오

**결정하지 않은 노드.** 설치기가 놓은 빈 템플릿 그대로면:

```
[healthcheck] OWNER-NOTICE-CREDENTIAL-MISSING DISCORD_BOT_TOKEN AUTOPHAGY_OWNER_ID
OWNER-NOTICE-CREDENTIAL-RECOVERY: OWNER decide once in /etc/autophagy/repair-approval.env …
```

**키 이름만 나오고 값은 나오지 않는다** — 이 문구는 수리 티켓 본문이 되고 로그에 남는다.

**두 갈래 중 하나를 쓰면 통과한다.**

| 선택 | 파일에 쓰는 것 | 프로브 출력 |
|---|---|---|
| 통지를 받는다 | `DISCORD_BOT_TOKEN=…` · `AUTOPHAGY_OWNER_ID=…` | `OWNER-NOTICE-CREDENTIAL-PASS` |
| 받지 않는다(선언) | `OWNER_NOTICE_OPTIONAL=1` | `OWNER-NOTICE-CREDENTIAL-DECLARED-OPTIONAL` |

두 통과를 다른 문구로 내는 이유는, 같은 문구면 **선언한 노드와 잊은 노드를 구별할 수
없기** 때문이다.

**판정할 수 없으면 통과가 아니다.** 파일 부재는 `-ABSENT`(재조정 유닛이 `-` 접두 없이
요구하는 파일이라 설치가 덜 끝났다는 뜻), 정규 파일이 아니거나 읽을 수 없으면
`-UNREADABLE`. 둘 다 FAIL 이다.

**argv 거부.** `discord_check.py` 는 argparse 로 argv 를 거부할 때 값을 돌려주지 않고
`SystemExit` 를 던진다. `RealExecutor.execute` 의 `except` 는 `BaseException` 을 잡지
않으므로 그대로 트레이스백으로 죽었다. 이제:

```
[FAIL] discord-readiness: USAGE-REFUSED: discord_check.py가 argv를 거부했다 (SystemExit 2) — …
```

**`SystemExit(2)` 와 토큰 부재의 `rc=2` 는 같은 숫자다.** 종료 상태를 판정표에 그대로
넣었다면 "설치기가 만든 명령이 틀렸다"가 "소유자의 토큰이 없다"(WARN)로 둔갑하고 설치는
거짓 이야기 위에서 계속 갔을 것이다. 그래서 이 경로는 판정표를 타지 않고 별도 FAIL 이다.

## 이 프로브가 증명하지 못하는 것

토큰의 **유효성**, Message Content 인텐트, 채널 접근, DM 도달 — 어느 것도 아니다.
게이트웨이가 쓰는 토큰은 agent 홈(0600)에 있어 ops 프로브가 읽을 수 없고, 읽으려면
sudo 권한을 새로 열어야 한다. 그 절반은 소유자가
[install.md](../guide/install.md) §5 의 `discord_check.py` 를 한 번 돌려 닫는다 —
설치 종료 출력의 「소유자 확인 절차」가 그 명령을 그대로 준다.

## 소유자 조치 (배포 후 1회)

카탈로그에 행이 하나 늘면 **허용목록 매니페스트가 한 줄 늘고 래퍼의 입력 지문이 바뀐다.**
그래서 이 릴리스를 받은 노드는 래퍼를 다시 만들어야 하며, 그전까지
`healthcheck probe allowlist matches the checks` 프로브가 드리프트를 보고한다.

```bash
automation/provision-healthcheck-probe.sh      # 노드에서 소유자가 1회
```

멱등이고, 같은 바이트면 아무것도 하지 않는다.
