# 기능 소개 — 캘린더 승인 복구 (실패 전파 + 중복조회 제거)

**완료:** 2026-07-25 · **티켓:** repair `t_3011a5f7` · **스킬:** `calendar`

## 무엇을
캘린더 변경 승인 흐름(워처가 `#approvals`/DM의 소유자 ✅를 감지 → confirm 서브프로세스가 실제 캘린더에 반영)의 **실패 처리·관측성·중복조회**를 견고화한다.

## 왜
이전엔 내부 confirm이 `rc=1`로 실패해도 워처가 stderr를 버리고 `exit 0`으로 끝나 **cron이 "정상"으로 오인** → 승인된 캘린더 변경이 조용히 실행되지 않았다. 또 워처와 confirm이 같은 Discord 메시지·반응을 **중복 조회**해 API rate-limit(429) 위험이 있었다.

## 핵심 동작 (불변식)
- **실패 전파**: confirm 자식 `rc≠0` → 워처도 non-zero 종료 + 원 rc·HTTP 상태·레닭션된 stdout/stderr tail을 구조화 JSON 로그로 보존. 타임아웃·예외·429·5xx·네트워크 오류도 동일한 실패 계약. **정상 tick은 조용한 `exit 0` 유지.**
- **중복조회 제거 + HMAC 일회용 승인**: 워처가 소유자 ✅/⛔·해시를 **한 번만** 검증(⛔ 우선, 소유자 전용) → draft id·hash·DM 채널/메시지·소유자·승인 액션에 바인딩된 **5분 1회용 HMAC 승인 파일**을 자식 confirm에 전달. 자식은 nonce를 원자적으로 소비하고 **Discord 재조회를 하지 않는다**. 복제·위조·다른 draft 재사용은 실행 전 거부.

## 사용 시나리오
1. **(happy)** cha가 캘린더 초안 DM에 ✅ → 워처가 1회 검증 → 일회용 승인으로 confirm → 캘린더 이벤트 **정확히 1회** 생성, 워처 `exit 0`. Discord 반응 조회는 승인당 1회로 축소(429 위험↓).
2. **(실패 가시화)** confirm이 `rc=1` 또는 429로 실패 → 캘린더 변경 실행 안 됨 + 워처 non-zero 종료 + 원인·HTTP 상태 로그 보존 → **cron이 실패를 정확히 인지**(더 이상 조용한 성공 오인 없음).
3. **(보안)** 위조·복제된 승인 파일 → 바인딩 불일치로 **실행 전 거부**. 승인되지 않은 변경은 실행되지 않는다.
