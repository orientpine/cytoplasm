# 승인 한 번으로 끝나는 스킬 배포 (B Wave)

## 무엇을
스킬을 고쳐 PR을 머지하고 배포 요청을 올리면, 소유자가 `#approvals`에서 **✅ 한 번**만 누르는 것으로
마운트까지 끝난다. 그 사이 사람도 세션도 개입하지 않는다.

```
개발 → PR 머지 → (노드 릴리스 자동 수렴, 약 1분) → 배포 요청 → ✅ 한 번 → (2분 내 마운트)
```

## 왜
✅를 누른 뒤에도 누군가 세션에 "승인했어"라고 말해줘야 배포가 끝났다. 승인 여부를 확인하려면
`deploy-skill.sh`를 다시 돌려야 했고, 그때마다 샌드박스·리뷰·peer 증명이 전부 다시 돌며 Discord를
여러 번 두드렸다 — 실제로 `HTTP 429`가 나서 **이미 승인된 스킬의 마운트가 막힌** 적이 있다.
그래서 소유자의 ✅는 늘 잠정적으로 느껴졌고, 밀린 배포가 며칠씩 드리프트로 남았다.

## 어떻게 — 네 겹

**① 리액션만 폴링하는 워처 (⑦)**
2분 주기로 대기 레코드를 열거하고 소유자 결정만 읽는다. 메시지·첨부는 절대 폴링하지 않는다(실시간
에이전트와의 경쟁 소비자 금지). 승인된 건만 기존 파이프라인을 **재개**할 뿐, 워처가 직접 마운트하지
않는다 — 그러면 게이트의 두 번째·약한 사본이 되고, 썩는 쪽은 언제나 둘째다.

**② 이미 실현된 승인은 재실행하지 않는다** → [소개](공급망-승인-재조정.md)
MOUNT는 끝났는데 레코드가 남는 창이 있었다. 그 유령을 매 tick 재배포하면 rate limit이 새 승인까지
막는다. 재조정이 live 심링크와 레코드 digest를 대조해, 이미 마운트된 건은 파이프라인 재실행 없이
기존 CAS로 **회수만** 한다.

**③ 배포되는 바이트는 `origin/main`에만 있다** → [소개](릴리스-배포-provenance.md)
스킬 소스는 root 소유 읽기 전용 릴리스이고, 그 트리 **전체**가 커밋 트리와 바이트 일치해야 한다.
에이전트가 쓴 코드는 origin/main에 없으므로 **구조적으로 배포될 수 없다**.

**④ 워처가 escalate할 수 있는 명령은 하나뿐**
워처는 `agent`로 돌고 그 계정에는 sudo가 없다. `ops`/`peer` 쉘을 주는 대신 절대경로 하나
(`/usr/local/libexec/autophagy-resume-deploy --skill <name>`)만 연다. **발동은 인가가 아니다** —
파이프라인이 소유자 ✅의 digest 바인딩, peer 증명, 아티팩트 digest를 전부 다시 확인한다.

**⑤ 재개가 실패해도 유예일 뿐, 막다른 길이 아니다**
같은 실패를 매 tick 반복하면 rate limit이 새 승인까지 막는다. 그래서 실패한 요청은 유예하되, 실패
지문을 `릴리스 sha:사유`로 잡아둔다 — **릴리스가 바뀐다는 것이 원인이 고쳐졌다는 가장 강한 신호**이므로,
그때는 시계를 기다리지 않고 다음 tick에 곧바로 재시도한다. 같은 릴리스에서만 시계 규칙이 적용된다.
그리고 기다리는 동안에도 매 tick 한 줄을 남긴다 — 침묵은 삭제와 구분되지 않기 때문이다.

## 사용 시나리오

### 정상 경로
1. 스킬을 고치고 PR을 머지한다.
2. 노드 릴리스가 자동 수렴한다(약 1분, 사람 개입 0).
3. `automation/deploy-skill.sh <skill>` — 샌드박스·리뷰·peer 증명까지 돌고 `#approvals`에 요청이 뜬다.
4. cha가 ✅ **한 번**.
5. 2분 내 마운트. 승인 레코드는 CAS로 자동 회수된다.

`readlink /srv/autophagy-skills/live/<skill>` 해시가 승인한 digest로 바뀌면 끝이다.

### 거부·보류 경로
- ⛔ → `settled`. 레코드는 **영구 보존**된다(pending 레코드가 곧 지속적 거부 기록이므로 지우면 같은
  바이트로 다시 물어보게 된다).
- 이미 마운트된 승인 → `hold`. 재배포하지 않는다.
- 승인을 읽을 수 없음(전송 실패·바인딩 불일치) → `retain`. 한 tick 더 기다릴 뿐 아무 일도 하지 않는다.
- `managed-activate`·`skill-publish` → 대기 레코드만으로는 재실행 인자를 알 수 없어 `retain`. 사람이 마저 끝낸다.

### 재개 실패 → 복구 경로
1. 재개가 실패한다(`failed (resume-exit:N)`). 그 요청은 유예된다.
2. 대기 중에도 매 tick 한 줄이 남는다 —
   `[supply-chain-watch] skill-deploy:<skill> backoff (attempt N, retry in Ns)`. 사라진 게 아니라 대기 중임이 보인다.
3. 원인을 고쳐 랜딩하고 노드 릴리스가 수렴한다(약 1분).
4. 다음 tick에 자동 재시도 → 마운트. 사람이 다시 부를 일은 없다.

수렴을 기다릴 여유가 없거나 같은 릴리스에서 급하면 `automation/deploy-skill.sh <skill>`을 직접 한 번
돌린다 — 승인은 이미 있으므로 ③만 수행된다.

## 주의
- **실패 양식이 '성공한 침묵'이다.** `ProtectHome=yes`로 하드닝하거나 게이트 디렉터리가 없으면 매 tick
  0건을 돌려주며 exit 0을 낸다 — `systemctl`로는 건강해 보이는데 ✅는 영원히 안 읽힌다. 그래서
  프로비저너가 6가지 전제조건을 확인하고 하나라도 어긋나면 타이머를 **켜지 않는다**.
- **워처 로그는 저널에 있다.** `journalctl -u autophagy-supply-chain-watch.service`. 운영 계정이
  `systemd-journal` 그룹이어야 보인다.
- 워처는 결정론적 실패를 무한히 재시도하지 않는다 — 유예 중에는 tick당 한 줄만 남기고, 릴리스가
  바뀔 때 곧바로 재시도한다. 로그가 소음이 되지도, 유예가 조용한 삭제처럼 보이지도 않는다.
