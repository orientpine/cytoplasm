# 헬스체크 릴리스 관측성

## 무엇을

헬스체크가 배포 미러 상태와 독립적으로 현재 릴리스 세대를 `origin/main`과 대조하고,
root 권한으로 설치된 릴리스 헬퍼 두 파일이 불변 릴리스 원본과 같은지도 확인한다. 수리 티켓
명령은 단일 builder가 만들며, 15개 체크의 SSH allowlist 원문 manifest를 함께 제공한다.

## 왜

기존 `release-stale` 탐지는 미러가 뒤처졌을 때만 실행되어, 미러만 먼저 당겨진 상태에서는
낡은 프로덕션 릴리스를 놓칠 수 있었다. 또한 root 헬퍼가 릴리스보다 낡아도 수렴 시점까지
발견되지 않았고, 체크 이름이 포함된 수리 명령 15개는 코드와 allowlist가 쉽게 어긋났다.
새 프로브와 byte-exact manifest 대조가 이 세 관측 공백을 닫는다.

## 사용 시나리오

- **정상**: 릴리스 세대가 origin/main과 같고 설치 헬퍼 해시도 릴리스 원본과 같으면 두
  로컬 체크가 PASS한다. `healthcheck_allowlist_manifest.sh --print`는 D1 형태 명령 15줄을
  출력하며 실제 `report_repair()` 경로와 바이트 단위로 일치한다.
- **드리프트**: 헬퍼가 다르면 해당 체크가 FAIL하고, 파일이 없거나 읽을 수 없으면
  `HELPER-DRIFT-UNKNOWN`으로 실패한다. origin이 불통이면 릴리스 비교는
  `BEHIND-UNKNOWN` 경고로 degrade한다.
- **중복 억제**: 같은 tick에서 미러 체크가 이미 `release-stale`를 FAIL로 소유하면 독립
  프로브는 WARN으로 낮아져 사고당 수리 티켓이 하나만 생긴다. 독립 프로브의 enforcement는
  기본 0(WARN)이며 승격은 OWNER 결정이다.

## 관련

- 핵심: `automation/healthcheck.sh`, `automation/checkout_mirror_probe.sh`,
  `automation/release_helper_probe.sh`
- 명령 manifest: `automation/healthcheck_command_builder.sh`,
  `automation/healthcheck_allowlist_manifest.sh`
- 증적: `.omo/evidence/fs2/task-1-parallel-followup-sweep-2.txt`
- 외부효과: 없음. 실제 노드 wrapper 재검증·해시 등록과 enforcement 승격은 OWNER가 수행한다.
