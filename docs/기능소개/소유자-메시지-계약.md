# 소유자 메시지 계약 — 어느 스레드인지 찾으러 다니지 않게

## 무엇을

계약을 채택한 승인·결과·정기 통지는 **대상 / 사실 / 위치 / 인계 / 되돌리기** 다섯 줄로 읽는다.
어디를 봐야 하는지, 내가 할 조치와 에이전트의 다음 실행이 무엇인지 함께 알리고, 없으면 없다고 표시한다.

## 왜

에이전트가 스레드에 올렸다고만 하고 **어느 스레드인지 가리키지 않아 소유자가 직접 찾아야 했다**.
이제 다른 곳에서 받은 통지에도 원래 위치의 링크가 붙고, 좌표를 모르면 추측 링크 대신 검색 안내를 준다.

## 사용 시나리오

1. **정상·폴백**: `<요청 키>`의 결과를 승인 스레드에 보내려다 실패 → 기존 폴백 통지 경로로 배달하면서
   그 목적지에 맞춰 다시 렌더 → 서버·스레드·메시지 좌표가 있는 원 승인 메시지의 **클릭 가능한 링크**를
   소유자가 받아 바로 연다. 같은 스레드 안에서 읽을 때만 위치가 `여기`다(양쪽 채널 좌표가 실제로 같을 때).
2. **서버 미상**: 같은 요청의 서버 좌표가 없는 상태에서 스레드 밖으로 통지 → 링크를 만들지 않고
   생산자가 준 `<검색 라벨> / <요청 키>`를 표시 → 소유자는 그 키로 찾는다. `@me`로 짐작한 DM 링크는 없다.
   원래 위치가 해당 없거나 이 메시지 자체이면 URL 없이 표시하며, 외부 자료 주소는 같은 채널이어도 별개다.
3. **조치 없음**: 추가 조치·실행이 없는 완료 통지를 받음 → 인계에 둘 다 없다고 명시 → 답을 기다리는
   요청으로 오해하지 않는다. 승인 카드의 기한·취소 효과도 함께 읽되, 이미 누른 카드의 삭제·재게시로 바꾸지 않는다.

모든 발신자가 봉투를 만드는 것은 아니다. **영구 구조 예외는 네 곳**이다: 자체 카드 없는 승인 위임,
최소정보 리마인더, 그리고 `origin_notice.deliver`가 폴백 목적지로 다시 렌더한 문자열을 받는
budget·calendar 콜백이다. 두 콜백은 기존 호환 문구도 받고, calendar는 워처·리마인더의 문자열도 받는다.
미이관 원장 `_RAW_CONTENT_EXEMPT`는 실제로 비어 있고 재등록을 막는 가드가 있으며, 네 예외는 별도
`_PERMANENT_RAW_CONTENT_EXEMPT`에 사유와 함께 남는다. 새 미이관 발신자를 영구 예외 옆에 숨기지 않기 위한 분리다.
파사드의 **`content: str` 경로는 유지**한다. 이 경계들과 구 런타임 호환이 남아 있고, 봉투를 import할 수 없는
회의 게이트웨이의 별도 접수 통지도 문자열을 쓴다. 문자열 전송을 없애 회의 통지를 끊는 변경이 아니다.
