# 메모리 재배치 (memory relocate, Phase 2)

## 무엇을

메모리 큐레이터가 `OPS_REFERENCE`로 분류한 **운영 사실**(LiteLLM 포트·gws scope·CLI 경로·mailon sync 절차 같은 인프라 사실)을 소유자 승인(✅) 후 **Obsidian 운영-참조 노트로 재배치**하고, RAG 인제스트가 검증되면 그 항목을 자체 메모리(MEMORY.md)에서 **삭제**해 공간을 회수한다. 별도 패키지 `automation/memory_relocate/`(큐레이터는 순수 제안자로 유지 — boundary test가 강제).

## 왜

메모리 큐레이터는 durable 판단(원칙/선호)만 트윈으로 승격·삭제한다. 그런데 MEMORY.md의 **80%는 인프라/운영 사실**이라 승격 대상이 아니고 완전 중복도 없어 구조적으로 못 줄인다("60자밖에 안 줄어듦"). 이 운영 사실들은 트윈(규범 판단)도 아니고 그냥 두기엔 캡을 잡아먹는다 — recall(검색)로 찾을 수 있는 **Obsidian 참조 노트**가 제자리다. 재배치는 그 사실을 무손실로 Obsidian에 옮기고(provenance: observed / authority: reference — 실행 권위 아님), 검증 후 네이티브에서 지워 캡 여유를 실질적으로 확보한다.

## 사용 시나리오

- **happy(자율)**: 노드의 `memory-relocate-watch` cron(30분, no-agent)이 **스스로** 진행한다 — 진행 중인 건이 없으면 자체 메모리를 분류해 가장 크게 회수되는 `OPS_REFERENCE` 항목을 골라 제안하고(→`relocations.json`에 `proposed` + OBSIDIAN_WRITE 바인딩 + composite action_hash) → **오너-DM 승인 메시지**를 게시(원문·목적지·확보 글자수·"승인 시 삭제, 이후 recall로만" 명시) → cha가 ✅ → 다음 틱이 Obsidian에 노트를 쓰고(원격 read-back 해시 검증) → RAG 인제스트(10분 주기) 확인 → **5-게이트** 통과 시 그 항목 하나를 백업 후 삭제 → `reconciled`. 사람이 개입하는 지점은 **✅ 하나뿐**이다.
- **승인 채널 바인딩**: 승인 DM을 게시한 순간 레코드는 message_id와 **게시된 채널**을 함께 영속한다(둘 중 하나라도 비면 전이 거부). 채널이 바인딩되지 않은 레코드는 조회 자체를 하지 않고 pending으로 두며, 결코 "메시지 없음"으로 해석하지 않는다(fail-closed) — 승인 DM이 고아가 되거나 소유자의 ✅가 폐기되지 않는다.
- **자율 경계**: 노드가 스스로 하는 것은 *분류·제안*까지다(외부효과 아님). 쓰기·삭제는 전부 소유자 승인 뒤에만 일어나므로 무인 틱이 데이터를 바꾸는 일은 없다. 동시에 1건만 진행해 승인 DM이 몰리지 않으며, 분류기(LLM) 실패 시 상태를 건드리지 않고 다음 틱에 재시도한다. `USER.md`는 v1에서 후보가 아니고, 이미 처리된 항목은 다시 제안하지 않는다.
- **거부/대기**: cha가 ⛔ → `abandoned`(원본 그대로). 승인 메시지가 사라지면 재게시(삭제 없음). 게시 실패·write 실패·RAG 미인제스트·게이트 블록은 모두 다음 틱 재시도이며 **네이티브는 절대 손대지 않는다**.
- **안전(5-게이트)**: 삭제는 `apply_relocation`의 다섯 관문을 **순서대로 모두** 통과할 때만 `delete_entry`(큐레이터의 단일 삭제 경로)로 실행된다 — ① 소유자 ✅ + composite action_hash 미변경, ② Obsidian 노트 존재(쓰기 원격 검증됨), ③ RAG 인제스트 확인, ④ 네이티브 snapshot digest 일치, ⑤ 정확히 한 항목. 하나라도 불확실하면 no-op·재시도. **USER.md(신원·스타일)는 v1에서 재배치 대상이 아니다.**
- **운영 조회**: `cd ~/.hermes/... && python3 -m memory_relocate.cli state show`는 원문·message_id를 가린 상태(상태별 건수 + 목적지 + 확보 글자수)를 출력. `propose --entry-file F [--dry-run]`은 제안 레코드를 만든다(Discord 게시·삭제 없음).

## 관련

- 코드: `automation/memory_relocate/`(model·store·binding·plan·render·rag_verify·approval_gate·apply·propose·watch_step·effects_live·cli) + `cron/memory_relocate_watch.py`(no-agent 리액션 워처)
- 재사용: Obsidian 승인형 쓰기(`automation/obsidian_write` write_note+PARA plan), 승인 라이프사이클(`automation/interop/approval_*`, ApprovalKind.OBSIDIAN_WRITE=오너 DM), RAG 인제스트 상태(`automation/rag_ingest`), 큐레이터 삭제(`automation/memory_curator/deletion.delete_entry`)·digest(`binding.entry_digest`)
- 승인은 위키/메일/과제비 게이트와 동일한 producer 패턴(ApprovalGate Protocol + `request_owner_approval`) — `test_approval_lifecycle_conformance`가 등록·단일성을 강제. 삭제는 5-게이트 뒤 단일 경로.
- 배포: 워처는 ops 체크아웃에서 실행(automation.memory_relocate/obsidian_write/interop를 repo root에서 import), `deploy.sh`가 provenance 검사 → ops ff-pull → 워처 배포 → 리액션 cron 등록.
