# 게이트웨이 런타임 드리프트 탐지

## 무엇을
게이트웨이가 **지금 도는 코드**와 **디스크의 벤더 소스**가 어긋났는지, 그리고 agent·peer 두 계정이 **같은 소스**를 싣고 있는지를 기계로 판정한다. 탐지 전용이며 재시동·재적용은 하지 않는다.

## 왜
2026-08-18, 벤더 자체 업데이트가 소스를 갈아끼우고도 게이트웨이를 재시동하지 않아 프로세스가 **옛 코드 + 새 파일** 상태로 20시간 돌았다. 유닛은 내내 `active/running`이었고 Discord 연결도 살아 있어서, `systemctl is-active`나 연결성에 기대는 프로브는 이 장애를 **원리적으로** 통과시킨다. 소유자는 자기 요청이 두 번 실패한 뒤에야 알았다. 같은 날 agent(v0.20.1)와 peer(v0.18.2)의 벤더가 갈라져 있었는데, 각자 자기 코드끼리는 일관돼 갈라짐 자체도 아무 신호를 내지 않았다 — 「게이트웨이 재시동 규칙」이 두 계정을 쌍으로 다루는 전제가 이미 깨져 있었다.

## 사용 시나리오
**드리프트 발견(happy path)** — 게이트웨이 기동 시각을 넘겨 판정한다.
```
python3 -m automation.hermes_compat.gateway_runtime_probe \
  --install-root ~/.hermes/hermes-agent --started-at 2026-08-18T03:00:00Z --json
```
→ `{"verdict": 1, "readings": [{"check": "staleness", "state": "STALE", ...}]}` · 종료코드 **1**. 이때 할 일은 「게이트웨이 재시동 규칙」대로 agent·peer **쌍** 재시동이다.

**계정 갈라짐** — `--peer-install-root` 를 함께 주면 두 계정의 소스 지문을 대조한다. 다르면 `DIVERGED` + 종료코드 1. mtime이 달라도 내용이 같으면 `CONVERGED` 다.

**판정 불가(실패 경로)** — 기동 시각을 안 주거나 소스를 못 읽으면 `UNKNOWN` + 종료코드 **2**. 판정 불가가 어긋남보다 높다 — "읽을 수 없었다"를 "괜찮다"로 보고하면 사고가 다음 요청까지 잠복하기 때문이다.

## 관련
- 구현 `automation/hermes_compat/gateway_runtime_probe.py` · 회귀 `tests/unit/test_hermes_compat_gateway_runtime_probe.py`
- 형제 프로브 `automation/hermes_compat/patch_state.py`(무패치 구동 탐지) — 같은 탐지 전용 계약과 종료코드 규약을 쓴다.
- 재적용·재시동은 **외부효과**라 소유자 원장 소관이다: `docs/qa/FS4/triage-ledger.md` 의 L118·L120 항목.
