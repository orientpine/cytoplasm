# 정기 작업을 Hermes cron 에서 사용자 타이머로 (P2 첫 묶음 + N1, 바로 전환)

**무엇을** — no-agent 정기 작업을 Hermes cron 대신 노드 계정의 systemd 사용자 타이머가 띄운다. 스크립트는 그대로이고, 띄우는 주체만 바뀐다. 이번 릴리스는 첫 묶음 7개다: `rag-ingest-watch`·`stt-eval-capture`·`voice-catalog-enroll`·`daily-cost-report`·`selfskill-audit-watch`(agent)·`doctor-watch`(agent)·`mail-triage-repair-daily`(N1, 새 no-agent 워처).

**폐기(2026-10-19)** — 위 목록은 최초 이관 기록이다. 소유자 "이것도 이제 없애라",
"이거 아예 삭제해 litellm" 결정으로 `daily-cost-report`는 제거되어 더 이상 등록·복구하지 않는다.
이후 메모리 예약 둘·알림 폴러와 `research-trends`도 은퇴해 현재 선언된 agent 잡은 28개다.
주간 연구 보고서와 키워드는 별도 연구 에이전트 공도리 채널에서 요청한다
([노드 예약 은퇴](주간-연구동향-노드-예약-은퇴.md), [비용 보고 제거](litellm-지우기.md)).

**바로 전환(2026-10-18 08:10 KST 형 "바로 전환 해줘")** — 하루 관찰 없이 agent 계정의 남은 no-agent 잡 24개(반응 워처·발송 루프·Discord 로 출력하는 잡 포함)도 같은 방식으로 옮겼다. peer 계정 잡(doctor·selfskill-audit·memory-relocate-peer)만 peer 퇴역 때까지 Hermes 에 남는다. 남은 FS3 고정 등록 줄(budget·notes-weekly-organize·메일 다이제스트·트리아지)은 Hermes 잡 정의를 계속 맞추고(되돌리기용) 그 뒤에 타이머가 그 잡을 일시정지한다. `research-trends` 등록 줄은 이후 은퇴해 재생성하지 않는다.

**왜** — 오토파지를 도리 기반으로 옮기며 Hermes 를 퇴역시키는 계획(형 결정 Q216·Q219, 목표 "이 서버에서 오토파지 에이전트 피어 옵스 모두 없애고 사이토플라즘 기능 100프로")의 P2 단계다. 그리고 10/02 노드에 손으로 넣었던 에이전트 모드 잡 `mail-triage-repair-daily` 는 저장소에 코드도 선언도 없어 릴리스가 관리하지 못했다(N1).

## 어떻게 동작하나

- 선언 한 줄: 각 배포기 옆 `deploy-manifest.txt` 의 `v2:cron` 행에 `runner=systemd` 를 붙인다(기본 `hermes` — 붙이지 않은 행과 다른 설치자는 예전과 같다). `deliver=local` 잡은 출력이 journal 에만 남고, `deliver=discord` 잡은 러너가 Hermes 와 같이 비어 있지 않은 출력을 Hermes 홈 채널(`~/.hermes/.env` 의 `DISCORD_HOME_CHANNEL_THREAD_ID` → `DISCORD_HOME_CHANNEL`)로 보낸다 — 침묵 표식(`[SILENT]`)은 보내지 않고, 실패하면 「⚠️ 정기 작업 '<이름>' 실패(종료코드 N)」 한 줄을 보낸다. 출력은 `~/.hermes/cron-timers/output/<이름>/` 에 최근 20개까지 남는다.
- 배포기는 `converge_timer`(`automation/deploy_timer.sh`)를 부르고, 노드 릴리스 트리의 `automation/cron_timer.py` 가 계정 안에서 맞춘다:
  1. 같은 이름의 Hermes 잡을 **일시정지하고 목록을 다시 읽어 paused 를 확인**한다(지우지 않는다).
  2. 그다음에야 `~/.config/systemd/user/autophagy-cron-<이름>.{service,timer}` 를 쓰고 타이머를 켠다. 첫 실행은 다음 달력 시각이다.
  3. 목록을 읽지 못하면 아무것도 바꾸지 않는다(rc 4). 일시정지가 먹지 않으면 타이머를 켜지 않는다(rc 5).
- 시각은 Hermes 설정의 시간대(`timezone: Asia/Seoul`)로 읽어 `OnCalendar=*-*-* 09:00:00 Asia/Seoul` 처럼 적는다. 그래서 08:00·09:00 KST 잡은 같은 시각에 돈다.
- 러너 `automation/cron_timer_run.py` 는 매 틱마다 `~/.hermes/cron/jobs.json` 을 본다. 같은 이름 Hermes 잡이 active 면 돌지 않고 `CRON-TIMER-SKIP` 만 남긴다 — 누가 Hermes 잡을 손으로 다시 켜도 두 번 돌지 않는다. 결과는 `~/.hermes/cron-timers/<이름>.json`(마지막 상태·연속 실패, 오류는 종료코드만)에 남는다.
- doctor 「정기 작업」 줄: 옮긴 잡의 Hermes 쪽 일시정지는 중지로 세지 않고, 타이머의 연속 실패는 Hermes 잡처럼 판정한다. 타이머가 꺼졌는데 Hermes 잡도 멈춰 있으면 "아무도 돌리지 않는다"로 FAIL 이다. 은퇴한 잡(`automation/retired_jobs.py` 의 `JOBS`)이 Hermes 목록에 일시정지로 남은 것과, 한 번만 돌고 끝난(`completed`) 잡은 고장·확인으로 세지 않는다.
- 릴리스 판정(`deploy_all.sh --verify`)은 그 행을 계정 안 `cron_timer check-declared` 로 본다(유닛 내용·타이머 켜짐·Hermes paused). 어긋나면 소유 배포기를 다시 돌린다.

## 사용 시나리오

- **형이 느끼는 것(정상)**: 매시 doctor 등 유지하는 작업은 예전과 같은 시각에 실행된다. 노드에서 `systemctl --user list-timers`에 현재 선언된 타이머가 보인다. 폐기된 09:00 지출 보고는 오지 않는다.
- **N1**: 09:10 KST 에 지난번 이후의 다이제스트 분류 실패·`(요약 실패)`·`DIGEST-FAIL stage=… code=…`·트리아지 워처 실패를 종류마다 `repair_cli.py manual "!repair 메일 다이제스트 점검: …"` 한 번으로 올린다. 메일 제목·주소·본문은 티켓에 넣지 않는다. 같은 종류가 다시 나면 같은 카드의 재발로 센다. 없으면 `없음`.
- **되돌리기**: `python3 -m automation.cron_timer revert --name <이름>`(계정 안, 릴리스 트리에서) — 타이머를 먼저 끄고, 이 수렴기가 멈춘 Hermes 잡만 resume 한다(남이 멈춘 잡은 그대로). 다음 릴리스에서 그 행의 `runner=systemd` 를 빼고 배포기를 `converge_cron` 으로 돌려 놓는다.
- **거부**: `local`·`discord` 밖의 전달을 `runner=systemd` 에 붙이면 선언 파싱이 막는다. 보낼 Discord 토큰·홈 채널이 없으면 그 실행은 실패로 남는다(조용히 버리지 않음). 날짜와 요일을 함께 정한 cron, 60을 나누지 않는 `every 7m` 처럼 달력으로 같은 뜻이 안 되는 주기도 막는다.
