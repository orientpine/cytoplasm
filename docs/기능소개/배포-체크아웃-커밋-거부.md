# 배포 체크아웃 커밋 거부 (deploy-checkout commit refusal)

## 무엇을

노드의 배포 체크아웃 `/srv/autophagy-agents`에 **모든 커밋을 무조건 거부하는 pre-commit 훅**을
설치한다. 동시에, 그래도 드리프트가 생기면 헬스체크가 내는 수리 티켓이 **비파괴 복구 절차를
본문에 싣고** 나간다.

## 왜

배포 체크아웃은 `origin/main`의 **단방향 거울**이다 — 허용된 쓰기는 `git fetch`와
`git pull --ff-only`뿐이다(루트 `AGENTS.md`「ops 체크아웃 단방향 규칙」). 그런데 사람도
에이전트도 그 안에서 그냥 커밋해 왔고, 그때마다 두 가지가 동시에 깨졌다.

1. **조용한 유실** — prod가 git에 없는 코드를 돌리다가, 다음에 누군가 깨끗한 체크아웃에서
   배포하면 아무 신호 없이 되돌아간다.
2. **시끄러운 정지** — 체크아웃이 origin보다 앞서면 `git pull --ff-only`가 막혀, 배포 파이프라인이
   모든 세션에서 선다.

2026-07-27에 실제로 발생했다(`skills/mail/SKILL.md` v1.5.3→1.5.5, 4개 커밋 회수). 규칙을 문서에
적는 것만으로는 재발을 막지 못한다 — 사고를 낸 주체는 언제나 그 문서를 읽지 않은 쪽이다.

## 사용 시나리오

**거부 경로 (기본 동작).** 에이전트나 사람이 노드에서 배포된 스킬을 고치고 그 자리에서 커밋한다:

```
$ git commit -m "learned in prod: ..."
[pre-commit] REFUSED — this is the ops deploy checkout, not a place to commit.
  ... 워크스테이션에서 커밋 → push → 여기서 git pull --ff-only 안내 ...
  ... 이미 여기 작업이 있다면 format-patch → am 으로 옮기라는 비파괴 절차 안내 ...
(exit 1)
```

커밋은 생기지 않고 HEAD는 그대로다. **막힌 작업은 파괴되지 않는다** — 스테이지에 그대로 남으므로
안내대로 워크스테이션으로 옮기면 된다. `--amend`도 같은 이유로 거부된다.

**허용 경로.** `git pull --ff-only`는 아무 영향을 받지 않는다. ff-merge는 커밋을 만들지 않으므로
pre-commit이 애초에 발동하지 않는다. 배포는 평소대로 "워크스테이션에서 커밋 → push → 노드에서
ff-pull"로 진행한다.

**탐지 경로 (2중 방어).** `git commit --no-verify`로 훅을 우회하면 구조적 거부는 뚫린다. 그때는
헬스체크의 `checkout_mirrors_origin` 프로브가 잡아 수리 티켓을 낸다. 이 티켓은 이제 체크 이름만
싣지 않고 **`format-patch` → `am` 복구 절차와 "`reset --hard` 금지"를 함께** 보낸다 — 반사적인
수리(버리고 정렬)가 공교롭게도 유일본 커밋을 파괴하는 조치이기 때문이다.
