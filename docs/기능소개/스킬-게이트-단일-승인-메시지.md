# 스킬 배포·발행 승인 — 단일 라이브 승인

## 무엇을
스킬 배포 게이트(`skill_gate`, 4단계 SANDBOX→REVIEW→owner ✅→MOUNT)와 관리형 스킬 발행
게이트(`skill_gate_publish`)의 `#approvals` 요청을 공유 승인 생명주기
(`request_owner_approval`)로 게시한다. 승인 키(`skill-deploy:{skill}` /
`skill-publish:{skill}`)마다 **살아 있는 요청은 항상 1건**이고, 저장된 `message_id`는
**덮어써지지 않는다** — 옛 메시지를 지운 뒤에만 교체된다.

## 왜
두 게이트 모두 pending 레코드를 무조건 다시 썼다. 그래서:
- **배포**: 같은 스킬을 다른 hash로 요청하면 레코드의 `message_id`가 조용히 교체되고,
  옛 메시지는 `#approvals`에 그대로 남았다. cha가 그 고아 메시지에 ✅를 눌러도
  아무 일도 일어나지 않는다(그 id를 소비할 코드가 없다).
- **발행**: 가드가 아예 없어서, 같은 릴리스를 두 번 요청하면 매번 새 메시지가 올라가고
  cha는 어느 것이 유효한지 알 수 없었다.
- 게이트에는 리액션 워처가 없다 — `check`가 방금 올린 요청의 stdout에서 `--message-id`를
  받으므로, 교체된 레코드의 옛 메시지는 영원히 소비되지 않는다.

## 사용 시나리오

### 정상 경로
1. `automation/deploy-skill.sh <skill>` → 샌드박스·리뷰 통과 후 `#approvals`에 요청 1건.
2. 같은 스킬·같은 hash로 재실행 → **아무것도 올라가지 않는다.** 기존 메시지 id와 nonce를
   그대로 다시 출력하므로 peer attestation·`check`가 이어서 진행된다.
3. 스킬을 고쳐 hash가 바뀌면 → 옛 메시지를 **먼저 지운 뒤** 새 요청을 올린다(고아 없음).
4. `--fresh` → 우회가 아니라 교체다. 기존 메시지를 지우고 새로 올린다.
5. 승인 메시지가 사라졌으면 → 고아 레코드를 풀고 다시 올려 재바인딩한다.
6. cha의 ✅는 유지됐지만 **peer attestation만 30분 TTL을 넘겼으면** → owner 메시지와 nonce를
   그대로 두고 peer가 같은 hash·nonce·action·destination을 다시 검증해 새 증명을 게시한다.
   새 owner 승인 요청이나 `approval-abandons.jsonl` 만료 이벤트는 만들지 않는다.
7. 발행(`publish-request`)도 동일 — 같은 `sha256 + manifest_sha256 + tag`면 재게시하지 않는다.

### 실패·거부 경로 (모두 **exit 6** + stderr `reason=<토큰>`, 기존 메시지는 보존)
- cha가 이미 ✅/⛔를 누른 뒤 내용이 바뀌면 → `owner-decided`로 연기. 그 승인은 지우지 않는다.
  peer refresh도 현재 owner 반응과 전체 실행 바인딩이 다시 검증된 경우에만 허용된다.
- 요청 본문이 저장된 레코드와 다르면 → `binding-mismatch`로 거부(삭제·해제 없음).
- pending 레코드가 손상/불완전하면 → `store-unreadable`로 거부. 건너뛰면 "미결 없음"으로
  읽혀 중복 게시가 되므로 fail-closed.
- Discord를 읽지 못하면 → `unverifiable`로 연기. 증명 못 한 생존은 생존으로 친다.
- 다른 프로세스가 같은 키의 lease를 쥐고 있으면 → `lease-held`로 연기.

**exit 6은 exit 3과 다르다.** exit 3은 여전히 "자동 제안 주 3회 상한"만을 뜻하며,
`deploy-skill.sh`도 두 코드를 각각 다른 메시지로 번역한다.
