# 공급망 승인 재조정 (B-4)

## 무엇을
공급망 워처(⑦)가 승인된 배포를 재개하기 **직전에**, 그 승인의 효과가 이미 실현됐는지 먼저 판정한다.
이미 마운트된 건은 파이프라인을 다시 돌리지 않고 게이트의 기존 compare-and-swap(`consume`)으로 **회수만** 하고,
아직 실현되지 않은 건만 실제로 재개한다. 확인이 안 되면 아무것도 하지 않고 다음 tick으로 미룬다.

## 왜
MOUNT까지 끝났는데 승인 레코드가 pending에 남는 창이 실재했다. `deploy-skill.sh`가 권한 install 성공 후
`hermes_lists_skill` 검증과 invoke smoke를 **거친 뒤에야** `consume`을 불렀기 때문에, 그 사이에 중단되면
효과는 실현됐는데 레코드만 살아남는다. 게다가 `consume`의 `record-absent`/`record-superseded`는 양성(benign)
처리라 exit 0이므로 `CONSUME-WARN`조차 찍히지 않는다 — **조용한 생존**이다.

이 유령 레코드를 워처가 매 tick 다시 집으면 두 가지가 겹친다. 이미 마운트된 것을 재배포해봐야 얻는 게 없고,
그 재실행이 Discord rate limit을 태워 **새 승인의 정상 실행까지 막는다**(실측: 승인 5건 연속 확인 중 `HTTP 429`로
이미 승인된 wiki 마운트가 fail-closed 차단). 반대로 레코드를 그냥 지우는 것도 답이 아니다 —
`supply_chain_plan.py`의 계약대로 *pending 레코드가 곧 지속적 거부 기록*이라, 지우면 같은 바이트로 새 요청이
올라가 소유자에게 이미 내린 결정을 다시 묻게 된다.

## 사용 시나리오

### 정상 경로 — 아직 실현되지 않은 승인
1. cha가 개인 서버 `#approvals`에서 배포 요청 메시지에 ✅.
2. 워처 tick이 리액션을 읽어 계획 `resume`을 만든다.
3. 재조정 판정: live 심링크가 아직 그 digest가 아님 → `run`.
4. `deploy-skill.sh`가 재개되어 MOUNT → `consume`으로 레코드 퇴장. **세션 개입 0회.**

### 이미 실현된 승인 — 재실행 대신 회수
1. 앞선 실행이 MOUNT까지 끝냈으나 검증 단계에서 중단돼 레코드가 남았다.
2. 다음 tick의 재조정 판정: `live/<skill>` → `releases/<skill>/<레코드의 digest>`가 **정확히 일치**하고,
   승인도 여전히 `APPROVED`.
3. → `retire-done`. 파이프라인을 **돌리지 않고** 기존 CAS `consume`으로만 회수한다.

### 거부·불확실 경로
- 소유자가 ⛔ → 계획이 `settled`라 재조정을 **아예 호출하지 않는다**. 닫힌 건에 Discord 왕복을 쓰지 않으며,
  레코드는 영구 보존된다(계획 B-3).
- 게이트를 못 읽거나, 심링크가 심링크가 아니거나, 승인 바인딩이 어긋나거나, 재조정 자체가 예외를 던지면
  → 전부 `hold` → tick 결과 `retain`. **한 tick 더 기다릴 뿐 아무 부수효과도 없다.**

## 주의
- **재조정은 기본값 없는 필수 인자다.** `watch_tick(..., reconcile=...)`에 기본값을 주면 호출자가 조용히
  검사를 빠뜨려 재실행 버그를 되살릴 수 있다. 구조적으로 불가능하게 만들었다.
- **삭제 경로를 새로 만들지 않았다.** 재조정 모듈에는 직접 `unlink`/쓰기가 없고 `abandon`도 부르지 않는다
  (`abandon`은 `SUDO_USER`를 권한자로 기록하는 운영자 전용 탈출구다). 유일한 mutation은 기존 `consume` CAS다.
- 창 자체도 좁혔다: `consume`을 권한 install **직후**로 옮겨, 사후 검증 단계가 실패해도 승인이 먼저 회수된다.
  `consume` 실패는 여전히 마운트를 되돌리지 않는다(`CONSUME-WARN` 경고만 — R4 계약 유지).
