01 / 개인 AI 에이전트 시스템

autophagy-agents

승인 없는 외부 발송 0건 · 특허 민감 콘텐츠 GLM 호출 0건

개인 메모리(RAG·위키)와 팀 보고 허브, 에이전트간 조율 프로토콜, 승인 기반 외부효과, 자가수리(Autophagy) 루프를 갖춘 개인 AI 에이전트 시스템이다.

이름의 뜻 — Autophagy(자가포식)는 자가수리 루프를 가리킨다. 오류를 스스로 티켓화하고, 진단·패치·샌드박스 검증을 거친 뒤 소유자 승인을 받아 고친다.

구동 위치는 설치별 노드다 — <primary-node>가 프로덕션 에이전트 런타임을, <rag-node>가 개인 RAG를 맡는다. 소유자와는 Discord DM에서 한국어로 대화하고, 다른 연구자들의 에이전트와는 각자 소유·각자 키·각자 인프라로 운영하며 공개 규약과 온보딩 킷으로만 결합한다.

02 / 불변식

중심 불변식 — 모든 외부효과는 승인 게이트를 지난다

모든 외부효과(메일 발송·캘린더 변경·예산·배포·위키 저장)는 소유자(cha) 승인 게이트를 경유한다. fail-closed — 설정·권한·확인이 불가능하면 실행하지 않는다.

이 문장 하나가 시스템 전체의 모양을 결정한다. 에이전트는 자기 판단으로 바깥 세계를 바꾸지 않는다. 도구 호출은 아래 여덟 단계를 통과해야만 실제 효과가 된다.

Agent tool call

에이전트가 도구를 호출한다. 이 시점까지는 아직 아무 효과도 일어나지 않았다.

external-effect denylist match

도구 이름과 정렬된 JSON 인자를 denylist와 대조한다. 매칭이 없으면 읽기로 보고 그대로 통과시킨다.

deterministic target_id + action_hash

대상 식별자와 요청 내용의 SHA-256 해시를 결정론적으로 만든다. nonce를 넣지 않으므로 같은 요청은 언제나 같은 해시가 된다.

owner approval request

소유자에게 승인 요청 메시지를 게시한다. 동일한 논리 요청에 살아 있는 메시지는 항상 1건뿐이다.

owner reaction (✅ or ⛔)

소유자가 ✅ 승인 또는 ⛔ 거부를 누른다. 워처는 메시지 본문이 아니라 리액션만 폴링한다.

binding verification

그 리액션이 그 해시·그 대상·그 소유자·그 채널에 실제로 묶여 있는지 다시 검증한다.

only ✅ + matching hash + owner identity

세 조건이 동시에 성립할 때에만 승인으로 인정한다. 하나라도 어긋나면 승인이 아니다.

effect execution

그제서야 메일이 나가고 일정이 바뀌고 스킬이 마운트된다.

어느 단계에서든 승인·해시·소유자·채널·attestation을 검증할 수 없으면 실행하지 않고 DEFER, REFUSE, 또는 approval_required로 종료한다.

03 / 승인 게이트

직접 눌러보는 승인 게이트

여기서부터는 읽는 사람이 cha다. 아래는 실제 승인 요청과 같은 모양의 예시 DM이다. ✅ 승인 또는 ⛔ 거부를 직접 눌러보면, 게이트가 무엇을 검증하고 어디서 멈추는지 판정 패널과 13단계 레일이 함께 움직인다.

두 개의 토글은 게이트가 승인을 거절하는 실제 조건 두 가지를 재현한다 — 승인 뒤에 내용이 바뀐 경우(해시 불일치)와, 소유자가 아닌 사람이나 봇이 리액션한 경우다. 켜 둔 채로 ✅ 승인을 눌러보면 결과가 달라진다.

이 시뮬레이터는 페이지 안에서만 동작한다. 메일은 발송되지 않고 어떤 외부효과도 일어나지 않는다.

개인 에이전트 → 소유자 DM 승인 필요 예시

수신: 세미나 간사 (예시 · 주소 마스킹됨)

이 초안은 소유자가 ✅ 승인을 누르기 전까지 어디에도 전송되지 않는다.

action_hash: sha256:ab12cd34… target_id: tool:gws_mail_send:mail.send channel: approvals · method: manual_reaction

대기 중 — 소유자 리액션을 기다립니다

요청은 게시되었고 해시에 묶인 채 멈춰 있다. 소유자의 리액션이 오기 전까지 게이트는 아무 효과도 실행하지 않는다. 위에서 ✅ 승인 또는 ⛔ 거부를 눌러보라.

승인 요청 생명주기 — 13단계

request_owner_approval · automation/interop/approval_lifecycle.py — 승인 메시지를 게시하기까지 게이트가 지나는 임계구역 전체다. 위에서 누른 결과에 따라 어디까지 진행되고 어디서 멈추는지가 아래 레일에 표시된다.

  1. 01 LEASE_ACQUIRE key lease 획득. 실패 시 DEFERRED / LEASE_HELD
  2. 02 POSTING_JOURNAL_CHECK 이전 게시가 commit 전 중단됐는지 확인. 남아 있으면 REFUSED / POSTING_JOURNAL_STALE
  3. 03 OUTSTANDING_LOAD 같은 logical key의 기존 요청 로드. 읽기 실패면 REFUSED / STORE_UNREADABLE
  4. 04 PROBE_EXISTING_REQUESTS 각 요청을 6종으로 분류: BOUND_PENDING / APPROVED / CANCELLED / MISSING / BINDING_MISMATCH / UNVERIFIABLE
  5. 05 RESPECT_OWNER_DECISION 이미 소유자가 결정한 건은 삭제하지 않고 DEFERRED / OWNER_DECIDED — 워처에게 양보
  6. 06 REFUSE_BINDING_MISMATCH 바인딩 불일치는 삭제하지 않고 REFUSED / BINDING_MISMATCH
  7. 07 CLEAN_MISSING Discord 메시지가 실제로 없는 건만 record drop
  8. 08 REUSE_BOUND_PENDING 동일 hash pending이 있으면 가장 오래된 것을 canonical로 재사용, 중복 정리 후 PENDING / DUPLICATE_COLLAPSED
  9. 09 SUPERSEDE_CONTENT_CHANGED 다른 hash pending은 기존 메시지를 먼저 삭제한 뒤 record drop
  10. 10 JOURNAL_RESERVE 게시 전 (key, action_hash, created_at)를 저널에 예약
  11. 11 POST_APPROVAL_MESSAGE 소유자 승인 메시지 게시. 저장된 message_id는 절대 조용히 덮어쓰지 않음
  12. 12 COMMIT_APPROVAL_RECORD message/channel 정보를 승인 record로 commit
  13. 13 JOURNAL_CLEAR 저널 clear 후 Outcome.POSTED

호출 판정 — evaluate_tool_call

automation/interop/external_effect_gate.py

  1. _matching_rule — 도구 이름과 정렬된 JSON 인자를 configs/external-effect-tools.yaml denylist와 매칭한다. 매칭이 없으면 external_effect=False, allowed=True — 읽기는 그대로 통과한다.
  2. target_id 생성 — tool:{rule_id}:{tool_name} 형태로 대상을 고정한다.
  3. action_hash 생성 — canonical payload {action, arguments, target_id, tool_name}를 키 정렬·compact JSON으로 직렬화해 SHA-256을 취하고 sha256:<hex>로 만든다. nonce는 포함하지 않는다 — 그래서 같은 요청은 언제나 같은 해시가 되고, 내용이 바뀌면 해시도 바뀐다.
  4. _has_valid_approval — approval log에서 아래 7가지를 모두 만족하는 레코드가 있어야 승인으로 인정한다.
  • action == external_effect.approval
  • hash 일치
  • target_id 일치
  • result.status == approved
  • channel == approvals
  • owner_id 일치
  • method == manual_reaction

일치하면 allowed=True / reason=approved, 아니면 allowed=False / reason=approval_required가 된다.

주의: evaluate_tool_call은 실행기가 아니라 경계에서 허용·차단 판정만 반환한다.

소유자 리액션 워처 — resolve_owner_decision

승인 요청이 게시된 뒤, 소유자의 리액션을 실제 효과로 바꾸는 쪽이다. 네 단계로 끝난다.

  1. WATCH_LEASE_ACQUIRE — 워처 lease를 잡는다. 실패하면 SKIPPED / LEASE_HELD로 물러난다.
  2. REACTION_PROBE — 승인 메시지에서 결정 상태를 판독한다. 워처가 보는 것은 리액션뿐이며 메시지 본문·첨부는 실시간 에이전트가 단독으로 소유한다.
  3. WAITING — BOUND_PENDING / MISSING / BINDING_MISMATCH / UNVERIFIABLE이면 아무 효과도 실행하지 않는다.
  4. CONSUME_DECISION — APPROVED 또는 CANCELLED일 때만 watcher.apply()를 실행하고 record를 drop해 CONSUMED로 종료한다.

✅ 승인 / ⛔ 거부 규칙

  • ✅ 는 승인·확정·실행, ⛔ 는 거부·취소를 뜻한다.
  • ⛔ 우선 — 둘 다 붙어 있으면 취소로 처리한다. 외부효과에 대한 fail-safe다.
  • 소유자 리액션만 유효 — reactor id == owner_id AND bot == false. 다른 사람이나 봇이 누른 리액션은 무시한다.
  • hash 바인딩 필수 + fail-closed — 리액션이 그 요청의 해시에 묶여 있음을 확인할 수 없으면 실행하지 않는다.

04 / 스킬

17개 스킬 — 에이전트가 실제로 할 수 있는 일

스킬은 이 에이전트의 능력 목록이다. 메일·캘린더·할 일·위키처럼 바깥 세계를 건드리는 스킬은 예외 없이 소유자 승인 게이트를 지난다 — 초안을 먼저 보여주고, 소유자가 ✅ 를 누른 뒤에야 실제 효과가 실행된다. 나머지는 읽기·개인 저장소 쓰기만 하므로 승인 없이 즉시 답한다.

05 / 배포

스킬은 4개의 관문을 통과해야 프로덕션에 닿는다

새 스킬은 만들었다고 곧바로 돌지 않는다. 격리 샌드박스 실행 → 결정론적 보안 리뷰 → 승인 요청 → 루트 설치까지 네 단계를 모두 통과해야만 프로덕션에 마운트된다. 세 번째 관문에서는 소유자(cha)의 ✅ 와 독립 피어 봇의 attestation이 둘 다 있어야 하며, 하나라도 없으면 그대로 멈춘다.

  • HOME을 일회용 디렉터리로 교체하고 dummy secret만 사용
  • peer가 agent secrets를 못 읽는지 isolation probe

하나라도 실패하면 SANDBOX-BLOCK exit 2 — 승인 단계에 진입조차 하지 못한다.

판정 원칙 — 커밋됨 ≠ 배포됨. 배포 판정은 readlink /srv/autophagy-skills/live/<skill> 해시.

06 / 인프라

두 대의 노드, 세 개의 계정

시스템은 설치별 노드에서 역할을 갈라 돈다. <primary-node>은 프로덕션이자 에이전트 런타임이고, <rag-node>는 개인 RAG 전용이다. 한 노드 안에서도 권한은 agent · peer · ops 세 계정으로 격리된다 — peer는 스킬 배포를 독립적으로 검토·증언하는 주체이고, ops는 게이트웨이·수집기와 읽기 전용 거울을 쥔다. 아래 각 항목에 마우스를 올리거나 키보드로 포커스하면 계정과 포트가 보인다.

<primary-node> 프로덕션 / 에이전트 런타임
<rag-node> 개인 RAG · ops 계정 단독, Hermes 게이트웨이 없음

healthcheck가 보는 항목

  • <primary-node> — LiteLLM · agent gateway · peer gateway · report-hub collector · report-hub dashboard · dashboard auth · checkout mirrors origin/main · skill mounts match release
  • <rag-node> — embedding · Qdrant · MCP

헬스체크는 읽기 전용이다. 실패는 repair 스킬이 민감정보를 지운 Kanban 수리 티켓으로 남기고, 자동 수리는 사람 검토 전까지 실행되지 않는다.

신뢰성 레이어 — 사고가 만든 다섯 개의 층

DG · 배포 안정성

"커밋됨 ≠ 배포됨"을 구조로 강제하는 층. 프로덕션이 git에 없는 코드를 돌거나, 낡은 체크아웃이 최신 결정을 조용히 되돌리는 사고에서 나왔다.

  • DG-1A 체크아웃 지연 감지 — 배포 체크아웃이 origin/main과 어긋나면 헬스체크가 잡아 수리 티켓을 낸다.
  • DG-1B 단일 랜딩 명령 — push → 노드 런타임 수렴 → 사후 검증을 한 명령으로 묶어, 방금 push한 sha가 실제로 돌기 전까지 종결하지 않는다.
  • DG-1C 스킬 ABI 가드 — 스킬 인터페이스가 어긋난 채 마운트되는 것을 막는다.
  • DG-2 배포 스냅샷 핀 — 배포 시점의 소스를 고정해 나중에 무엇이 나갔는지 되짚을 수 있게 한다.
  • DG-3·5 불변 런타임 릴리스 — 프로덕션이 실행하는 코드를 읽기 전용 릴리스 트리로 옮겼다. 상주 체크아웃이 배포 재료이자 런타임이던 이중 역할을 끊는다.
  • DG-6 랜딩 계약 이중화 — 릴리스 모드와 폴백 모드에서 랜딩의 사후조건을 각각 다르게 강제한다.
  • B-6 봉인 릴리스 provenance — 봉인된 릴리스가 어느 커밋에서 왔는지 증적을 남긴다.

08 / 설계 원칙

이 시스템이 지키는 열 가지

기능보다 먼저 정해진 것들이다. 대부분은 실제 사고 뒤에 규칙으로 굳었고, 산문이 아니라 코드 가드와 테스트로 강제된다.

01

모든 외부효과는 소유자 승인 게이트 경유

메일 발송·캘린더 변경·예산 요청·스킬 배포·위키 저장 — 바깥 세상을 건드리는 모든 동작은 게이트를 지난다. 직접 실행 경로는 존재하지 않는다.

02

fail-closed

설정을 읽을 수 없거나, 권한이 모호하거나, 상태를 검증할 수 없으면 실행하지 않는다. 확신이 없을 때의 기본값은 언제나 "안 함"이다.

03

커밋됨 ≠ 배포됨

git에 있다는 사실은 프로덕션에서 돈다는 뜻이 아니다. 배포 판정은 언제나 라이브 심링크의 해시 — readlink /srv/autophagy-skills/live/<skill>.

04

상태 마킹은 성공 이후

claim → 작업 → 성공했을 때만 processed 기록. 실패하면 lease를 놓아 다음 틱이 다시 집게 한다. 미리 마킹하면 실패가 조용히 삼켜진다.

05

stdlib 전용 지향

Python 3.12 표준 라이브러리 중심. from __future__ import annotations, @dataclass(frozen=True, slots=True), 엄격 타입. 외부 의존은 함수 내부 lazy import + fail-closed 가드로 격리한다.

06

추적 config = 불변 시드

런타임 상태는 체크아웃 밖에만 쓴다. 추적 파일을 런타임에 고치면 배포 체크아웃이 dirty해져 다음 git pull --ff-only가 막히고, 모든 세션의 배포가 선다.

07

ops 체크아웃은 단방향 거울

노드의 배포 체크아웃은 origin/main을 받기만 한다. 그 안에서 만든 커밋은 origin에 도달하지 못해 유실되므로, pre-commit 훅이 모든 커밋을 무조건 거부한다.

08

배포 provenance

origin/main에 있는 바이트만 배포된다. 미커밋·미푸시·뒤처진 체크아웃에서의 배포는 DEPLOY-BLOCK으로 중단된다. 디렉터리를 통째로 보낼 때는 untracked 파일까지 검사한다.

09

승인 메시지 단일성

같은 논리적 요청에 살아 있는 승인 메시지는 항상 1건. 중복 게시도, 저장된 message_id를 조용히 덮어쓰는 것도 금지 — 소유자가 누른 ✅가 고아가 되기 때문이다.

10

산문이 아니라 코드가 진실

문서에 적어 두는 것만으로는 부족하다. 도메인이 겹치는 스킬의 mutating 경로에는 결정론적 코드 가드가 양방향으로 있어야 하고, conformance 테스트가 그것을 기계적으로 강제한다.

09 / 안티패턴

무엇을 하지 않는가

금지 목록은 취향이 아니라 사고 기록이다. 아래 여섯 가지는 각각 실제로 무언가를 망가뜨린 뒤에 규칙이 되었다.

cron 워처가 Discord 메시지·첨부를 폴링

실시간 에이전트가 메시지와 첨부를 단독으로 소비하는데 cron까지 폴링하면 두 소비자가 같은 이벤트를 읽는다. 결과는 메시지 중복 처리, race condition, 승인 메시지와 일반 대화의 오인, 이미 처리한 초안의 재실행.

그래서 워처는 "사람이 기존 승인 메시지에 남긴 리액션"이라는 좁고 안정적인 신호만 읽는다.

자식 subprocess에 자격증명 미전파

no-agent cron은 시크릿을 os.environ에 넣지 않는다. 자식 프로세스를 띄울 때 env=로 명시 전달하지 않으면, 파일은 디스크에 멀쩡히 있는데 런타임에서만 "키 없음"으로 실패한다.

채널·기능별 병렬 confirm 워처 신설

승인 표면이 하나 늘 때마다 render·resolve·cron을 새로 만들면 게이트가 갈라진다. 승인 채널은 레코드에 바인딩된 channel_id 필드로만 달라지고, 절차는 기존 게이트 하나를 재사용한다.

SKILL.md 라우팅에만 의존

도메인이 겹치는 스킬에서 산문 라우팅만 두면 LLM이 두 경로를 동시에 발동한다. 실제 사고: peer-test 오전 10시 한 줄이 캘린더와 조율 양쪽에 서로 다른 시각으로 이중 등록됐다. 이제 공유 판정 함수가 양쪽 CLI를 함께 강제한다.

토큰 모양 문자열을 주석·문서에까지 사용

secret-scan은 문맥을 보지 않는다. 예시로 적어 둔 토큰 모양 문자열 하나가 오탐을 일으켜 배포 전체를 막는다. 실제 값이 아니어도 쓰지 않는다.

프로덕션 게이트웨이에 테스트 모드 플래그

테스트용 우회 플래그가 프로덕션에 들어오면 승인 게이트가 무력화된다. production guard가 그 조합을 발견하면 부팅 자체를 거부한다 — 실행 중 조용히 안전하지 않은 상태가 되는 것보다 낫다.
