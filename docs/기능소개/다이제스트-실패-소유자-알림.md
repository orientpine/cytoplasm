# 다이제스트 실패 시 소유자 알림 — 구조화 마커 + owner-DM 전달

**완료:** 2026-07-31 · **티켓:** repair `t_7707ebfd` · **스킬:** `mail`

## 무엇을

매일 08:00 KST 기관메일 다이제스트(`mail-daily-digest` cron)가 **어떤 이유로든 실패하면 소유자(cha)에게 반드시 알림이 도달**하도록 고쳤다. 실패는 이제 자유문장이 아니라 한 줄짜리 구조화 마커 `DIGEST-FAIL stage=<build|deliver|runner> retry_safe=<true|false> code=<...>`로 표면화되고(주소·본문·토큰 마스킹), cron은 그 마커를 owner DM으로 전달한다.

## 왜

2026-07-31 아침 다이제스트가 소유자 DM에 도착하지 않았다. 7번째 항목의 `glm-main` 분류가 180초 timeout으로 실패해 다이제스트 전체가 전송 이전 단계에서 중단됐는데, **소유자는 그 실패를 전혀 통보받지 못했다**. 원인은 두 가지였다:

1. cron이 `--deliver local`로 등록돼 있었다 — Hermes에서 `local`은 "전달 대상 0개(출력 파일에만 저장)"라, 워처가 만든 실패 알림이 아무 데도 가지 않았다.
2. 워처의 인틱 재시도가 producer가 더 이상 내지 않는 자유문장(`digest DM 발송 실패`)에 걸려 있어 계약이 이미 깨져 있었다.

## 어떻게 (구조)

- **producer**(`triage_digest.run_digest`): 빌드 단계(분류/요약 LLM 실패)와 전달 단계(owner DM 실패) 두 경계를 각각 `stage=build code=llm_call_failed` / `stage=deliver code=discord_delivery_failed` 한 줄 마커로 감싼다. `detail=`은 redact 후 개행 제거·길이 제한. 둘 다 `retry_safe=false`(빌드 항목이 이미 캘린더 초안을 위임했을 수 있고, 전달은 일부 Discord 청크가 이미 나갔을 수 있어 재전송이 소유자 중복을 만든다).
- **cursor 불변식 유지**: run 기록은 여전히 DM 성공 후에만 원자적으로 이뤄지고, 실패는 `record_digest_run` 이전에 raise한다 — 실패 시 cursor 미전진(재시도 안전).
- **watcher**(`mail_digest_watch.py`): 모든 실패를 한 줄 마커로 **stdout**에 낸다(Hermes `--no-agent`는 stdout만 전달, stderr는 버림 — 성공=빈 stdout=무음). 자식 마커는 그대로 통과시키고, 마커가 없으면(크래시·비마커 종료·미마운트) `stage=runner`로 합성한다. 인틱 재시도는 `retry_safe=true` 마커에만 발동한다.
- **cron**(`deploy.sh`): `--deliver local` → `--deliver discord`로 바꾸고, 기존 등록 job은 `hermes cron edit <job_id>`로 제자리 수렴한다.

## 사용 시나리오

- **소유자 관점(정상)**: 변화 없음. 08:00에 다이제스트 DM을 받고, 실패가 없으면 아무 알림도 없다(무음 틱).
- **소유자 관점(실패)**: 다이제스트가 실패하면 이제 `DIGEST-FAIL stage=... code=...` 한 줄이 owner DM으로 도착한다 — 07-31처럼 조용히 사라지지 않는다. 마커에는 메일 주소·본문·긴 숫자가 마스킹되어 없다.
- **실패/거부 경로**: 전달 실패(`retry_safe=false`)는 소유자에게 중복 DM을 만들지 않으려 재전송하지 않는다. name-resolution류 `retry_safe=true` 마커만 20/60/120초 인틱 재시도 후, 그래도 실패하면 한 번 알린다. Discord 전체 장애 시에는 즉시 알림 성공은 보장할 수 없고 cron이 `last_status=error`로 기록한다.
