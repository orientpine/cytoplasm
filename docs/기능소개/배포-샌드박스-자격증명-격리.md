# 배포 샌드박스 자격증명 격리 — 테스트 승인이 진짜 DM을 열지 않게

**완료:** 2026-08-01 · **웨이브:** NF-1 · **대상:** `deploy-skill.sh` · `mail` · `automation/interop`

## 무엇을

스킬을 배포할 때마다 두 번씩 찍히던 이 줄을 없앴다.

```
NOTIFY-FAIL draft=<id> err=Discord request failed: POST /users/@me/channels
```

세 곳을 고쳤다. ① 메일 발송 완료 DM은 이제 **소유자 리액션 승인일 때만** 나간다(주입·테스트 승인은 `NOTIFY-SKIP`으로 거부). ② 배포 샌드박스 시나리오는 **일회용 HOME**에서 돌아 계정의 `~/.env.secrets`에 손이 닿지 않는다. ③ Discord 요청 실패 메시지가 **원인 종류와 HTTP 상태**를 남긴다.

## 왜

세 개가 겹쳐 있었다.

**(1) 테스트 승인이 실제 외부효과를 냈다.** `skills/mail/scripts/scenario.sh` §9는 조작된 소유자 id `<synthetic-owner-id>`로 서명 주입 승인을 만들어 `confirm`을 돌린다. 그런데 `cmd_confirm`은 승인 방식과 무관하게 무조건 완료 DM을 시도했다 — 즉 배포 stage 1(peer 계정)과 post-mount smoke(agent 계정)가 매번 진짜 Discord에 DM 채널 개설을 요청했다.

**(2) `env -i`는 자격증명을 격리하지 못했다.** `bot_token()`은 환경변수가 없으면 `~/.env.secrets` **파일을 읽는 폴백**을 갖는다. 배포는 실제 계정 HOME을 그대로 넘겼으므로, 샌드박스가 **프로덕션 봇 토큰으로 인증**했다. `skills/AGENTS.md`의 "실시크릿 미주입"과 `deploy-skill.sh` 헤더의 "DUMMY secrets only (env -i isolation)"는 둘 다 사실이 아니었다.

**(3) 에러가 자기 원인을 지웠다.** `approval_directory._request`가 모든 예외를 `Discord request failed: {method} {path}` 한 줄로 뭉갰다. 그래서 **토큰이 없어 네트워크 호출조차 없었던 경우**와 **실제 HTTP 실패**가 완전히 같은 문자열을 냈다. 로그만 보면 "Discord POST가 실패한다"로 읽히지만 전자는 POST 자체가 없었다. 이 결함이 2026-07-26부터 원인 불명으로 남아 있던 이유다.

프로덕션은 멀쩡했다. 실측하면 진짜 소유자 id로는 DM 채널이 200으로 열리고, 시나리오의 가짜 id만 `400 {"code":50033,"message":"Invalid Recipient(s)"}`를 받는다 — 과거 기록의 "HTTP 400"의 정체가 이것이었다.

## 어떻게 (구조)

- **승인 출처 allowlist** (`triage_cli._notify_sent`): `_DM_NOTIFIABLE_METHODS = {"manual_reaction"}`. 목록에 없으면 — 앞으로 추가될 승인 방식 포함 — `NOTIFY-SKIP`을 stderr에 남기고 반환한다(fail-closed). 가드를 `dm_owner`가 아니라 CLI에 둔 이유는, 취소 알림(`dm_owner("메일 발송 취소됨")`)이 승인 출처를 갖지 않는 정당한 호출자이기 때문이다. `E2E_TEST_MODE` 환경변수 게이팅은 검토 후 기각했다 — 주변 환경에 의존하면 새 승인 방식에 대해 fail-closed가 아니다.
- **일회용 HOME** (`deploy-skill.sh` stage 1 · post-mount smoke): `env -i` **바깥**에서 `mktemp -d` + `chmod 700`으로 만들고 `trap`으로 지운다(`env -i`가 `TMPDIR`를 지우므로 순서가 중요하다). 시나리오 스크립트 경로는 여전히 실제 HOME에서 찾는다. `INTEROP_RUNTIME`은 존재를 검증한 뒤 명시 전달하고, 없으면 조용히 저하되지 않고 `SANDBOX-HOME-BLOCK`(exit 90)으로 크게 실패한다.
- **원인 보존** (`approval_directory._request`): `cause=<예외 타입>` + `HTTPError`일 때만 `http_status=<정수>`를 붙인다. `str(error)`·`repr`·URL·reason·헤더·본문은 **의도적으로 제외** — `api`는 주입된 콜러블이라 그 예외 문자열을 신뢰할 수 없다. `raise ... from error` 체이닝은 유지하고, 메시지는 120자 미만으로 두어 호출부의 `redact(...)[:120]`이 진단을 잘라내지 못하게 했다.

## 사용 시나리오

- **소유자 관점(정상)**: 변화 없음. 메일 발송이 ✅로 승인되면 `✉️ 발송 완료 …` DM이 그대로 온다.
- **소유자 관점(배포)**: `automation/deploy-skill.sh mail`을 돌리면 이제 `NOTIFY-FAIL` 대신 `NOTIFY-SKIP draft=… reason=signed_injection_e2e` 한 줄이 보이고, 시나리오는 `leg=signed-confirm`으로 그대로 통과한다. 정상 동작임을 알리는 표식이지 오류가 아니다.
- **실패 경로**: 배포 노드에 `~/.hermes/interop_runtime`이 없으면 stage 1이 `SANDBOX-HOME-BLOCK interop runtime missing`으로 **중단**한다. 조용히 통과시키면 mail·calendar·budget·wiki 네 스킬이 `SCENARIO-PASS`를 찍으면서도 서명 승인 구간 검증을 잃기 때문에, 일부러 시끄럽게 실패시킨다.
- **진단**: Discord 경계 실패가 나면 이제 `cause=GateError`(자격증명 등 로컬 문제, 호출 없음)와 `cause=HTTPError http_status=401`(실제 원격 실패)이 구분된다.
