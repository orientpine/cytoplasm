# 반복 수렴 스킵·repair cron 실패 관측

## 무엇을

릴리스 리컨실러가 같은 이유로 수렴을 건너뛰는 상태를 연속 집계하고, 기존 실패 임계치에
도달하면 기존 소유자 알림 경로로 드리프트를 한 번 보고한다. repair-report consumer cron은
예외를 마스킹해 기록하되 이제 실패 종료코드를 반환한다.

## 왜

업데이트 신뢰 거부, 업데이트 대상 미해결, 채널 바인딩 실패는 모두 상태 저장 전에 정상
종료되어 같은 문제가 계속돼도 실패 횟수가 늘지 않았다. 끝나지 않는 롤백도 별도 통지 없이
반복될 수 있었고, repair cron은 내부 예외가 나도 스케줄러에 성공으로 보였다.

## 사용 시나리오

- **정상 경로**: 일시적인 대상 조회 실패 한 번은 조용히 다음 틱을 기다린다. 같은 사유가
  `FAILURE_NOTICE_THRESHOLD`만큼 연속되면 기존 `notify_owner` 경로로 드리프트를 한 번 알리고,
  정상 수렴 뒤에는 기존 복구 알림과 함께 상태를 초기화한다.
- **실패 경로**: repair-report consumer가 예외를 내면 상세 메시지는 노출하지 않고 예외 종류만
  stderr에 남긴 뒤 non-zero로 종료한다. 큐 항목은 성공 처리되지 않아 다음 스케줄이 재시도한다.
- **allowlist 변경**: healthcheck `LIVE_CHECKS`가 바뀌면 모든 항목과 synthetic 항목 하나에서
  매니페스트가 파생된다. 커밋된 매니페스트가 다르면 검사가 즉시 실패한다.
