# 반복 수렴 스킵·repair cron 실패 관측

## 무엇을

릴리스 리컨실러가 같은 이유로 수렴을 건너뛰는 상태를 집계하고 기존 소유자 알림 경로로
한 번만 보고한다. 특히 `origin/main`에 서명 태그가 없으면 첫 2분 tick에 정확한 remote SHA,
현재 runtime SHA, 복구 명령을 즉시 알린다. repair-report consumer cron은 예외를 마스킹해
기록하되 이제 실패 종료코드를 반환한다.

## 왜

업데이트 신뢰 거부, 업데이트 대상 미해결, 채널 바인딩 실패는 모두 상태 저장 전에 정상
종료되어 같은 문제가 계속돼도 실패 횟수가 늘지 않았다. 끝나지 않는 롤백도 별도 통지 없이
반복될 수 있었고, repair cron은 내부 예외가 나도 스케줄러에 성공으로 보였다. 이후 태그 없는
머지가 세 차례 재발했고 기존 통지는 세 tick 뒤 `origin/main: unresolved`로 와서 조치가
늦었다. 서명은 계속 사람의 명시적 릴리스 선언으로 남기되 누락 탐지만 기억에서 분리했다.

## 사용 시나리오

- **서명 태그 누락**: `UNSIGNED-HEAD`가 확인되면 read-only `git ls-remote`로 raw
  `origin/main`을 다시 읽어 `unsigned:<sha>` incident key로 즉시 알린다. 같은 SHA의 후속 tick은
  침묵하고, SHA가 다시 바뀌면 새 알림을 한 건 보낸다. 전송 실패는 기존 `pending_notice`에
  남겨 다음 tick에 재시도한다.
- **다른 스킵**: 일시적인 대상 조회 실패 한 번은 조용히 다음 tick을 기다린다. 같은 사유가
  `FAILURE_NOTICE_THRESHOLD`만큼 연속되면 기존 `notify_owner` 경로로 한 번 알린다.
- **복구**: 신뢰 가능한 태그가 생겨 정상 수렴하면 기존 복구 알림과 함께 상태를 초기화한다.
- **안전 경계**: raw SHA는 알림 문구와 중복 억제 key에만 쓰고 설치 대상으로 사용하지 않는다.
  서명키는 로컬 유지보수 워크스테이션에만 남으며 CI·노드 자동 서명은 하지 않는다.
- **실패 경로**: repair-report consumer가 예외를 내면 상세 메시지는 노출하지 않고 예외 종류만
  stderr에 남긴 뒤 non-zero로 종료한다. 큐 항목은 성공 처리되지 않아 다음 스케줄이 재시도한다.
- **allowlist 변경**: healthcheck `LIVE_CHECKS`가 바뀌면 모든 항목과 synthetic 항목 하나에서
  매니페스트가 파생된다. 커밋된 매니페스트가 다르면 검사가 즉시 실패한다.

## 라이브 검증

`v1.0.75@d215e92f`를 먼저 배포한 뒤 docs-only PR #260을 태그 없이
`0884af67`로 머지했다. 첫 timer tick에서 state가 곧바로
`notified_target=unsigned:0884af67…`, `consecutive_failures=1`,
`pending_notice=null`이 됐고 runtime은 `d215e92f`에 남았다. 2분 간격 세 tick을 더
기다린 뒤에도 incident key는 하나, pending notice는 없고 실패 횟수만 4가 됐다. 즉 Discord
전송은 성공했고 같은 SHA를 중복 통지하거나 서명 없는 코드를 설치하지 않았다. 통지는 exact
remote/runtime SHA와 `automation/release-tag.sh --wait`를 담는다.

## 개정 (2026-08-30, VA-3)

unsigned `origin/main`의 sha별 1회 즉시 통지는 폐지됐다 — 머지=축적 체제에서 그 상태는
릴리스 사이의 **정상**이다. 대신 백로그가 3일을 넘기면 "미배포 커밋 N건 · X일 경과 ·
`automation/release.sh` 안내" 다이제스트를 기간당 1건 보내고, 릴리스가 착지하면
리셋한다. 스킵 사유별 임계 통지·durable pending 재시도 등 나머지 규율은 그대로다.
상세: [머지=축적과 릴리스 백로그 다이제스트](머지-축적과-릴리스-백로그-다이제스트.md).

## 개정 (2026-09-03, 미러 동결 구분)

08-29 부터 관측 미러가 미커밋 편집으로 3일간 동결됐을 때 리컨실러는 release-backlog 경로만
탔고(연속 실패 162회, 사고 미개시), 다이제스트는 "릴리스를 실행하세요" 만 반복했다. 릴리스는
사실 밀린 적이 없었다. 이미 관측하고 있던 `mirror_state` 를 unsigned-head 경로에 넘겨 문구가
둘을 구분한다 — dirty/ahead 면 미러가 origin/main 을 따라갈 수 없다고 말하고 비파괴 복구
(`git format-patch` → 개발 체크아웃에서 적용 → commit/push, `reset --hard` 금지)를 안내하며,
behind 면 릴리스 뒤 자동으로 따라간다고 적어 사람 손을 부르지 않는다. 상태는 `state.json` 에
additive 로만 저장하고, 문구와 미러 로직은 `deploy_reconcile_backlog`/`_mirror` 로 갈라 사고
시계를 250 LOC 안에 둔다.

## 개정 (2026-09-11, 대상과 다음 행동)

드리프트·릴리스 백로그·헬스체크 전이 통지는 이제 소유자 메시지 봉투의 다섯 필드로
보낸다. 대상은 관측한 커밋·차단 사유·체크 이름이고, 소유자가 할 일과 자동화가 다음에
할 일을 구분한다. 커밋·체크 이름만 있으면 검색 키로 안내하며 Discord 링크를 추측하지 않는다.

- **백로그**: 기존 3일 임계에 도달하면 `owner`에 워크스테이션의 `automation/release.sh`
  실행·소유자 ✅ 1회를, `agent_next`에 서명된 릴리스 수렴과 미러 안전 판정 유지를 싣는다.
  dirty/ahead 미러는 먼저 패치로 작업을 옮기는 비파괴 복구 안내도 유지한다.
- **드리프트·차단**: 원인 확인은 소유자의 행동, 자동 재시도는 다음 행동으로 표시한다.
  재시작·포인터 수정을 통한 임의 복구는 안내하지 않는다. 회복 통지는 소유자 조치 없음이다.
- **헬스체크**: 새 실패·회복 체크를 구분하고 원인 확인 전 변경 금지를 명시한다.
  이미 열린 사건의 반복 실패는 여전히 무통지이며 다음 스윕은 계속 관측한다.
- **시간·재시도**: 새 수렴 통지는 기존에 계산한 시작·현재 시각을 `Periodic`으로 싣는다.
  회복과 시각을 저장하지 않는 헬스체크는 관측 완료 `Result`다. 문자열뿐인 기존 큐의 재전송도
  원래 관측 종료 시각을 만들지 않고 `Result`로 보낸다(배포 성공을 뜻하지 않는다).
- **호환·실패**: `deploy_reconcile_notice`가 기존 durable 문자열 형식을 읽는다. 지원하지
  않는 옛 형식·봉투 import 불가·파사드 capability 부재는 기존 원문 바이트로 전달한다.
  전송 실패는 기존 큐/다음 스윕으로 재시도한다. 저장 형식·콜백 계약·600초 드리프트·3회 실패·
  3일 백로그 임계·에피소드 경계·미러 판정·승인 게이트는 바꾸지 않았다.
