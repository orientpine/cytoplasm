# 게이트웨이 없이 다이제스트 반응 처리

## 무엇을 · 왜
Hermes 게이트웨이를 멈춰도 다이제스트 카드의 전문·회신 초안 반응을 읽는다.
기존 2분 전체 틱만 남기면 반응이 늦어지므로, agent 사용자 타이머
`mail-digest-reactions`가 `every 20s`로 반응만 확인한다. 전체 틱은 그대로다.

## 사용 시나리오
- 카드의 전문 반응을 누르면 다음 스캔에서 기존 경로가 전문 스레드를 열고 카드 아래 링크를 남긴다.
  회신 초안 반응은 기존 초안·승인 카드만 만들며 발송은 승인 카드에서 따로 결정한다.
- 최근 3일 카드만 틱당 최대 20장을 순환 조회한다. 보통 다음 20초 틱에서 시작하지만,
  카드가 20장보다 많으면 여러 틱에 걸리고 모델이 초안을 쓰는 동안도 지연될 수 있다.
  게이트웨이 이벤트·20초 스캔·2분 틱이 겹쳐도 SQLite의 카드·동작별 claim으로 한 번만 실행한다.
- 429가 나면 공용 REST 클라이언트의 제한된 재시도 뒤 스캔을 중단한다.
  Retry-After(최소 20초)를 로컬 상태에 기록해 다음 틱도 쉬며 타이머 실패로 세지 않는다.
  소유자 이외 반응과 3일 지난 카드는 실행하지 않는다.

## 비용 · 배포
기본 조회 예산은 20초당 카드 GET 최대 20회(초당 평균 1회),
다른 사람이 반응한 카드에만 이모지별 사용자 조회 최대 2회가 추가된다.
공용 클라이언트의 429 재시도와 실제 전문 게시·초안 생성 요청은 별도다.
같은 타이머의 겹침은 기존 `cron_timer_run` 잡별 잠금이 막고, 직접 경량 호출도
DB 옆 `.reaction-scan.lock`으로 겹치지 않는다. 커서는 `.reaction-scan.json`에 보관한다.

`skills/mail/deploy-manifest.txt`의 `v2:cron;runner=systemd` 선언을
기존 `skills/mail/deploy.sh`가 수렴한다. 새 root 작업이나 노드 수동 설정은 없다.
고정 진입점 `mail_digest_reactions_watch.py`와
`mail_triage_watch.py --digest-reactions-only`가 같은 반응 전용 CLI를 호출한다.
