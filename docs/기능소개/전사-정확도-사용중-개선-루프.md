# 전사 정확도 사용 중 개선 루프

## 무엇을

녹음에서 얻은 전사 가설과 소유자가 고친 정답을 비공개 평가 루트에 모아, 같은 녹음에서
인식·화자 분리·정렬 후보를 비교한다. 단어 시각으로 화자를 먼저 배정하고 문장을 조립하며,
근거 없는 발화나 겹친 발화는 `화자0`으로 표시한다. **평가 보고는 자동 모델 교체가 아니다.**

## 왜

문장 전체에 화자 하나를 붙이면 발화 경계가 긴 문장에 묻힌다. 앞 문장의 화자를 근거 없이
물려주면 미상 발화도 확정처럼 보인다. 또한 원음·실행 조건·교정본이 연결되지 않으면
모델을 바꿔 좋아졌는지 재현해서 판단할 수 없다. 이제 오디오 SHA와 설정 지문으로 비교 대상을
묶고, 원문은 체크아웃 밖에 두며 보고에는 마스킹된 지표만 남긴다.

## 사용 시나리오

1. **평소처럼 사용한다.** 감시 Drive 폴더의 회의 녹음 또는 Plaud 녹음을 로컬로 전사한다.
   단어 시각과 화자 turn의 지지로 배정한 뒤 같은 판정끼리 문장을 만든다. 미상·겹침의 `화자0`은
   사람 이름으로 승격하지 않는다. 화자 분리 자체가 실패하면 전사는 화자 없이 계속한다.
2. **교정이 정답으로 쌓인다.** 소유자가 전사본을 고치면 별도 no-agent 수집 워처가 기존 Drive·
   Obsidian 미러를 읽어 교정본을 모은다. 원본·동결 노트는 고치지 않고 Discord 메시지도 폴링하지 않는다.
   Plaud 노트를 vault에 쓰는 기존 소유자 승인 경계는 그대로다.
3. **비교한 뒤 사람이 채택한다.** 저장소 루트에서 아래 명령으로 자료 유무와 후보를 확인한다.
   `run --configs`는 GPU 유휴 판정과 공유 파이프라인 잠금 뒤 순차 실행하며, 비교 보고는
   CER·화자 순열 CER·DER·개체 지표와 쌍대 비교의 불확실성을 보여 준다. 표본이 부족하면
   채택을 확정하지 않는다. `run --self-test`는 임시 참조 검산이지 소유자 정답을 대체하지 않는다.

```bash
python3 -m automation.stt_eval status --root <private-evaluation-root> --json
python3 -m automation.stt_eval run --root <private-evaluation-root> --configs configs/stt-eval/candidates-asr.json
python3 -m automation.stt_eval compare --root <private-evaluation-root> --a <baseline-label> --b <candidate-label> --json
```

**실패·거부도 결과다.** 빈 상태는 `no records`, 체크아웃 안 평가 루트는
`STT-EVAL-ROOT-REFUSED`로 거부한다. 화자 분리·정렬 실패는 진단을 남기고 기존 전사·토큰 시각을
보존한다. `SPEECHTOTEXT_WHISPER_DTW`의 `--dtw`, pyannote 분리, WhisperX 정렬은 모두
명시 옵트인이다. 인식 조건이 바뀌면 창 캐시 지문도 바뀌어 옛 창을 새 조건의 결과로 쓰지 않는다.

Plaud 원음은 `DRIVE_PUBLISH_ENABLED=1`일 때만 owner-only Drive 보관을 시도한다. 공용 파사드의
검증과 SHA 원장 기록이 끝나야 로컬 파일을 지울 수 있고, 실패하면 원본을 보존한다. 꺼져 있으면
기존 삭제 정책이 유지된다. 평가 원장·정답·가설은 `STT_EVAL_ROOT`(기본 `~/.hermes/stt-eval`)에 둔다.
회의 워처는 내려받은 원본을 기존 `ffprobe` 경로로 측정해 원장에 밀리초 길이를 적는다.
측정 실패는 전사를 막지 않고 `duration_ms=0`(미상)으로 기록한다. CPU-only 상한
`STT_ENGINES_CPU_MAX_MS`가 설정되면 상한 초과와 미상 녹음의 분리·정렬 후보를 모두
건너뛰되 ASR은 계속한다. CUDA 복구 시 변수를 지우면 기존처럼 길이와 무관하게 실행한다.

**2026-09-22 정정**: `run` 이 내려받은 원음을 `audio.bin` 으로 CLI 에 넘겨, CLI 의 형식 게이트가 모든 후보를 rc=5(`지원하지 않는 형식`)로 거부했다 — 그때까지 후보 비교는 가설을 하나도 만들지 못했다. 이제 러너가 머리 바이트(`OggS`·`fLaC`·`ID3`·`ftyp`·`WAVE` 등)로 확장자를 붙여 넘기고, 모르는 형식은 그대로 두어 CLI 가 판정한다. 바이트는 바뀌지 않으므로 원장의 오디오 SHA 도 그대로다.
