# 설치 마법사·프로필 (INSTALL-TUI)

## 무엇을

`python3 -m automation.install.wizard`는 처음 설치하는 운영자에게 노드 값을 묻고
`node.toml`을 작성한 뒤, 한국어 계획 요약·확인·실제 설치·결과 안내로 이어준다.
프로필로 헬스체크 범위를 정하므로 새 설치자가 설치 뒤 선언을 따로 추측할 필요가 없다.

## 왜

기존 `quickstart.sh`는 안전한 실행 순서는 지켜줬지만 config를 손으로 고치는 일과
감시할 서비스 묶음을 고르는 일은 운영자에게 남겼다. 마법사는 그 입력만 돕는다.
**설치 로직은 여전히 기존 설치기 하나가 소유**하고, 계획 요약도 고정 건수가 아니라
실제 dry-run 출력에서 집계한다. 수동 설치와 다른 설치 규칙이 생기지 않는다.

## 사용 시나리오

### 정상 흐름 — 내 노드의 첫 설치

1. 소유자가 릴리스 번들의 공개키와 별도 경로로 받은 공지 지문을 준비하고
   [빠른 시작 §4](../guide/quickstart-install.md#4-실행할-한-줄)의 명령을 터미널에서 실행한다.
2. 전제 확인 뒤 `core` 프로필·공개 origin URL·자기 호스트 이름·운영자 계정·공지 지문에
   답한다. config는 기본 `~/.config/autophagy/node.toml`에 생긴다. 기존 `--config` 파일이
   있으면 편집하지 않고 재사용하며, 공지 지문은 `--expect-update-trust-fingerprint`로 줄 수 있다.
3. root 없이 만든 계획과 한국어 요약을 읽는다. `--dry-run-only`면 여기서 rc 0으로 끝난다.
   이것은 **전제 검사가 모두 통과했다는 뜻이 아니다**. config·계획 로그도 이미 남아 있다.
4. `yes`를 입력하면 같은 설치기 인자에서 `--dry-run`만 뺀 실제 설치로 간다. 비-root일 때만
   sudo를 붙이고, `DISCORD_BOT_TOKEN`이 환경에 있으면 그 변수의 보존을 시도한다.
5. 외부 전제까지 갖춰 종료 게이트가 통과하면 rc 0과 다음 행동을 받는다. 실패하면 설치기
   종료코드와 막힌 이름·조치·로그 경로를 받고, 원인을 고친 뒤 같은 명령을 다시 실행한다.

**Discord 승인 게이트는 이 흐름에 관여하지 않는다.** 로컬 설치 확인이며, sudo는
`yes` 뒤에만 나간다. 비대화 자동화는 필요한 입력과 명시적 `--yes`를 함께 준다.
마법사는 공지 지문을 지어내지 않는다. 생략하면 설치기의 기계 대조가 빠지고 WARN이 된다.

### 거부 흐름 — 설치하지 않고 멈추기

- 확인에 `n` 입력 → **rc 3, sudo 0회**. dry-run은 실행됐고 config·계획 로그는 남는다.
- 질문·확인이 필요한데 터미널 없음 → **`WIZARD-NO-TTY`, rc 2**. 설치기는 실행하지 않는다.
- `--profile rga`처럼 모르는 이름 입력 → **`WIZARD-UNKNOWN-PROFILE`, rc 2**.
  입력한 이름과 알려진 프로필을 보여주며 조용히 다른 프로필로 설치하지 않는다.
- 공개키를 읽을 수 없음 → **`WIZARD-TRUST-KEY-UNREADABLE`, rc 2**. 키 경로를 고친다.

### 프로필이 해주지 않는 것

`rag`·`report-hub`·`full` 선택은 **헬스체크 선언**이지 RAG 스택이나 report-hub 유닛의
설치가 아니다. 대응표·선언 파일과 환경 우선순위는 [설치 가이드 §4](../guide/install.md#프로필과-헬스체크-선언),
기존 노드·수동 서비스 변경 뒤의 `--suggest` 복구는 [운영 가이드](../guide/operations.md#설치가-운영하지-않는-서비스는-선언에서-뺀다)가 소유한다.
