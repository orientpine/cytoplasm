# 연구계획서 자동생성 — 목표 한 문장에서 HWPX 발행까지

## 무엇을

연구 목표 문장 하나를 입력하면 근거 조사부터 소유자 전용 Drive 발행과 불변 버전 기록까지 이어지는 `proposal` 스킬 v2다. 파이프라인은 반드시 `research → corpus → images → draft → refine → render → publish → version` 순서로 실행한다. 특히 윤문(`refine`)은 렌더 앞에 있어야 하며, 이 순서는 산출물 계약이다.

- **근거**: `automation.knowledge` 파사드가 개인 RAG·wiki 트윈·Obsidian·주간 연구동향을 한 경로로 제공하고, 웹 딥리서치는 `SYNTHESIS.md`로 합친다. `CONFIRMED` 20건 이상, 출처 도메인 8개 이상, 섹션 커버리지를 충족해야 하며 출처 없는 주장은 본문에 들어가지 않는다.
- **그림**: 기본 15장, 30장 프로파일을 생성한다. 프롬프트는 `no text, no labels, no numerals`, 캡션은 `그림 N.` 형식이며 2페이지 밴드마다 1장 밀도를 강제한다. 렌더된 그림은 문단 중앙 정렬로 최대 142.9mm(구 95mm 캡의 1.5배)까지 표시되고, 본문 인용은 그림을 주어로 세우지 않고 주장 문장 끝 괄호 표기(`…를 개발한다 (그림 N).`)를 쓴다 — refine 이 결정론 전처리로 재작성한다. `gpt-image-2`를 쓰되 캐시·재개와 월 10달러 소프트캡으로 비용을 제한한다.
- **윤문과 렌더**: `im-not-ai` 고정 리비전(`177e6453…`)의 Codex 호스트가 마스킹 후 11개 불변식을 지켜 윤문한다. 민감 본문은 non-GLM 호스트에서만 처리한다. HWPX 렌더는 고정 SHA의 `kimm-docbot` 서브프로세스만 사용하며 `PROPOSAL_DOCBOT_PIN=382f1a60a49a0f2f2e6abe21dcced9b6c011358b`가 없거나 다르면 `ENGINE-PIN-BLOCK`으로 닫힌다.
- **시각 검토**: `visual-review`가 최종 HWPX를 페이지별 PNG와 PDF로 펼친다. 에이전트는 모든 페이지를 직접 열어 제목·표 머리글 고립, 과도한 공백, 그림과 본문의 밀도 편차를 판정한다. 결과는 HWPX SHA별 QA 캐시에 두어 불변 버전은 수정하지 않는다.
- **추진 내용 표**: `tables.json`의 `gantt` 표로 전 연차를 채운다 — 연차마다 연구 꼭지 8개, 각 꼭지의 월 배분이 연차를 남김없이 덮어야 렌더가 통과한다(완결성 fail-closed). 근거 추적성(Coverage Score)은 계획서 본문에서 빠지고 `out/proposal.hwpx.traceability.md` 사이드카로 관리된다.
- **게시와 버전**: `DriveClient`가 owner-only 권한과 업로드 SHA read-back을 확인하고 finalize 프로토콜로 게시한다. `delta/raw`는 제외하며 공유·권한 변경은 하지 않는다. 버전은 불변 `vNNNNNN`이고 `run_key` 재실행은 멱등이다. `improve`는 새 델타만 닫으며 충돌을 풀지 못하면 `DELTA_CONFLICT_UNRESOLVED`로 중단한다.

## 왜

연구계획서는 근거 수집, 그림 제작, 문체 정리, HWPX 조판, 게시가 서로 다른 도구에 흩어지기 쉽다. 그러면 출처 없는 주장이 섞이거나, 윤문 전 문서를 렌더하거나, 재실행이 기존 버전을 덮어쓰는 문제가 생긴다. 이 기능은 단계별 산출물과 실패 게이트를 하나의 순서로 고정해 재현 가능한 초안과 감사 가능한 발행본을 만든다.

자율 굴착기 사례는 실제 Drive에 `v000001`로 발행됐다. 워크스테이션 판정은 추정 31쪽, 그림 15장과 비교표였으며, 실제 문서 본문은 저장소 문서나 증적에 복사하지 않는다.

## 사용 시나리오

```bash
python3 skills/proposal/scripts/proposal_cli.py research \
  --slug S --goal '연구 목표 문장 하나'
```

이후 같은 CLI에서 `corpus`, `images`, `draft`, `refine`, `render`, `visual-review`, `publish`, `version`을 앞 단계 산출물이 준비된 순서대로 호출한다.

- **happy — 최초 발행**: 목표 문장을 입력한다 → 지식 파사드와 웹 조사가 근거 계약을 통과한다 → 그림·초안·윤문을 거쳐 HWPX를 렌더한다 → owner-only와 SHA read-back을 확인한다 → `v000001`을 발행한다. 같은 `run_key`로 다시 실행해도 새 버전을 중복 생성하지 않는다.
- **happy — 직접 시인성 검토**: `visual-review --slug S --json`을 실행한다 → SHA로 고정된 페이지 PNG 목록이 나온다 → 에이전트가 전 페이지를 직접 읽고 제목 고립·표 분할·공백·밀도를 확인한다. 숫자 지표만 통과한 문서는 시인성 검토 완료로 간주하지 않는다.
- **실패 — 엔진 핀 불일치**: `PROPOSAL_DOCBOT_PIN`이 설치된 `kimm-docbot` SHA와 다르다 → 렌더가 `ENGINE-PIN-BLOCK`으로 중단된다 → 게시와 버전 확정은 실행되지 않는다. 올바른 핀과 엔진을 맞춘 뒤 중단 지점부터 재개한다.

- 윤문·렌더·시각 검토·게시: `proposal_refine.py`, `proposal_render.py`, `proposal_visual_review.py`, `proposal_publish.py`

- 근거 경계: `automation/knowledge/`, `SYNTHESIS.md` 품질 계약, 출처 없는 주장 차단

- 외부효과 게이트: owner-only, SHA read-back, finalize, 공유·권한 변경 없음, `delta/raw` 제외
