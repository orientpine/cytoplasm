# 음성 녹취 → 전사본(.md) → 회의록 자동화 (speechtotext)

## 무엇을

Google Drive의 지정 폴더에 녹취 파일을 놓아두면, 5분 틱 워처가 그것을 집어 **전사본
`.md`** 를 만들고 그대로 기존 `meeting` 스킬에 넘겨 **회의록·칸반 카드·마일스톤**까지 잇는다.
사람이 손댈 지점은 "파일을 폴더에 넣는다" 하나뿐이다.

## 왜

회의록 기능은 이미 있었지만 입구가 **텍스트**뿐이었다 — 녹음은 소유자가 직접 받아쓰거나
외부 서비스에 올린 뒤 붙여넣어야 했다. 그 수작업을 없애면서 두 가지를 같이 해결한다.

- **원음이 게이트보다 먼저 나가는 문제.** meeting의 민감도 게이트는 *텍스트*만 본다. 외부
  전사 API를 쓰면 특허·민감 회의의 **음성이 게이트를 거치기 전에** 공유 프로바이더로
  넘어간다. 그래서 전사는 기본이 **로컬**(whisper.cpp)이고, `SPEECHTOTEXT_BACKEND=local`
  일 때 도구가 없으면 네트워크로 폴백하지 않고 멈춘다.
- **장시간 녹취가 조용히 잘리는 문제.** 2시간짜리 파일은 디코더가 중간에 멈춰도 전사본이
  멀쩡해 보인다 — 마지막 한 시간이 없을 뿐이다. 이제 구간 타임스탬프 합집합을 `ffprobe`
  실제 길이와 대조해, 설명되지 않는 앞/뒤 구간이나 비정상적으로 긴 내부 공백이 있으면
  **회의록으로 넘기지 않고 거부**한다(exit 8). 침묵은 결함이 아니므로 커버리지 비율만으로
  판정하지 않는다.
- **반복 붕괴가 커버리지를 통과하는 문제.** 커버리지는 "구간이 비었는가"만 본다. 디코더가
  무너져 같은 문장만 되풀이하면 타임스탬프는 멀쩡히 채워져 있어 그대로 통과한다. 실제 94분
  녹취에서 그 일이 났다 — 한 문장이 910회 반복되며 전사본의 28%를 먹었는데 게이트는 "누락
  없음"이라고 답했다. 이제 최다 8어절의 점유율을 따로 재서 기본 8%를 넘으면 거부하고
  (정상 구간 1.2% vs 붕괴한 녹취 57.1%), 원인이던 문맥 이월은 기본으로 끈다(`-mc 0`) —
  끄고 같은 구간을 다시 디코딩하니 1.2%로 돌아오며 사라졌던 28분치 발화가 복구됐다.

## 과제별로 묶인다

파일 이름이 과제를 말한다 — `20260825_해양고신뢰성.m4a` 의 과제는 `해양고신뢰성` 이다(날짜가 아닌
첫 토큰). 그 과제의 자료는 Drive 에서 한자리에 모인다:

```
autophagy/전사본/해양고신뢰성/용어집.txt      ← 소유자가 직접 고치는 입력
autophagy/전사본/해양고신뢰성/2026/…md        ← 정리된 전사본
autophagy/회의록/해양고신뢰성/2026/…md        ← 회의록
```

용어집을 과제별로 두는 이유는 고유명사가 **한 과제의 사실**이기 때문이다. `한전기술` 은 이 과제의
참여기관이지 모든 회의의 단어가 아니다. 그래서 과제 용어집이 전역 용어집을 덮어쓴다 — 일반적인
오인식(영무→업무)은 전역에, 기관·장비 이름은 과제에 둔다.

## 두 개의 산출물이 Drive에 남는다

`autophagy/전사본/<YYYY>/<날짜>_<라벨>.md` 에 **읽을 수 있게 다듬은 전사본**이, 그리고
`autophagy/회의록/<YYYY>/<회의일>_회의록-<라벨>.md` 에 **회의록**이 남는다. 다듬기는 요약이
아니라 가독성이다 — 한 줄로 이어진 전사를 문장·문단으로 나누고, 연속으로 똑같이 반복된
문장만 접고, 용어집으로 고유명사를 바로잡는다. 그 위에서 결정사항·액션아이템을 읽어내는
일은 meeting 이 그대로 맡는다.

두 경로 모두 **한 번도 동작한 적이 없었다는 사실**을 이번에 실측으로 찾았다. 전사본 쪽은
`DRIVE_PUBLISH_ENABLED` 가 `~/.env.secrets` 에만 있어 CLI 가 그 값을 못 봤고(그래서
`drive_link=""`), 회의록 쪽은 발행 코드가 마운트 경로에서 `automation` 을 import 하지 못해
매번 `DRIVE-PUBLISH-SKIP reason=ImportError` 로 조용히 건너뛰었다. 둘 다 실패가 조용해서
릴리스를 넘어 살아남았다.

## 사용 시나리오

- **happy**: cha가 `autophagy/회의녹음/` 폴더에 `킥오프 회의.m4a`(1시간 40분)를 올린다 → 다음 틱에
  워처가 소유자 전용 파일임을 확인하고 내려받아 로컬 whisper.cpp로 전사 → 커버리지 검증
  통과 → `~/.hermes/speechtotext/transcripts/2026-08-25_킥오프 회의.md` 저장 →
  `meeting ingest` 자식 실행 → 회의록 노트·칸반 카드·마일스톤 생성. 소유자는 결과 통지만
  받는다. `DRIVE_PUBLISH_ENABLED=1`이면 전사본도 `autophagy/전사본/2026/`에 올라간다.
- **누락 의심**: 전사가 12분에서 멈추면 `exit 8`로 중단하고 회의록을 만들지 않는다. 안내는
  "스레드·모델을 올려 재시도하거나, 확인 뒤 `SPEECHTOTEXT_ALLOW_INCOMPLETE=1`". 잘린 회의록이
  진짜 회의록 행세를 하는 것보다 낫다.
- **API 경로 + 2시간 파일**: 로컬 도구가 없으면 25MiB 상한에 걸린다. 이때는 15분 창 +
  10초 겹침으로 나눠 올리고, 겹친 구간에서 **실제로 반복되는 텍스트만** 지운 뒤 순서대로
  잇는다(일치하지 않으면 양쪽을 남긴다 — 중복은 불편이고 누락은 실패다). ffmpeg조차 없으면
  `exit 3`으로 거부하며 로컬 전사 설정을 안내한다.
- **공유된 파일**: 폴더에 있어도 소유자 단독 소유가 아니면 `SPEECHTOTEXT-SKIP
  reason=not-owner-only`로 건너뛴다. 남의 회의 녹음이 자동으로 내 칸반에 들어오지 않는다.
- **실패한 틱**: 회의록 생성이 실패하면 처리 완료로 기록하지 않아 다음 틱이 다시 시도한다.
  전사본은 남으므로 재시도가 전사를 다시 지불하지 않는다.

## 관련

- 스킬: `skills/speechtotext/` — `speechtotext_cli.py`(transcribe/ingest) ·
  `stt_audio.py`(입력 정책) · `stt_local.py`(whisper.cpp) · `stt_client.py`(OpenAI 호환) ·
  `stt_chunked.py`(분할·이음매) · `stt_coverage.py`(누락 검증) · `stt_media.py`(ffprobe) ·
  `stt_transcript.py` · `stt_drive.py` · `speechtotext_drive_watch.py`(no-agent cron)
- 회의록 본체: [`meeting`](../../skills/meeting/SKILL.md) — 민감도 게이트·칸반·통지·Drive 발행은 그대로 meeting 소유
- 승인 게이트: **신설하지 않았다.** Drive 읽기는 denylist 밖이고, 회의록의 외부효과는
  meeting의 기존 게이트가 소유하며, 전용 폴더에 파일을 놓는 행위가 `!meeting`과 동급의
  명시 의도다. 대신 fail-closed 3중(폴더 미설정=무동작 · 소유자 단독 확인 · 성공 후 마킹).
- 공유 변경: `automation/drive_client.py`에 `download_file`, `automation/drive_taxonomy.py`에
  `transcript`(전사본) 카테고리 1행
- 회귀 고정: `tests/unit/test_speechtotext_skill.py`
- 계획: [.omo/plans/speechtotext-skill.md](../../.omo/plans/speechtotext-skill.md)
- 이어지는 기능: 전사본이 한 줄에 한 문장으로 쓰이고 블록마다 화자·시각 헤더가 붙는다 —
  [전사본 화자 구분과 문장 단위 출력](전사본-화자-구분과-문장-단위-출력.md)
