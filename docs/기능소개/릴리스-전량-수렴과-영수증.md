# 릴리스 전량 수렴과 영수증

## 무엇을

`automation/deploy_all.sh`는 현재 릴리스의 스킬 마운트와 계정 홈 배포물을 한 번에
대조하고, 필요한 기존 배포기를 실행한 뒤 **전량을 다시 판정**한다. 전부 일치한 경우에만
`/srv/autophagy-private/deploy-all/receipt.json` 영수증을 남긴다.

단독 스킬 배포는 그대로 유지된다. 영수증은 한 릴리스가 한 번 전량 반영되었다는
롤아웃 증명이고, 이후의 개별 드리프트는 기존 healthcheck 프로브가 계속 잡는다.

## 왜

기존에는 스킬·워처·플러그인을 각각 배포했기 때문에 “일부만 최신”과 “전부 최신”을
명령 하나로 구분할 수 없었다. 배포가 빠졌는데도 이미 반영된 것으로 오인하거나, 반대로
이미 끝난 기능을 다시 개발하는 문제가 생겼다. 전량 재판정과 현재 릴리스 SHA에 묶인
영수증으로 이 추측을 없앤다.

## 사용 시나리오

### 정상 경로

1. `automation/deploy_all.sh --plan`으로 현재 릴리스의 누락·드리프트를 읽는다.
2. 릴리스와 개발 체크아웃의 SHA가 같은 상태에서 `automation/deploy_all.sh --apply`를
   실행한다.
3. 오케스트레이터는 기존 `deploy-skill.sh`와 각 패키지 `deploy.sh`만 호출한다. 스킬은
   릴리스 ✅가 바인딩한 **전체 governed skill digest**를 재사용하고, 플러그인이 바뀌면
   agent·peer 게이트웨이를 모두 재시동한다. 노드 current가 실행 체크아웃 HEAD와
   이미 같으면 unsigned 새 main을 수렴하려 하지 않고 현재 sealed release를 그대로 쓴다.
4. 마지막 전량 재판정이 통과하면 영수증을 기록하고 SHA256 read-back으로 확인한다.
5. 이후 healthcheck의 `release_fully_deployed`가 영수증 SHA와 현재 릴리스 SHA를
   계속 대조한다.

### 실패·거부 경로

- 관측이 잘렸거나 홈 배포물을 읽지 못하면 `DEPLOY-ALL-UNVERIFIABLE`로 실패한다.
- 체크아웃 HEAD와 노드 릴리스 SHA가 다르면 다른 세대 파일을 섞지 않고
  `RELEASE-MISMATCH`로 멈춘다.
- current와 실행 HEAD가 같은 경우는 origin/main이 다음 미릴리스 커밋으로 전진했더라도
  정상 배포한다. 둘이 다를 때만 서명된 origin/main 수렴을 시도한다.
- 배포기 하나라도 실패하거나 고아 마운트처럼 수동 판단이 필요하면 최종 재판정이
  실패하며 영수증을 쓰지 않는다.
- 영수증이 없거나 깨졌거나 현재 릴리스와 다르면 healthcheck가 모두 FAIL로 보고한다.

## 운영

워크스테이션에서 노드에 접근할 수 없는 세션은 코드·테스트·문서까지만 완성한다.
실제 적용은 노드 접근 가능한 운영 환경에서 `--plan`을 먼저 확인한 뒤 `--apply`로
수행한다. root 자산과 RAG·런타임 패키지는 기존 상시 프로브에 위임되며 영수증의
`delegated` 필드가 그 경계를 명시한다.
