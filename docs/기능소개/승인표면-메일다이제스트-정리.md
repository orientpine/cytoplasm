# 승인 표면·메일 다이제스트 정리

## 무엇을

승인 채널 해석기의 인증 주체와 메일·캘린더·조율·위키 스킬이 주입하는 Discord API를
일치시켰다. 메일 다이제스트의 GLM 요청은 JSON 출력과 추론 비활성화를 명시하며, 한 메일의
분류 응답이 깨지면 그 분류만 한 번 더 시도한다.

배포 시나리오의 채널 값은 운영 override처럼 보이지 않는 fixture 이름을 쓰고, peer와 같은
최소 환경으로 시나리오를 재현하는 절차도 `docs/guide/스킬-제작.md`에 표준화했다.

## 왜

기존에는 실제 인증을 수행하는 주입 API와 directory의 가짜 `"unavailable"` 토큰이 달라
채널 설명과 캐시 fingerprint의 의미가 어긋났다. 또한 추론 모델이 자연어 또는 긴 reasoning을
내면 메일 한 건의 분류가 실패했다. fail-open은 전체 다이제스트 중단을 막았지만, 정상 분류를
회복할 기회는 없었다.

## 사용 시나리오

- **정상/회복 경로**: 오전 다이제스트가 새 메일을 분류한다 → GLM은 JSON mode·thinking disabled로
  응답한다 → 첫 응답 파싱이 실패해도 같은 메일의 분류만 한 번 재호출한다 → 두 번째 응답이
  유효하면 정상 category/flags로 표시한다. 캘린더 위임은 분류가 확정된 뒤에만 한 번 실행된다.
- **실패 경로**: 두 번 모두 호출 또는 파싱에 실패한다 → 해당 메일은 `중요`로 보수적으로
  표시하되 실행 가능한 flag를 만들지 않고 `분류 실패` 배지를 붙인다 → 나머지 메일과 다이제스트
  전송은 계속된다.
- **배포 전 재현**: 스킬 디렉터리를 `/tmp/isolated/`로 복사하고 최소 환경으로 `scenario.sh`를
  실행한다 → 리포 안의 lazy import에 기대는 거짓 PASS를 peer 전에 확인한다.

## 관련

- 공유 해석기: `automation/interop/approval_directory.py`
- 스킬 binding: `skills/{mail,calendar,coordination,wiki}/scripts/*_binding.py`
- 메일 하드닝: `skills/mail/scripts/triage_llm.py`, `triage_digest.py`
- 격리 절차: `docs/guide/스킬-제작.md`
- 배포: mail·calendar·coordination·wiki 각각 소유자 승인 필요. 코드는 커밋만 된 상태이며 마운트와
  cron 수렴은 별도 owner-approved 세션에서 수행한다.
