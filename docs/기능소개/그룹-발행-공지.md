# 그룹 발행 공지 (announce)

## 무엇을

관리형 스킬을 발행하면 그 릴리스 공지가 **roster가 지정한 그룹 채널**로 정확히 한 번
올라간다. 같은 릴리스를 다시 발행해도 공지는 늘어나지 않는다.

## 왜

공지는 두 가지가 어긋나 있었다.

1. **대상이 그룹의 것이 아니었다.** 채널은 발행자 워크스테이션의 환경변수
   (`MANAGED_ANNOUNCE_CHANNEL_ID`) 하나로만 정해졌다. 그런데 "어디서 팀원이 읽는가"는
   그룹의 속성이지 한 설치의 속성이 아니다 — roster가 이미 그룹의 단일 문서인데
   공지만 그 밖에 있었다.
2. **같은 릴리스가 두 번 게시될 수 있었다.** 발행 스크립트를 다시 돌리면 공지도 다시
   나갔다. 이 저장소는 승인 메시지에 대해 이미 「승인 메시지 단일성 규칙」으로 이
   문제를 풀어 두었는데, 공지는 승인이 아니라는 이유로 그 규율 밖에 있었다.

## 어떻게 (설계 요지)

- **대상**: roster의 선택 필드 `announce_channel_id`(숫자 문자열, 형식이 틀리면 roster
  자체가 fail-closed 거부). 값이 있으면 그 채널이 이긴다. **필드가 없거나 roster가 없으면
  기존 환경변수 동작 그대로다** — 이미 돌고 있는 설치는 아무것도 바뀌지 않는다.
- **중복 방지**: 새 메커니즘을 만들지 않고 승인 게이트가 쓰는 기법과 그 원시 도구를
  그대로 재사용한다 — `FileKeyLease`(키 단위 lease)와 `PostingJournal`(게시 직전 예약)이
  같은 것이고, `action_hash`는 릴리스 내용에 바인딩된다
  (`sha256(manifest digest + tag + channel)`).
  - 이미 공지된 릴리스 → 게시하지 않고 저장된 message id를 반환한다.
  - 같은 태그인데 바인딩이 달라졌다 → **거부**한다(조용한 이중 게시 대신).
  - 전송이 실패하면 예약을 **일부러 남긴다**. 실패한 전송이 실제로는 도착했을 수 있어
    재시도가 이중 게시가 되기 때문이며, 다음 실행이 시끄럽게 거부한다.
- 공지는 승인이 아니므로 `approval_lifecycle.request_owner_approval` 파사드를 **경유하지
  않는다** — 그 파사드의 일은 존재하지 않는 소유자 결정(✅/⛔)을 probe 하는 것이다.
  재사용한 것은 파사드가 아니라 **기법과 그 원시 도구**다.

## 사용 시나리오

**happy path** — 그룹 채널로 공지

```yaml
# ~/.hermes/roster.yaml
announce_channel_id: "1004"     # 그룹 서버의 공지 채널 id
```

```bash
python3 -m automation.group_roster validate ~/.hermes/roster.yaml
# ROSTER-VALID group_id=gildong-lab members=3 update_channel=upstream announce_channel=1004

python3 -m automation.managed_skills.publish_cli --skill managed-lab-notes ...
# PUBLISHED skill=managed-lab-notes tag=managed-lab-notes/v3
# → 채널 1004 에 공지 1건
```

**재실행** — 같은 릴리스를 다시 발행

```bash
python3 -m automation.managed_skills.publish_cli --skill managed-lab-notes ...
# → 채널에는 여전히 공지 1건. 원장이 이미 게시된 message id 를 돌려준다.
```

**설정하지 않았을 때** — `announce_channel_id`를 생략하면 공지 대상은 예전처럼
`MANAGED_ANNOUNCE_CHANNEL_ID`이고, 그것도 없으면 공지 자체를 하지 않는다(무음 no-op).

## 관련

- 코드: `automation/managed_skills/announce.py`(대상 해석 + 게시),
  `automation/managed_skills/announce_ledger.py`(해시 바인딩 원장),
  `automation/group_roster/{schema,validator}.py`(`announce_channel_id`),
  재사용한 원시 도구 `automation/interop/approval_lease.py`.
- 런타임 상태: `~/.hermes/managed-skills/announce/`
  (override `MANAGED_ANNOUNCE_STATE_DIR`) — 체크아웃 밖(「추적 config = 불변 시드」).
- 승인 게이트는 관여하지 않는다 — 공지는 외부효과 승인 대상이 아니라 발행 이후의 알림이다.
  발행 자체의 소유자 승인은 기존 `skill_gate publish-request` 경로 그대로다.
- 매뉴얼: `docs/guide/manual-group-admin.md` §3, §5.3.
- 계획: `.omo/plans/public-release.md` W-F3-C.
