# 메모리 정리 — 한 줄에 메시지 하나

## 무엇을 · 왜

메모리 항목마다 **원문과 이동할 목적지를 담은 짧은 한국어 메시지 하나**를 기존 요청별 승인 스레드에
올린다. USER.md의 다른 사람 정보는 Obsidian 사람 노트(`person--…`)로, 처리 규칙은 MEMORY.md로,
운영 참고는 기존 참조 노트로 옮긴다. 새 메시지는 `owner-ko-v4` 계약으로 렌더하며 예전 판본은 그대로 둔다.

소유자 지시(2026-10-15 05:42 KST):
> "개별로 달수있게 해 이러면 정리건수 많아지면 내가 일일이 기억해야 해. 개별 메세지를 작성하게 해야지."

여러 줄을 번호·색상으로 한 카드에 묶고 마지막에 승인하는 방식에서는 어떤 선택이 어느 줄에 해당하는지
계속 기억해야 했다. 이제 **해당 줄의 메시지에서 리액션 하나만 누른다. 별도의 최종 승인은 없다.**

## 사용 시나리오

- **이동**: 사람 정보 메시지의 `➡️`를 누르면 기존 워처가 그 줄만 동결한다. 노트 저장·내용 해시·RAG
  인제스트·원본 스냅샷·단일 항목 확인을 거쳐 원래 메모리에서 지운다. USER.md 규칙은 MEMORY.md에
  같은 글이 들어간 것을 확인한 뒤 지운다. 상한 초과나 확인 실패 때는 원본을 남긴다.
- **유지**: `📌`를 누르면 그 줄은 원래 자리에 남고 다시 제안하지 않는다.
- **삭제**: `🗑️`를 누르면 agent와 peer의 USER.md·MEMORY.md에서 **글이 정확히 같은 항목만**
  각 계정의 잠금·스냅샷 확인·백업을 거쳐 지운다. 별도 노트는 만들지 않는다.
  agent는 같은 선택에 묶인 peer 완료 영수증을 기다린다.
- 봇은 메시지마다 `➡️`·`📌`·`🗑️` **정확히 세 개**를 미리 단다. 타인과 봇의 리액션은 무시한다.
  선택이 없으면 보류하고, 소유자가 둘 이상 누르면 **유지**한다.
- 워처가 동결하기 전 리액션을 제거하면 현재 상태를 따른다. 한번 동결하면 이후 리액션 변경·재시작으로
  선택을 바꾸지 않는다. 삭제를 포함해 이 규칙이 적용되므로 결정 후 리액션 변경은 철회 수단이 아니다.
- 메시지 ID·요청 키·원문 바이트 해시·목적지의 결합을 검증한다. 메시지를 읽을 수 없거나 원문이 바뀌거나
  바인딩이 모호하면 실행하지 않고 보류한다. 동결 후 실행 직전에도 메시지 무결성을 확인한다.

## 기존 카드의 자동 이관

기존 워처가 아직 미결인 배치 카드의 모든 리액션을 검사한다. **어떤 이모지에도 소유자 리액션이 없을 때만**
기존 키 lease 안에서 옛 레코드를 `abandoned / superseded-by-per-line`로 보관하고,
각 줄을 같은 승인 스레드의 개별 메시지로 재제안한다. **옛 Discord 메시지는 지우지 않는다.**
재게시가 모두 끝나면 그 스레드에 짧은 결과 한 줄을 남긴다. 이미 소유자가 반응한 배치는
이 이관이 건드리지 않으며, 저장된 예전 판본·선택 규칙으로 기존 워처가 처리한다.

5줄 배치 제한과 틱당 한 카드 제한은 새 경로에서 쓰지 않는다. 대기 중인 11줄도 한 틱에 모두 게시하며,
실제 429는 기존 transport의 제한된 Retry-After 처리에 맡긴다. 메시지 하나의 1,900자 예산은 유지하고,
너무 긴 한 항목이 다른 항목의 제안을 막지 않는다. 새 스레드 처리기·게시 경로·승인 워처는 없다.
노드에서 수동 이관 명령을 실행하거나 설정을 고칠 필요가 없다.

## agent 검증과 token-less peer

P5의 [피어 은퇴 모드](메모리-피어-은퇴.md)가 명시된 노드는 아래의 양 계정 경로 대신
agent만 백업 삭제하고 은퇴 영수증을 남긴다. 설정이 없는 노드는 아래 계약 그대로다.

소유자 결정 Q149: **"peer 확인 빼고 가"**. agent만 원문·메시지·소유자 선택을 검증해 한 번 동결하고,
기존 요청함의 `<키>.decision.json`으로 전달한다. peer는 Discord 토큰 없이, 요청 바인딩이 같은
agent 결정을 자신의 원장에 동결해 자기 홈의 삭제만 처리한다. 선택이 다른 영수증은 거부한다.
이동은 기존 `apply.py`의 다섯 게이트와 composite action hash, RAG 검증을 그대로 지난다.

peer가 중단돼도 이동·유지는 진행하고 양 계정 삭제만 기다린다. peer가 신뢰하는 것은 agent 소유 요청·결정
파일이므로 agent 계정 침해가 peer 삭제 권한으로 이어지는 기존 신뢰 경계는 그대로다. 백업은 남는다.
삭제와 완료 영수증 사이에 중단되면 `delete-interrupted`로 보류해 같은 글을 자동으로 다시 지우지 않는다.

기존 릴리스 배포기가 요청함과 두 워처를 준비한다. 새 자격증명·root 작업은 없다.
백업은 각 계정 `~/.hermes/memories/*.deleted-*`, agent 결정은
`memory-curator/choice-decisions`, 옛 카드 감사 기록은 `memory-curator/superseded-batches`에 남는다.
