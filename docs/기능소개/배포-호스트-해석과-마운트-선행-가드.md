# 배포 호스트 해석과 마운트 선행 가드

**무엇을**: 스킬 배포 스크립트가 `~/.hermes/node.toml` 에서 배포 호스트를 스스로 읽고,
`todo` 워처는 자기가 import 하는 스킬이 **이미 마운트돼 있을 때만** 배포된다.

## 왜

두 가지가 2026-08-27 배포 사이클에서 드러났다.

**① 호스트를 손으로 줘야 했다.** `calendar` · `coordination` · `mail` · `todo` · `wiki` 는
`${DEPLOY_SSH_HOST:-}` 만 보고, 나머지 열한 개가 쓰는 노드 설정 폴백이 없었다. 그래서
`node.toml` 에 호스트가 멀쩡히 있어도 `exit 3` 으로 거부해 변수를 손으로 export 해야 했고,
그날 mail·todo 에서 두 번 걸렸다. 가드가 있었는데도 못 잡은 이유는 그 가드들이 **다른 질문**을
보고 있었기 때문이다 — 하나는 "변수를 쓰면서 eval 을 빠뜨려 `set -u` 로 죽는가", 다른 하나는
"아무 데도 없을 때 자기 이름으로 거부하는가". **"설정이 있으면 읽는가"** 는 어디에도 없었다.

**② 배포 순서가 산문에만 있었다.** `todo_confirm_reaction_watch.py` 는 다른 워처와 달리 live
스킬을 subprocess 로 부르지 않고 `sys.path` 에 넣어 **import** 한다. 스킬 마운트보다 먼저
배포하면 매 틱 기동 즉시 ImportError 로 죽고, 소유자가 누른 승인 ✅ 를 아무도 소비하지 않는
**침묵**이 된다. 2026-08-21 repair 승인 워처가 정확히 그 모양으로 5일간 5,329회 죽어 있었다.
그날은 사람이 순서를 지켜 피했지만, 그 순서는 어디에도 코드로 없었다.

## 사용 시나리오

**호스트 — 그냥 된다.** 변수를 export 하지 않고 배포한다.

```bash
skills/todo/deploy.sh          # DEPLOY_SSH_HOST 없이도 node.toml 의 호스트로 진행
DEPLOY_SSH_HOST=other-node skills/todo/deploy.sh   # 명시하면 그쪽이 이긴다
```

어느 출처에도 호스트가 없으면 예전처럼 `DEPLOY-BLOCK` + `exit 3` 으로 **자기 이름을 대며**
멈춘다(해석 불가한 이름을 ssh 에 넘기지 않는다).

**마운트 — 순서가 틀리면 거부한다.** 스킬을 아직 마운트하지 않고 워처만 배포하면:

```
DEPLOY-BLOCK: live 마운트에 워처가 import 하는 모듈이 없다: todo_execution_reconcile ...
              스킬을 먼저 마운트하라 — automation/deploy-skill.sh todo (소유자 승인).
              워처를 먼저 배포하면 매 틱 ImportError 로 죽어 승인이 소비되지 않는다.
```

`exit 5` 이고 **아무것도 push 되지 않는다**. 마운트를 마친 뒤 다시 돌리면 그대로 진행한다.

필요한 모듈 목록은 손으로 적지 않는다 — `automation/live_mount_preflight.py` 가 워처 소스를
파싱해 정적 import 와 `import_module`/`__import__` 의 문자열 인자를 모아 스킬 `scripts/`
디렉터리와 교집합을 낸다. 그래서 워처에 import 가 늘어도 등록을 잊는 실패 모드가 없고,
표준 라이브러리와 `automation.*` 런타임은 교집합에서 저절로 빠진다.

## 관련

- 호스트 해석: `skills/{calendar,coordination,mail,todo,wiki}/deploy.sh`,
  `automation/node_config_sh.py`, `tests/unit/test_deploy_host_reads_node_config.py`
- 마운트 선행: `automation/live_mount_preflight.py`, `skills/todo/deploy.sh`,
  `tests/unit/test_live_mount_preflight.py`
- 승인 게이트가 관여한다: 마운트 자체는 `automation/deploy-skill.sh` 의 소유자 ✅ 경로이며
  이 가드는 그 순서를 강제할 뿐 승인을 대신하지 않는다.
- 단위 테스트가 실제 노드로 배포를 나가던 잠재 결함도 같은 사이클에서 닫았다
  (`tests/unit/test_deploy_host_fail_closed.py` 격리 보강 — FS3 정산 레코드 재생 해시는 불변).
