# 배포 스크립트 정리

## 무엇을

스킬과 공용 런타임을 배포할 때 **검사한 Git 파일만 포장**하고, 실행 시작 시 정한 물리 저장소 경로를 끝까지 재사용하도록 배포 스크립트를 정리했다. 승인 확인 전용 모드, Hermes 목록 확인, peer attest 사전 동기화의 운영 메시지도 실제 동작과 일치시켰다.

## 왜

기존 tar 명령은 Git이 무시하는 `.env`·가상환경 같은 잔여물을 함께 실을 수 있었고, 실행 중 `current` 심링크가 바뀌면 서로 다른 릴리스를 검증·포장할 수 있었다. 또한 `--approve-only` 성공을 마운트 완료로 오해하거나, `managed-X`를 `X`로 잘못 찾거나, ops 권한 실패를 “git 체크아웃 아님”으로 보고하는 진단 함정이 있었다.

## 사용 시나리오

### 정상 경로

1. cha가 `automation/deploy-skill.sh <skill>`로 배포를 시작한다.
2. 스크립트는 시작 시 저장소의 물리 경로를 한 번 확정하고 Git 추적 목록으로 아카이브를 만든다.
3. SANDBOX → REVIEW → 승인·peer attest → MOUNT 순서가 완료되면 검증된 파일만 라이브 스킬 저장소에 설치된다.

승인 상태만 확인하려면 `--approve-only`를 쓸 수 있다. 이 모드는 승인 유효성만 확인하고 **마운트하지 않는다**는 메시지를 출력한다. 실제 마운트는 플래그 없이 배포를 재개해야 한다.

### 실패·거부 경로

- ops 계정으로 릴리스 상태를 조회할 권한이 없으면 sudo/권한 오류로 즉시 중단한다. 릴리스가 실제로 없을 때만 기존 ops 체크아웃의 ff-only 경로를 사용한다.
- 제거 뒤 Hermes 목록에 `managed-X`만 남고 `X`가 없으면 `X` 제거는 성공으로 판정한다.
- Git이 추적하지 않는 비소스 잔여물은 배포 아카이브에 포함되지 않는다.

## 관련

- 핵심: `automation/deploy-skill.sh`, `automation/deploy_provenance.sh`
- 회귀: `tests/unit/test_deploy_archive_manifest.py`, `tests/unit/test_deploy_skill_sync_policy.py`
- 작업 묶음: `.omo/plans/parallel-followup-sweep.md` §5 G1
