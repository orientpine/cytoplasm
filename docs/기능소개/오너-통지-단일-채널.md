# 오너 통지 단일 채널 (ON-1·ON-2·ON-3)

## 무엇을

소유자에게 가는 모든 **통지**(일일 지출·주간 연구동향·아침 자가 스킬 감사·헬스체크·
리마인더·구매 검토 요청·인터롭 위임 결과·수렴 실패 알림)를 `automation/owner_notice.py`
파사드 **한 경로**로 모으고, 목적지를 설정 키 하나로 정한다:
`owner_notice_channel_id`(`~/.hermes/interop/config.json`, env `OWNER_NOTICE_CHANNEL_ID` 우선).
설정되면 그 채널(**`#notifications`**)로만 보내고, 미설정이면 기존 소유자 DM이다.

## 왜

승인은 v7이 이미 `#agent-chat` 스레드로 옮겼지만 **통지는 아직 DM으로 흩어지고
있었다** — 파사드 밖에서 `/users/@me/channels`를 직접 여는 발신자가 6곳(실측)이었다.
정기 통지 트래픽이 대화 채널을 오염시키지 않도록 별도 채널로 분리한다(§10-6 확정,
2026-08-28). 사본이 여섯이면 반드시 드리프트한다 — 목적지 결정은 한 곳만 안다.

## 어떻게

- **ON-1**: 파사드가 채널을 해석한다. 설정되면 **그 채널로만**(DM 폴백 없음 — 게시
  실패는 `False`로 호출자 큐잉·재시도, 「절대 예외를 던지지 않는다」 계약 불변).
  설정을 읽을 수 없어도(EACCES 포함) 던지지 않고 미설정으로 답한다(ProtectHome 교훈).
- **ON-2**: 직접 DM 발신 6곳(reminder_poller·research_trends·cost-report·
  memory_curator effects·procurement review·hermes_plugin 위임 결과)을 파사드 경유로
  이관. 마스킹 규칙은 각 발신자 것 그대로 — 채널은 목적지만 바뀐다. 첨부를 보내는
  procurement는 `resolve_notice_target()`으로 대상 채널 id만 받아 첨부를 올린다
  (DM 오픈은 여전히 파사드/central directory 안에서만). research_trends의 agent-chat
  직송(2026-08-24)은 §10-6 확정으로 대체됐다.
- **ON-3**: conformance — `/users/@me/channels`를 여는 코드는 central directory와
  E2E gate driver 2곳뿐(`tests/unit/test_approval_surface_inventory.py`). 새 통지
  발신자가 DM을 다시 열면 CI RED다.

## 소유자 메시지 봉투 (2026-09-11)

`notify_owner(content=None, *, notice=None, message=None)`와
`notify_owner_dm(content=None, *, notice=None, message=None)`는 `OwnerMessage` 봉투도 받는다.
본문은 위치 인자·`content=`·기존 `notice=` 중 하나로 전달한다. 두 별칭에 같은 본문을 주면
한 번만 보내고, 서로 다른 본문이나 본문 누락은 `NOTIFY-FAILED: TypeError`와 `False`로
거부한다(자격증명 미설정 판정이 먼저다). `message=None`이면 본문을 바이트 그대로 보내며,
봉투를 주면 그 렌더 결과만 보내고 기존 문자열은 붙이지 않는다.
혼합 세대 호출자는 `getattr(owner_notice, "ACCEPTS_OWNER_MESSAGE", False)`로 지원을 확인한다.
생산자의 선택 모듈 import는 `ImportError`뿐 아니라 초기화 중의 다른 `Exception`에도
기존 문자열 배달로 내려간다. 렌더 판본·집계·마스킹·실제 배달 실패의 마커는 바뀌지 않는다.

예를 들어 주간 보고의 원본 메시지 좌표를 `message.location`에 넣으면 소유자는
`#notifications`(미설정 시 DM)에서 원본 링크를 눌러 바로 이동한다. `channel`·`message`
위치는 양쪽 `channel_id`가 모두 있고 같을 때만 "여기"로 표시한다. 따라서 같은 승인
스레드의 결과는 자기 링크 없이 남지만, 좌표 없는 레거시 레코드가 목적지 미상의 폴백으로
가면 "여기"가 아니라 링크 없음·검색 라벨·키를 보여 준다. 길드나 DM 링크를 추측하지 않는다.
`resource`는 채널 좌표가 같거나 양쪽 모두 없어도 로컬이 되지 않아 URL을 유지한다.
주소 없는 `resource`는 검색 라벨·키로 안내한다. `scope="none"`은 위치 없음("해당 없음")이며
검색 키를 무시하므로 검색만 있는 위치는 주소 없는 `resource` 또는 `space="unknown"`인
Discord 위치로 표현한다. `notify_owner_dm`은 통지 채널 설정과 무관하게 열린 소유자 DM을
목적지로 쓴다. 링크 확인용 네트워크 조회는 하지 않는다.

이 지역성 정정은 발신자 이관 전에 착지했으며 `owner-ko-v1`을 유지한다.
이미 게시된 카드·문구를 바꾸는 작업이 아니다.

지원하지 않는 `render_version` 등으로 렌더가 실패해도 프로세스는 계속된다.
import와 렌더 모두 기존 예외 가드 안에 있어 `NOTIFY-FAILED: <type>`와 `False`만
남기고, 자격증명이 없으면 렌더 전에 기존 `NOTIFY-UNCONFIGURED`를 남긴다.
기존 발신자 이관·승인 판정·이미 게시된 카드 변경은 이 확장에 포함되지 않는다.

## 지출·연구동향 정기 보고의 관측 범위

두 발신자는 이제 봉투로 통지한다. 금액 정책·보고서 본문·발송 성공 뒤 상태 기록은 그대로다.
소유자가 보는 통지는 5필드이고, 추가 조치는 없으며 다음 정기 보고를 명시한다.

- **일일 지출**: 스냅샷의 KST 자정~집계 시각을 오늘 지출의 관측 구간으로 표시한다.
  월·전체 누적과 구분하며, 소유자용 원장 조회 화면이 없음을 위치에 밝힌다.
  근거 확인은 Discord 에이전트 DM에 '일일 지출 근거 확인'을 요청하도록 안내하며,
  내부 테이블이나 ops 전용 경로를 소유자가 열 수 있는 위치로 제시하지 않는다.
  시각 누락·형식 오류는 구간을 추측하지 않고 사유가 있는 보고 결과로 전달한다.
- **주간 연구동향**: 기존 arXiv·Semantic Scholar 조회는 날짜 필터 없는 최신 검색이다.
  ISO 주는 발송 중복 방지 키이지 관측 구간이 아니므로 `Periodic` 대신 `Result`를 쓰고
  **관측 구간 없음: 날짜 필터 없는 최신 검색**을 명시한다. 기존 논문·근거 링크는 유지하고
  위치에는 실제 저장한 보고서 파일명의 검색 키를 싣는다. 파일 좌표가 없으면 해당 없음이다.

예를 들어 아침 지출 보고에는 오늘 자정부터 스냅샷 시각까지가 표시된다. 스냅샷 시각이
잘못되어도 금액 보고는 도착하며 구간 부재 사유가 보인다. 동향 보고에서는 저장된 파일명으로
원문을 찾을 수 있고, 최신 검색 결과를 임의의 일주일 전체 관측으로 오해하지 않는다.
계약 import 불가 또는 파사드 지원 플래그 부재 시 두 발신자 모두 기존 본문을 바이트 그대로 보낸다.
연구동향 홈 배포는 기존 `research_trends.py`·`research_trends_core.py` 묶음을 함께 갱신한다.

관련: [지출 보고 규약](../guide/cost-report.md),
`tests/unit/test_cost_report_periodic_notice.py`. 새 승인·통지 표면이나 링크 확인 요청은 없다.

## 위임 응답·릴리스 회수 통지

위임 응답은 상관 id만 보내지 않고 **어떤 조회에 대한 누구의 응답인지**와 원문 검색 키를
함께 보낸다. 예를 들어 가용 시간 조회가 돌아오면 조회 대상·응답 발신자·Discord 검색 키가
보인다. 여기서 실행 완료는 **응답 수신**의 완료이며 일정 확정이나 외부 실행을 뜻하지 않는다.
게이트웨이가 가진 실제 스레드(없으면 채널) 좌표는 보존하되, 공간 정보가 없으므로 링크를
추측하지 않는다. 배달 실패는 이전과 같이 `RuntimeError`로 훅 호출자에게 전파한다.

릴리스 승인 기준이 tip과 달라지면 **자동 완결 보류**와 `automation/release.sh` 재실행 요청을
표시한다. 실행 완료 표시는 불일치 **탐지**의 결과이지 릴리스 완료가 아니다. 요청별 통지
마커는 성공한 배달 뒤에만 기록한다. 감사 회수 후에는 원 승인에 회신으로 회수 사유를 남기며,
같은 채널에서는 위치를 “여기”로 표시한다. 원 카드·리액션·감사·바이트 단위 아카이브는 불변이다.

계약 모듈이 없거나 파사드가 봉투를 지원하지 않는 구형 런타임에서는 기존 문자열을 그대로
전송한다. 직접 회신하는 감사 회수는 계약 import 부재 시 기존 문자열을 사용한다.
승인 리마인더는 예외다: 모든 호출자가 공유하는 `(channel_id, content)` 전송 계약과
유형·경과시간·공용 정의의 원문 링크만 담는 최소정보 포인터를 유지한다.

회귀: `test_interop_result_notice.py` · `test_release_result_notice.py` · `test_release_recovery.py`.

## 소유자 설정 (1회)

0. peer 게이트웨이의 `~/.hermes/config.yaml` 최상위 `discord.ignored_channels` 에 이
   채널 id 를 넣는다(`#approvals` 와 나란히). peer **신원**은 자기 통지를 게시하려고 채널에
   있어야 하지만 LLM 게이트웨이가 남의 통지를 읽으면 통지마다 스레드·논평·`/sethome` nag
   를 남긴다(2026-09-21 실측, 프로브 `peer_ignored_channels` 가 감시).
1. 개인 서버에 `#notifications` 텍스트 채널을 만들고 세 봇(agent·peer·**ops**)을
   초대/권한 부여한다 — ops 봇 초대 전에 채널을 지정하면 ops 발신 통지(수렴 실패·
   헬스체크)가 게시 불가로 큐잉만 된다(ON-4 롤아웃 순서).
2. 각 발신 계정의 `~/.hermes/interop/config.json`에 `"owner_notice_channel_id": "<채널 id>"`
   기입(또는 유닛 env에 `OWNER_NOTICE_CHANNEL_ID`). ProtectHome 유닛(repair·ops)은
   env 쪽을 쓴다.
3. 미설정 상태는 그대로 DM — 레거시 설치 무영향.

## 배포 주의

이관된 홈 배포 사본(`poll_reminders.py`·`send_cost_report.py`·`research_trends.py`)은
각 배포기 실행 전까지 옛 DM 경로로 돈다("커밋됨 ≠ 배포됨"). 게이트웨이 플러그인
(hermes_plugin)은 파일 갱신 후 **재시동**까지 해야 반영된다(agent+peer 세트 규칙).
