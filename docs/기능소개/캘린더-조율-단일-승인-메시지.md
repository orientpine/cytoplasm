# 캘린더·일정 조율 — 단일 라이브 확인

## 무엇을
캘린더 변경과 에이전트간 일정 조율의 owner-confirm DM을 공유 승인 생명주기로 관리한다.
캘린더는 `calendar:{calendar_id}:{event_id 또는 start}`, 조율은 `coord:{slot}`을 승인 키로 사용해
키마다 살아 있는 확인 DM을 1건으로 제한한다. 생산자와 리액션 워처는 같은 lease를 잡는다.

## 왜
기존 append-only JSONL 저장소는 게시할 때마다 새 `draft_id` 또는 `correlation`로 행을 추가했다.
같은 일정에 확인 DM이 중복 게시되면 cha가 어느 메시지를 승인해야 하는지 불명확해지고,
draft별 조회도 유일하지 않아 실행이 fail-closed로 막혔다. 운영 노드에는 기존 행이 살아 있으므로
백필이나 파일 재작성 없이 새 reader가 legacy 행에서 같은 논리 키를 계산해야 했다.

## 사용 시나리오

### 정상 경로
1. 같은 일정·같은 sha256의 확인을 다시 요청한다 → 새 DM을 올리지 않고 기존 메시지 id와 행을 유지한다.
2. 같은 승인 키의 내용이 바뀐다 → 옛 DM을 먼저 삭제하고 해당 행을 CAS로 제거한 뒤 새 DM 1건을 게시한다.
3. cha가 ✅/⛔를 누르면 기존 24시간 TTL 워처가 같은 lease 안에서 결정을 소비하고 캘린더 실행 또는 폐기를 수행한다.
4. 배포 전 legacy 행은 calendar draft의 `calendar_id`와 `event_id`(없으면 `start`), 또는 coordination 행의
   `slot`에서 키를 즉시 계산한다. 온디스크 마이그레이션은 없다.

### 실패·거부 경로
- cha가 이미 ✅/⛔를 누른 요청은 삭제하지 않고 워처에 양보한다.
- pending JSONL 한 줄이라도 손상되면 “미결 없음”으로 간주하지 않고 게시를 거부한다.
- Discord 메시지를 읽지 못하거나 sha256 바인딩이 다르면 기존 행과 DM을 보존한다.
- 워처가 lease를 쥐고 있으면 생산자는 게시·삭제·행 변경을 전혀 하지 않는다.
- calendar legacy 행의 draft 파일이 없으면 `calendar:__orphan__:{draft_id}`로 격리한다. 새 의도와
  매치하지 않으며 기존 워처 정리 경로 외에는 삭제하지 않는다.
- 저장소의 `correlation`은 조율 프로토콜 실행 식별자일 뿐 승인 키가 아니다.
