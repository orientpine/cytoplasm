# 릴리스 버전 승인 — ✅ 한 번이 릴리스 전체를 인가한다

## 무엇을

`automation/release.sh`는 직전 릴리스 태그 이후 쌓인 변경을 표면별 바인딩과 패치노트로
묶어 `kind=release` 승인 요청 하나로 게시하고, 소유자 ✅를 받으면 그 HEAD에 서명 릴리스
태그를 자른다. 태그가 잘리면 2분 리컨실러가 릴리스를 수렴시키고, 전량 반영과 영수증은
`automation/deploy_all.sh --apply`가 완성한다.

## 왜

지금까지 머지가 곧 배포였다(`merge-pr.sh`가 태그를 자동으로 잘랐다). 그래서 스킬 n개가
바뀐 릴리스는 소유자 ✅를 n번 요구했고, 무엇이 함께 나가는지를 한 화면에서 본 적이 없다.
이 명령은 "무엇이 바뀌었고(표면별 digest), 왜 바뀌었는지(커밋 제목, 20줄 상한)"를 하나의
승인으로 묶는다. 승인은 version·HEAD·표면 digest 전체에 해시 바인딩되므로, ✅ 뒤에
무엇이든 바뀌면 승인이 무효가 된다.

## 사용 시나리오

### 정상 경로

1. 워크스테이션에서 `automation/release.sh`를 실행한다. 서명키와 태그 컷은
   워크스테이션에 남고 표면별 diff 계획도 그 체크아웃에서 계산한다. 승인 producer의
   request/decision만 `release_approval_remote.sh`가 현재 HEAD의
   추적 `automation/` 스냅샷을 agent 전용 임시 런타임에 stage한 뒤 **노드 agent
   계정에서** 실행한다. 따라서 봇 토큰을 워크스테이션으로 복사하지 않고, 승인
   레코드도 배포 게이트가 읽는 `~agent/.hermes/skill-gate`에 바로 남는다. plan
   JSON은 SSH stdin을 agent 소유 0600 임시 파일로 한 번 받은 뒤 producer가 읽고,
   종료 시 삭제한다(`/dev/stdin` 재오픈의 교차 UID 권한 문제 회피).
2. 전제 검사: clean tree, `HEAD == origin/main`, 로컬 CI 영수증(기존 push 게이트 재사용).
   하나라도 어긋나면 승인 트래픽 없이 exit 4로 멈춘다.
3. 직전 릴리스 태그..HEAD의 변경을 계획해 승인 요청을 게시한다. 본문은 사람이 먼저
   이해하도록 **전체 배포 번들 표면 이름 → 사용자·운영 변경을 설명하는 커밋 제목 → 전체
   action hash** 순서다. nonce와 표면별 64자 digest는 승인 레코드에만 보관한다.
   자동 생성 패치노트가 길면 완전한 줄 단위로 줄여 생략 줄 수를 명시하고, 그래도
   1900자를 넘으면 fail-closed한다.
4. 소유자가 ✅를 누르면 서명 태그가 잘리고 리컨실러가 ~2분 내 수렴한다.
5. `automation/deploy_all.sh --apply`로 스킬·홈 배포물까지 전량 반영하고 영수증을 남긴다.

### 실패·거부 경로

- **⛔**: 태그 없음, prod 불변, exit 9.
- **무응답**: 기본 실행은 종료하지 않고 계속 기다린다. 따라서 실행 중인
  `release.sh`는 ✅를 감지하면 별도 재실행 없이 즉시 태그를 자른다. 테스트·제한 운영이
  `RELEASE_DEADLINE_SECONDS`를 명시한 경우에만 exit 8이며, 요청은 살아 있어 재실행으로
  재개된다(action hash가 nonce를 제외하므로 중복 게시 0).
- **다른 HEAD의 승인**: decision 폴링이 레코드의 `head_sha`를 현재 HEAD와 대조하므로,
  옛 승인이 새 커밋을 인가하는 일은 없다.
- **고정 필드만으로 1900자 초과**: 표면 이름과 전체 action hash를 줄이지 않고
  거부한다. 임의의 긴 `ReleaseSpec`도 기존대로 거부하며, 축약 대상은 git에서 자동
  생성된 패치노트뿐이다.
- **이번 diff에서 바뀌지 않은 스킬**도 bundle digest에 들어간다. 릴리스 뒤 늦게
  발견된 마운트 드리프트를 같은 ✅로 수렴하려면 승인 레코드가 전체 desired set을
  포함해야 하기 때문이다. 패치노트의 변경 내용에는 실제 바뀐 커밋만 표시한다.
- **노드 자격증명 부재·SSH 실패**: 승인 요청을 게시하지 않고 실패한다. 워크스테이션의
  `~/.env.secrets`는 승인 경로가 아니며 `DISCORD_BOT_TOKEN`을 복사해 넣지 않는다.
- **다음 릴리스 시작**: 이전 `pending/release.json`이 최신 서명 태그 HEAD와 같고
  Discord 결정도 APPROVED일 때만 byte-exact 0600 `release-history/<HEAD>.json`으로
  옮긴 뒤 새 요청을 게시한다. 미승인·다른 HEAD·읽기 불가·archive 충돌은 모두 기존
  레코드를 보존하고 fail-closed한다.
- **문구 버전 전이**: `render_version`이 없는 v1 레코드는 nonce·개별 digest를 포함한
  당시 게시 문구로 그대로 재생한다. 새 사람 중심 문구는 v2 레코드에 명시적으로
  저장한다. 게시 뒤 renderer를 바꿔 과거 ✅가 binding mismatch가 되지 않는다.

## 확장 — 릴리스 승인이 스킬 배포를 인가한다 (VA-2)

`automation/deploy-skill.sh <skill> --release-approval`은 per-skill ✅ 사이클을 릴리스
승인 검증으로 대체한다. staged gate의 `release-authorize`가 ① 이 스킬의 digest가 승인된
표면 집합에 있는지(없으면 Discord 왕복 없이 거부 — 릴리스 이후 바뀐 스킬은 옆 승인으로
못 탄다), ② 릴리스 메시지의 ✅(⛔ 우선), ③ 릴리스 메시지에 바인딩된 peer 증명을 순서대로
확인한다. SANDBOX·REVIEW·peer attestation은 그대로다 — 없어지는 것은 소유자의 ✅ n회뿐이다.
단독 수동 배포(`deploy-skill.sh <skill>`)는 기존 per-skill 승인 그대로 남는다(긴급 핫픽스
경로, §10-3).
