# 승인 게시 복구와 강화 저널 (TRACK-BC)

## 무엇을

승인 메시지를 게시하는 순간의 세 가지 취약점을 한 번에 막는다.

1. **429 재시도** — 메모리 재배치 transport가 Discord rate limit을 만나면 `Retry-After`만큼 자고 최초 호출을 포함해 최대 3회 시도한다(`sleeper` 주입 가능).
2. **강화 저널(enriched journal)** — posting journal의 예약 레코드에 게시 직후 `message_id`·`channel_id`를 덧붙인다. 다음 틱이 그 예약을 읽어 **이미 게시된 메시지를 되찾는다**.
3. **원자적 순서** — 게시 → 저널 강화 → 레코드 커밋 → 저널 clear까지 끝낸 **뒤에** ✅/⛔ 리액션을 붙인다. 리액션 부착 실패는 게시를 무효로 만들지 않고, probe 시점에 빠진 이모지를 다시 붙여 보정한다.

## 왜

기존 파사드는 posting journal에 예약이 남아 있으면 무조건 `POSTING_JOURNAL_STALE`로 거절했다. 게시는 성공했는데 그 직후 프로세스가 죽으면, 소유자 DM에는 승인 메시지가 떠 있는데 상태 파일에는 아무 바인딩이 없고, 파사드는 영원히 거절한다. 승인 메시지는 고아가 되고 그 건은 다시는 진행하지 못한다. 게시 전에 리액션을 붙이던 옛 순서도 같은 계열이었다. 리액션 API가 실패하면 멀쩡히 올라간 메시지가 실패로 처리됐다.

## 사용 시나리오

- **happy**: `request_owner_approval`이 lease를 잡고 저널을 본다. 예약이 없으면 평소대로 게시한다.
- **복구(같은 action_hash)**: 예약이 남아 있고 그 안의 `message_id`/`channel_id`가 현재 intent와 같은 key·channel·action_hash면 원격을 probe한다. `BOUND_PENDING`이면 그 메시지를 **그대로 커밋**하고 `PENDING`을 돌려준다(중복 게시 없음). 이미 ✅/⛔면 커밋한 뒤 `DEFERRED / OWNER_DECIDED`로 워처에 양보한다. 원격에 없으면(`MISSING`) 저널만 지우고 정상 게시로 넘어간다.
- **복구(다른 action_hash)**: 내용이 바뀐 요청이다. 아직 소유자가 누르지 않은 `BOUND_PENDING`이면 옛 메시지를 supersede(delete)하고 저널을 비운 뒤 새로 게시한다. 이미 눌린 것은 **파괴하지 않고** `DEFERRED`로 보존한다.
- **거절**: 예약이 깨졌으면(`message_id` 등 결손) `REFUSED / POSTING_JOURNAL_STALE`. 확인 불가는 `UNVERIFIABLE`, 바인딩 불일치는 `BINDING_MISMATCH`. 전부 fail-closed다.
- **워처 병합**: cron 틱이 순수 상태머신 결과와 디스크에 영속된 상태를 비교해, action_hash가 그대로인데 message 바인딩만 새로 생겼으면 그 바인딩을 결과에 병합한 뒤 저장한다. 효과 계층이 방금 쓴 바인딩을 상태머신 스냅샷이 덮어써 지우던 문제를 막는다.
- **재게시 허용**: `resolve_tick`의 `proposed` 분기에서 `message_id is not None` 단락을 제거해, 저널 복구가 필요한 건이 게시 단계에 도달할 수 있게 했다. 중복 방지는 저널·probe가 맡는다.
