# 릴리스 전 노드 도우미 점검과 수렴 거부 사유

## 무엇을

`release.sh`가 승인 카드를 올리기 **전에** 노드의 root 수렴 도우미가 이 릴리스와 같은 판인지
확인하고, 낡았으면 그 자리에서 멈춘다(exit 4). 그리고 `deploy_all.sh --apply --wait-converge`가
반영을 기다리다 실패하면 노드가 **왜** 거부했는지를 함께 적는다.

## 왜

노드의 수렴 도우미(`/usr/local/libexec/autophagy-converge.d/`)는 릴리스 트리 **밖**의 root 정적
사본이다. 머지만으로 갱신되지 않는 것은 설계다 — 자동으로 따라가면 "PR 병합 = root 임의 코드
실행"이 된다(MD-1). 대신 낡은 사본은 조용히 실패하지 않고 **수렴을 거부**하는데, 그 거부는
태그를 자른 뒤에야 보였다.

2026-09-22 실측: 소유자 ✅ 를 받고 서명 태그까지 자른 v1.10.3 이 `deploy_all` 에서
`waiting for the node release` 를 40번 찍은 뒤 `rc=4` 로 죽었다. 진짜 사유
(`SNAPSHOT-BLOCK: remote main moved`)는 노드 저널에만 있어 사람이 찾아내야 했고, 승인 한 번이
통째로 헛돌아 같은 내용을 v1.10.4 로 다시 승인받아야 했다.

## 사용 시나리오

**도우미가 낡은 경우 (승인 전에 멈춘다)**

```
$ automation/release.sh
[release-helper] HELPER-DRIFT: origin_snapshot.sh differs from the rendered release source
[release-helper] run provision-deploy-converge.sh on the node as root
[release] RELEASE-BLOCK: 노드의 root 수렴 도우미가 릴리스와 다르다 — 위 안내의
          프로비저너를 먼저 돌린다(승인 전에 멈췄다)
```

카드도 태그도 만들어지지 않는다. 안내대로 노드에서 프로비저너를 한 번 돌린 뒤 다시 실행하면
그 자리에서 재개된다. 이미 ✅ 받은 요청도 같이 막는데, 승인 레코드는 살아 있으므로 잃는 것이 없다.

**판정하지 못하는 경우 (막지 않는다)**

노드가 불통이거나 권한이 없어 판정할 수 없으면 `HELPER-DRIFT-UNKNOWN` 한 줄을 남기고 진행한다.
판정 불가는 위반이 아니다 — 여기서 막으면 노드가 잠깐 불통인 동안 릴리스 자체가 불가능해진다.

**그래도 막혔을 때 (사유가 보인다)**

```
[deploy-all] RELEASE-MISMATCH: local HEAD 2a43d1fee7c6 != node release 4f02d1eeb962
[deploy-all] NODE-CONVERGE-REFUSED: [deploy-reconcile] HELPER-FAILED converge:
             SNAPSHOT-BLOCK: remote main moved
```

저널에 아무것도 없으면 사유를 지어내지 않고 "찾지 못했다"고 적는다. 이 조회는 진단 전용이라
실패해도 종료 코드·영수증을 바꾸지 않는다.

## 관련

- `automation/release.sh` 전제 ④ · `automation/deploy_all.sh` `converge_refusal`
- 판정은 기존 헬스체크 프로브 `automation/release_helper_probe.sh`를 그대로 실어 보낸다 —
  새 프로브·새 승인 표면을 만들지 않는다.
- 탈출구 `RELEASE_ALLOW_HELPER_DRIFT=1`은 샌드박스 전용이며 쓰면 stderr 에 남는다.
- 회귀: `tests/unit/test_release_sh.py`, `tests/unit/test_deploy_all_cli.py`
- 근본 해결(도우미 갱신)은 여전히 소유자가 노드에서 root 로 `provision-deploy-converge.sh`를
  한 번 돌리는 것이다. 이 기능은 그 필요를 **릴리스 전에** 알려 줄 뿐이다.
