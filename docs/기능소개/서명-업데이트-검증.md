# 서명 업데이트 검증

## 무엇을

노드 자동 업데이트는 공개 `origin`의 `main` 커밋이 **서명된 annotated release tag**로 함께
게시됐을 때만 그 태그가 가리키는 SHA에 수렴합니다. 서명은
`/etc/autophagy/update-allowed-signers`의 `update-trust@autophagy` principal로 검증하며,
lightweight tag나 bare commit은 릴리스로 인정하지 않습니다.

## 왜

mutable `main`을 root helper가 바로 적용하면 upstream 쓰기 권한 탈취가 곧 공급망 RCE가 됩니다.
사후 롤백은 이미 실행된 악성 코드를 없던 일로 만들 수 없으므로, 검증은 `current` 전환과 gateway
재시작보다 먼저 끝나야 합니다. ops pre-gate와 root-owned helper가 같은 정책을 각각 확인해
검증과 적용 사이의 ref 변경도 fail-closed로 막습니다.

## 사용 시나리오

- **정상**: `public_export.sh`가 공개 commit과 SSH-signed tag를 atomic push하면 리컨실러가 임시
  bare repository에서 tag object를 가져와 `git verify-tag`로 principal을 확인합니다. root helper가
  다시 검증한 같은 SHA만 설치하고, 이후 W-F1-C의 restart·smoke·rollback 트랜잭션이 실행됩니다.
- **거부**: `main`만 전진하거나 lightweight tag만 붙으면 `UNSIGNED-HEAD`로 helper를 호출하지
  않습니다. healthcheck의 `signed update trust` 검사가 같은 차단 사유를 기존 수리 티켓 경로에
  싣고, `current`는 그대로 유지됩니다.
- **키 교체**: allowed-signers를 새 키로 교체한 뒤에는 옛 키로 서명한 tag가 즉시
  `BAD-SIGNATURE`로 거부됩니다.
- **위험한 호환 모드**: `~/.hermes/node.toml`의 `require_signed_updates = false`만 과거의 mutable
  `main` 동작을 허용합니다. 제3자 설정에서 필드를 생략하면 기본값은 `true`입니다.
