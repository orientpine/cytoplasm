# autophagy-agents

연구자 한 사람이 자기 노드에서 돌리는 개인 에이전트 시스템이다. 메일·캘린더·문서·
노트·과제비 같은 실제 업무를 대신 처리하고, Discord를 통해 다른 연구자의 에이전트와
대화한다. **모든 외부효과는 소유자 본인의 승인을 거친다** — 이 한 문장이 이 저장소의
설계 중심이며, 나머지는 대부분 그 불변식을 지키기 위한 장치다.

## 왜 이런 모양인가

에이전트에게 실제 권한을 주면 두 가지가 동시에 필요해진다: 사람이 매번 확인하지
않아도 일이 진행될 것, 그리고 **사람이 승인하지 않은 일은 절대 일어나지 않을 것**.
둘을 함께 만족시키는 방법으로 이 시스템은 다음을 택했다.

- **읽기는 자유, 쓰기는 게이트.** 메일 발송·캘린더 등록·문서 저장·스킬 배포는 모두
  소유자의 ✅ 리액션 이후에만 실행된다. 승인은 내용 해시에 바인딩되므로, 승인 뒤
  내용이 바뀌면 실행되지 않는다.
- **fail-closed가 기본.** 설정이 없거나 권한을 확인할 수 없거나 판단이 모호하면
  실행하지 않는다. 조용히 넘어가는 경로를 만들지 않는다.
- **커밋됨 ≠ 배포됨.** 프로덕션에 도는 것은 불변 릴리스이고, 업데이트는 **서명된
  릴리스 태그**에만 수렴한다. 실패하면 자동으로 되돌리고 소유자에게 알린다.
- **신뢰 근원은 에이전트가 쓸 수 없는 곳에 둔다.** 승인 판정과 서명 검증이 읽는
  파일은 root 소유이며, 에이전트 계정이 그것을 바꿀 수 있으면 검증 전체가 무의미해진다.

## 연합 모델 — 각자 자기 설치를 소유한다

여러 연구자가 함께 쓰더라도 **중앙 서버도, 멀티테넌트 호스팅도, 공용 계정도 없다.**
각자 자기 호스트에 자기 설치를 갖는다. 자기 봇, 자기 자격증명, 자기 데이터,
그리고 **자기 승인 게이트**다.

그럼 "그룹"이란 무엇인가. 그룹은 서비스가 아니라 **공급망·정책 경계**이고, 물리적
구성물은 정확히 셋뿐이다:

1. 그룹 관리자가 소유한 **관리형 스킬 저장소**
2. 관리자의 **서명키 1쌍** (개인키는 관리자만, 팀원은 공개키만 갖는다)
3. **roster** — 팀원 명단

이 셋 말고 그룹을 표현하는 서버·DB·중앙 서비스는 없고, 앞으로도 만들지 않는다.

그래서 그룹 관리자가 **할 수 없는** 일이 분명하다:

- 팀원 설치의 외부효과를 **대리 승인할 수 없다.** 승인 게이트는 팀원 본인 것이다.
- 팀원의 자격증명·메일·노트·대화를 **볼 수 없다.**
- 이미 팀원 노드에 마운트된 스킬을 **원격으로 회수할 수 없다.** 관리자가 할 수 있는
  것은 배포 키 폐기(그 시점부터 새 릴리스 수신 차단)와 취소(revocation) 발행까지이며,
  실제 제거는 그 설치의 소유자가 실행한다. 이것은 결함이 아니라 "각자 자기 설치를
  소유한다"의 직접적인 귀결이다.

두 채널은 서로 다르다는 점도 중요하다. **소프트웨어 업데이트**는 업스트림에서 직접
받고, **스킬**은 그룹 관리자에게서 받는다. 그룹 관리자는 소프트웨어 유지보수자가
아니어도 된다. 그리고 스킬은 전파(fetch·서명검증·격리)까지만 자동이고, **live 마운트는
각자의 ✅ 없이는 절대 일어나지 않는다** — 자동 활성화는 공급망 침해가 조용히 팀
전체로 퍼지는 경로이기 때문에 영구 비목표다.

한 설치는 v1에서 **하나의 그룹**에만 속한다.

## 설치

**[docs/guide/install.md](docs/guide/install.md)** 가 설치 절차의 단일 진실이다.
먼저 [docs/guide/third-party-runtime-prereqs.md](docs/guide/third-party-runtime-prereqs.md)로
전제(Discord 앱·봇·채널, 모델 provider, Hermes 게이트웨이, 업데이트 신뢰키)를 준비한 뒤
설치 가이드를 따른다.

요약하면 이렇다:

```bash
# 무엇이 설치될지 먼저 본다 — root 불필요, 아무것도 쓰지 않는다
python3 -m automation.install \
    --config /tmp/node.toml \
    --update-trust-key <bundle>/update-trust.pub \
    --expect-update-trust-fingerprint 'SHA256:<공지된-지문>' \
    --dry-run

# 실제 설치 (멱등 — 막히면 고치고 같은 명령을 다시 실행한다)
sudo python3 -m automation.install --config /tmp/node.toml \
    --update-trust-key <bundle>/update-trust.pub \
    --expect-update-trust-fingerprint 'SHA256:<공지된-지문>'
```

업데이트 신뢰키의 지문은 이 README와 각 릴리스 노트에 공지되며, 설치 직후
**설치기가 아닌 경로로** 대조하는 것이 이 부트스트랩의 핵심이다.

## 구조

```
configs/        # 노드 config·라우팅 정책·환경 템플릿 등 설정 시드
skills/         # 에이전트 스킬 (메일·캘린더·문서·위키·할일 …)
automation/     # 오케스트레이션·승인 게이트·워처·배포·설치기
  install/      # 단일 노드 설치기 (python3 -m automation.install)
prompts/        # 프롬프트 자산
tests/
  unit/         # 단위 테스트
  e2e/
    scenarios/  # E2E 시나리오
docs/
  guide/            # 가이드 문서 (설치·전제·운영·규약)
  patch/            # 패치 노트
  qa/               # QA 증적
  troubleshooting/  # 트러블슈팅
logs/           # 로그 (git 미추적, 디렉토리만 유지)
.omo/           # 계획/오케스트레이션 상태 (repo에 포함)
```
